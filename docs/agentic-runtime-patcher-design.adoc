= ndh omo/agent runtime patcher — design
:toc:

NOTE: Detailed spec: `omo-patch-spec.adoc` (omo harness + agentic assets).

== Context

* Chosen agentic harness: *omo*.
* Problem: declaring every skill/agent that might be needed for a task type is too costly — all of them load into every context.
* Need: select at runtime the agents/skills actually needed for a given task type, by patching agentic assets (JSON + Markdown) instead of declaring them all upfront.
* Tools: `yq-go` (JSON), `mdpatch` from `github:coddingtonbear/markdown-patch` (structure-aware Markdown), packaged in ndh and installed via flox from the flake.

== Externalized agentic assets (.d)

* Agentic assets no longer live as monolithic files under `hosts/*`.
* They are split into `<x>.d/` directories (e.g. `modules/home-manager/omo.d/`, `modules/home-manager/agent.d/`), like bash scripts (`flox-config.d/`, `manage-tailnet.d/`).
* Each `.d` holds declarative fragments: `*.yaml` (patches) + source files (json, md, jsonc).
* Home-manager activation assembles/patches from these fragments instead of writing a static file.

== YAML fragments

* Patches are expressed in YAML (readable, diff-friendly), not JSON.
* A YAML fragment describes: target (asset), kind (json|markdown), operation (set|merge|replace|insert|delete), selector, value.

[source,yaml]
----
profile: ndh-host-provision
targets:
  - path: ~/.omo/omo.jsonc
    kind: json
    patches:
      - op: set
        selector: .categories.quick.model
        value: litellm-bioskop/agent
  - path: ~/.agents/skills/foo/SKILL.md
    kind: markdown
    patches:
      - op: replace
        heading: "## When to use"
        value: |
          Updated content.
----

== Markdown patching tool

* Chosen: `mdpatch` (`github:coddingtonbear/markdown-patch`) — structure-aware edits (headings, frontmatter, block refs), no sed/regex.
* Lighter alternative if needed: a small Node script with `gray-matter` + `marked`, but that adds npm deps to package.
* Decision: mdpatch for runtime (packageable via buildNpmPackage), with a minimal Node-script fallback for simple cases.

== Single command: omo-patch

One command, two scopes (repo-local and global), each with its own physical locations (because each harness discovers assets where it expects them):

=== Repo-local scope (inside the project)

* `.omo/` — project omo config: `init-deep.json`, hooks (`hooks/`), project settings.
* `skills/` (or `.agents/skills/`) — project-specific skills (e.g. `senpi-runtime-patch`, `host-provision`, `nix-rebuild`, ...).
* Project-local `.omo/hooks/` are committed with the repo and apply to anyone working in it.

=== Global scope (the seat)

* `~/.omo/` — seat omo config: `omo.jsonc`, `agent/{models,settings,mcp}.json`, categories, agents, memory, `hooks/`, `plugins/`.
* `~/.agents/skills/` — cross-project skills (caveman, browseros-neo, git-master, debugging, ...).
* `~/.agents/.skill-lock.json` — installed-skills lock.

=== Resolution order

omo/senpi discover project-local assets first (when trusted), then global. `omo-patch --profile` applies to the scope implied by the current directory and the profile; a profile can target both scopes.

One command, two physical locations (because each harness discovers assets where it expects them):

* `~/.omo/` — oh-my-openagent: `omo.jsonc`, `agent/{models,settings,mcp}.json`, categories, agents, memory, `hooks/`, `plugins/` (extensions). `omo.jsonc` contains `disabled_skills`, which filters what loads from `~/.agents/skills/`.
* `~/.omo/hooks/` — lifecycle hooks (managed by physical presence)
* `~/.omo/plugins/` (extensions) — managed via omo install/remove
* `~/.agents/skills/` — skills (senpi discovers here). Managed by `omo-patch` (copy/remove + lock).

NOTE: Memory and MCP server management are left to omo itself; omo-patch only touches `agent/mcp.json` when a profile explicitly lists it.
* `~/.agents/.skill-lock.json` — installed-skills lock.

Hooks are managed by physical presence in `~/.omo/hooks/` (no toggle in omo.jsonc). Skills by physical presence in `~/.agents/skills/` plus `disabled_skills`.

== Use cases

=== omo-patch

[cols="1,3",options="header"]
|===
| Command | Effect
| `omo-patch add caveman` | remove `caveman` from `disabled_skills` in `omo.jsonc`; verify physical presence in `~/.agents/skills/`.
| `omo-patch remove caveman` | add `caveman` to `disabled_skills` (does not delete the file).
| `omo-patch list` | show enabled (present and not disabled) vs disabled skills.
| `omo-patch --profile opencode-go` | switch `settings.json` + `omo.jsonc` categories/agents to opencode-go free models.
| `omo-patch --profile omo-default` | restore local Llama state.
| `omo-patch --profile ndh-host-provision` | categories on `agent`/`agent-deep`, litellm concurrency 2, ssh/incus/tailnet skills enabled.
|===

== Repo-local skills (ndh)

Skills that live in the ndh repo (`skills/` or `.agents/skills/`) and are specific to ndh's domain. Generalized to rke2lab later.

[cols="1,3",options="header"]
|===
| Skill | Role
| `host-provision` | bootstrap a host (bioskop/nikopol/nerd-nixos): install, sops, join tailnet
| `nix-rebuild` | nixos-rebuild/darwin-rebuild, diagnose errors, rollback
| `secret-rotation` | sops edit, re-encrypt, propagate
| `tailnet-ops` | node status, add node, ACL, split-DNS
| `incus-ops` | manage incus instances/segments
| `storage-ops` | ZFS datasets, snapshots, replication
| `network-debug` | tailscale, DNS, NFS, kerberos
| `fleet-status` | inventory and health of hosts
| `senpi-runtime-patch` | (already present) repair the eval runtime
|===

Global (cross-project) skills stay in `~/.agents/skills/` (caveman, browseros-neo, git-master, debugging, ...).

=== Typical flow

[source,bash]
----
omo-patch --profile ndh-host-provision
----

Single command: installs skills, enables them in `disabled_skills`, switches models, installs hooks.

== UML — Sequence (applying a profile)

[mermaid]
....
sequenceDiagram
  autonumber
  actor Op as Operator
  participant Cmd as omo-patch
  participant Spec as Patch spec (ndh)
  participant Asset as Agentic assets
  participant Yq as yq-go
  participant Mdp as mdpatch

  Op->>Cmd: run --profile ndh-host-provision
  Cmd->>Spec: load the profile's patches
  Spec-->>Cmd: list (json, md)
  loop for each patch
    Cmd->>Asset: read target
    alt JSON
      Cmd->>Yq: apply set/merge
      Yq-->>Cmd: ok
    else Markdown
      Cmd->>Mdp: apply patch
      Mdp-->>Cmd: ok
    end
    Cmd->>Asset: write if changed
  end
  Cmd-->>Op: report (files touched)
....

== UML — Classes (concepts)

[mermaid]
....
classDiagram
  class PatchSpec {
    +profile: string
    +targets: AssetTarget[]
  }
  class AssetTarget {
    +path: string
    +kind: json|markdown
    +patches: Patch[]
  }
  class Patch {
    +op: set|merge|replace|insert|delete
    +selector: string
    +value: any
  }
  class Patcher {
    +applyJson(target, patch)
    +applyMarkdown(target, patch)
    +backup(target)
    +rollback(target)
  }
  PatchSpec "1" --> "*" AssetTarget
  AssetTarget "1" --> "*" Patch
  Patcher ..> AssetTarget
