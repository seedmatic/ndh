:toc: left

:icons: font

== Overview

This document describes how the *corporate bare-metal Mac* (`vz.nikopol`) and its peers —
the personal Tart VM `nikopol`, the Incus netflow instances, and the collector `nnh` —
address each other *reliably while the MacBook roams* across networks (home, office,
phone hotspot).

The design constraint: `vz.nikopol` is JAMF/corp-managed and *cannot run a VPN binary*
(no Tailscale/Headscale on it), so it is never a `mammoth-skate` member. But everything
that must talk to it lives on the *same physical machine*: the two Tart VMs (`nikopol`,
`nikopol-nixos`) bridge onto the same Wi-Fi L2 as the corp Mac. So the reliability problem
is *local*, not remote — the only thing that changes as the MacBook roams is the *DHCP
address* each interface gets from the current network.

The solution is a *static `172.16.6` overlay, local to this machine's virtualized space*:

* `vz.nikopol` holds a *static* `172.16.6.253/30` alias on `en0` — an address that does
  *not* change when the MacBook moves between networks.
* `nikopol-nixos` (the Incus host VM) holds `172.16.6.254/30` on `lan-br` (the other
  `/30` end, on the shared Wi-Fi L2) and `172.16.6.1/25` on a *managed Incus network*
  (Incus dnsmasq); it forwards (`ip_forward`) between the `/30` and the `/25` so the corp
  Mac reaches the netflow instances.
* The netflow instances (collector, …) live on the isolated managed `172.16.6.0/25` —
  behind `nikopol-nixos`, off the Wi-Fi L2, so their dnsmasq never competes with the
  roaming network's DHCP.

*No tailnet involvement for `172.16.6`.* The prefix is *not* advertised into
`mammoth-skate`; `nikopol-nixos` is a tailnet member for the *cluster* (rke2lab), but plays
no subnet-router role here. Remote access to `vz.nikopol` (e.g. from `bioskop`) rides the
existing pattern: `ProxyJump=nikopol` lands on the personal VM — itself a tailnet member —
and then hops *locally* to `172.16.6.253`. Nobody remote ever needs to reach `172.16.6`
directly, so there is nothing to advertise and no NAT anywhere (source IPs stay intact —
the point of the netflow project).

Why the static overlay is reachable at all: `nikopol-nixos`'s kernel and each Incus
instance egress via `lan-br → vmlan0 → vmnet` with distinct MACs; `vmnet` delivers frames
to `vz.nikopol`'s *secondary* `.253` alias by destination, independent of the source. The
old guest→host hairpin only ever bit the corp Mac's *primary* Wi-Fi address, not a
secondary `172.16` alias — so the overlay works in both directions on any network.

The address plan is a single source of truth in `catalog/default.nix` (`netplan.segments`,
the same data `nnh` uses for flow attribution). The Darwin and NixOS modules *derive*
`.253`/`.254`/the CIDRs — they never hard-code them.

*Legend*: the netflow instances live on the *isolated* managed bridge (`172.16.6.0/25`,

L3 forwarding between the `/30` link and the `/25`; no NAT, so the corp Mac sees real
source IPs and only needs one static route (`172.16.6.0/25 via .254`).

The exchanges that matter, in order.

participant "collector (nnh)\n(/25)" as COLL

== local: personal VM ↔ corp Mac ==
NK -> VZ : ssh vz.nikopol → 172.16.6.253 (direct L2, any network)

== remote: reach the corp Mac from off the MacBook ==
OP -> TS : ssh vz.nikopol
TS -> NK : ProxyJump=nikopol (tailnet member)
NK -> VZ : local hop → 172.16.6.253
note over NK,VZ: no 172.16 advertised — remote lands on the VM first,\nthen hops locally

== netflow export from the corp Mac ==
VZ -> NIXOS : flows → .254 (route 172.16.6.0/25 via .254)
NIXOS -> COLL: forward to collector on /25 (no NAT — src stays .253)
@enduml
----

*Legend*: every path terminates on the *local* `172.16.6` overlay; the tailnet only ever
carries the operator to the personal VM. No NAT anywhere — source IPs are preserved
end-to-end, which is what the netflow project needs.

== Address plan (single source of truth)

Declared once in `catalog/default.nix` (`netplan.segments`), consumed by the Darwin and
NixOS modules by derivation — never hard-coded twice.

[options="header"]
|===
| Address / CIDR | Role | Where it is set
| `172.16.6.0/25` | managed Incus network (dnsmasq) for netflow instances | Incus managed bridge on `nikopol-nixos`
| `172.16.6.1` | managed-network gateway | Incus bridge (on `nikopol-nixos`)
| `172.16.6.252/30` | static P2P link, corp Mac ↔ Incus host | catalog segment `nikopol-roaming-link`
| `172.16.6.253` | `vz.nikopol` en0 alias (static, roaming-stable) | Darwin static-alias module (derived from catalog)
| `172.16.6.254` | `nikopol-nixos` link end (on `lan-br`) | NixOS, on `lan-br`
|===

The `172.16.0.0/12` supernet is reserved for roaming; each corp bare-metal host takes its
own non-overlapping slice (nikopol = `172.16.6.0/24`, decomposed into the `/25` net and the
`/30` link). `nnh` attributes flows most-specific-prefix-wins, so the `/25`
(`nikopol-roaming-net`) and the `/30` (`nikopol-roaming-link`) are declared as separate
segments. The corp Mac carries one static route — `172.16.6.0/25 via 172.16.6.254`, to
reach the collector — also derived from the catalog. Nothing is advertised into the tailnet.

== Usage patterns

=== Derive addresses from the catalog — never hard-code

✅ *DO* — read the segment from `ndh.context.catalog.netplan.segments` in the module:

[source,nix]
----
# Darwin module for vz.nikopol
let
  seg = lib.findFirst (s: s.name == "nikopol-roaming-link")
          (throw "roaming link segment missing") netplan.segments;
  # .253 = corp Mac, .254 = Incus host — one place, both sides derive from it
in { networking.staticRoutes = { ... }; }
----

❌ *DON'T* — repeat the literals in the Darwin alias, the NixOS route, and the SSH alias.
Three copies drift; that is exactly the identifier-mismatch class of bug the project forbids.

=== Keep the managed Incus network *managed*, never bridged

✅ *DO* — a managed bridge (`incus network create … ipv4.address=172.16.6.1/25`) with
Incus's dnsmasq bound to that bridge only. It is isolated from the Wi-Fi L2, so no DHCP
collision with the roaming network is possible.

❌ *DON'T* — a `bridged`/`macvlan` NIC on `en0` for these instances: their DHCP would land
on the Wi-Fi L2 and fight the hotspot's DHCP. The corp Mac's `.253` and the host's `.254`
are *static* — nothing on the `172.16.6` overlay uses DHCP on the physical L2.

=== Reach `vz.nikopol` at a fixed address; ProxyJump for remote

✅ *DO* — the SSH alias points at the static `.253`. From the personal VM it resolves
directly; from any other host it jumps through the VM first:

[source]
----
# on the nikopol VM — direct local hop
Host vz.nikopol
  HostName 172.16.6.253
  User stephane.lacoin

# on bioskop / any remote operator host — land on the VM (tailnet member), then hop
Host vz.nikopol
  HostName 172.16.6.253
  User stephane.lacoin
  ProxyJump nikopol
----

❌ *DON'T* — advertise `172.16.6.0/24` into the tailnet to reach `.253` directly, or
resolve the corp Mac's live Wi-Fi IP via an ARP-cache lookup / virtiofs "published IP".
The advertise is unnecessary (ProxyJump already lands on a tailnet member), and the
ARP/virtiofs paths pre-date the static overlay and are removed.

== Setup

. *Catalog* — declare the roaming segments (done): `nikopol-roaming-net` = `172.16.6.0/25`,
  `nikopol-roaming-link` = `172.16.6.252/30`.
. *Incus managed network* on `nikopol-nixos` — `172.16.6.0/25` (gateway `.1`) with dnsmasq;
  attach the netflow instances. Add the new bridge name to
  `networking.firewall.trustedInterfaces`.
. *Incus host `/30` end + forwarding* — `172.16.6.254/30` secondary address on `lan-br`,
  and `boot.kernel.sysctl."net.ipv4.ip_forward" = 1` so the corp Mac reaches the `/25`.
  *No* `services.headscale-gateway`, *no* advertise, *no* NAT.
. *Corp Mac* (`vz.nikopol`) — a Darwin static-alias module (launchd, on the
  `network-bond.nix` pattern) sets `172.16.6.253/30` on `en0`, plus `networking.staticRoutes`
  for `172.16.6.0/25 via 172.16.6.254`. Both derived from the catalog.
. *SSH alias* — `vz.nikopol` → `HostName 172.16.6.253`; add `ProxyJump nikopol` on hosts
  other than the personal VM.

== Troubleshooting

Cannot reach `vz.nikopol` at `.253`::
Check the alias is set on `en0` (`ifconfig en0 | grep 172.16.6.253`). From a remote host,
check `ProxyJump=nikopol` resolves (the VM is a tailnet member). For the collector path,
check `net.ipv4.ip_forward=1` on `nikopol-nixos` and the `172.16.6.0/25 via .254` route on
the corp Mac.

netflow export not arriving::
From the corp Mac confirm the `172.16.6.0/25 via 172.16.6.254` route
(`route -n get 172.16.6.3`); on `nikopol-nixos` confirm the collector holds its dnsmasq
lease on the managed bridge.

DHCP weirdness on a hotspot::
Ensure the `172.16.6` net is a *managed* (isolated) Incus bridge, not bridged on `en0`.
Only the hotspot should serve DHCP on the Wi-Fi L2.
