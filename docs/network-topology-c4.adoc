= Baremetal Instance Segments & vz-host Access (C4-Style UML)
:toc: left
:toclevels: 3
:icons: font

== Overview

Each *baremetal host* owns a per-host *instance segment*: a *systemd-networkd* bridge with
its own dnsmasq, a DNS domain `.<host>`, and a subnet route advertised into the tailnet.

NOTE: It was an *Incus managed network* until 2026-09-25. Clustering forced the change: Incus
requires that "all members of a cluster must have identical networks defined" and `ipv4.address` may
not differ per member, while these differ per host BY DESIGN — and worse, a cluster-wide network is
materialised on EVERY member, so each host would carry a bridge holding the OTHER's `/21` and route
the cross-host reach into a dead interface. Incus now manages no network at all; instances attach to
these bridges as an unmanaged `parent`. See `modules/nixos/baremetal-segment.nix` and
`modules/nixos/cluster-vmnet.nix`.
This lets any tailnet peer resolve `<instance>.<host>` (split-DNS to that segment's
dnsmasq) and reach the instances — and, for `nikopol`, the *corporate bare-metal Mac*
`vzhost.nikopol` that cannot join the tailnet.

The `nikopol` segment concretely:

* `nikopol-nixos` (the Incus host VM, a tailnet member) owns the *networkd bridge*
  `fabric-br` = `172.16.16.0/21`, whose addressing, DHCP and `.nikopol` zone are served by the
  host's own `services.dnsmasq` (`local=/nikopol/` makes it authoritative), carrying the netflow
  instances (collector `nnh`, …). Its dnsmasq also holds a static `host-record` for
  `vzhost.nikopol → 172.16.24.2`.
  `ConfigureWithoutCarrier = true` is load-bearing: a memberless bridge has no carrier and networkd
  would withhold the address, leaving dnsmasq nothing to bind — which is backwards, since the first
  instance needs DHCP to come up.
* A static `/30` point-to-point link (`172.16.24.0/30`) on the shared Wi-Fi L2 joins
  `vzhost.nikopol` (`172.16.24.2`) to `nikopol-nixos` (`172.16.24.1` on `lan-br`); `nikopol-nixos` forwards
  (`ip_forward`) between the `/30` and the `/21`.
* `nikopol-nixos` *advertises* the aggregate `172.16.16.0/20` into the tailnet, and
  *split-DNS* points the `.nikopol` domain at its dnsmasq (`172.16.16.1`). A tailnet peer
  thus resolves `collector.nikopol` / `vzhost.nikopol` and reaches them — the corp Mac
  included — without the Mac ever being a tailnet member.
  The aggregate is a `/20` and not the `/21`: it covers BOTH halves of the host's slice, so the
  `/30` link to the corp Mac rides the same single route. Narrowing it to the `/21` would cut
  `vzhost.nikopol` off, since the `/30` sits in the high half.

Three further facts, added 2026-09-27:

* *Each host also advertises its `vmnet` cluster segments* (`cluster-vmnet.nix`), so a cluster's
  kube-vip VIP and cilium LB pool are reachable from the tailnet. The advertiser is the host that
  OWNS the bridge — not a pod inside the cluster, which is what rke2lab rendered until then and
  which died with the cluster it was meant to make debuggable.
* *Each host ACCEPTS its peers' routes* (`acceptRoutes = true`) and forwards the peer's zone to that
  peer's dnsmasq (`server=/<peer>/<peer netGateway>`), so `nixos.<other-host>` resolves and routes
  from either side. Routing gives the address, the dnsmasq forward gives the name.
* *The home LAN is NOT advertised*, deliberately. A LAN-fixed host used to advertise
  `netplan.lan.cidr` so off-site peers could reach every device at home; a peer that accepts routes
  AND sits on that LAN then installs `192.168.1.0/24 → utun0`, displacing its own connected route.
  It cost a LAN outage on 2026-09-27 — see the ⚠️ note in `modules/nixos/baremetal-segment.nix`.
  `--accept-routes` is all-or-nothing per client and grants' `via` only chooses BETWEEN routers, so
  no scoping makes it safe.

*No NAT anywhere* — source IPs are preserved end-to-end (the point of the netflow
project). The corp Mac carries a return route to the tailnet range (`100.64.0.0/10 via
172.16.24.1`), so replies find their way back without masquerading.

[IMPORTANT]
====
*Controller: Tailscale SaaS; Headscale is HIBERNATING.* The fleet's live control-plane is
*Tailscale SaaS* (the `mammoth-skate` tailnet). Self-hosted Headscale is scaffolded in the repo
but not deployed, and its policy file `catalog/tailnet/acl.hujson` is NOT what the fleet runs —
the applied policy is generated (`tailnetAclCanonical` in
`modules/.common.d/manage-tailnet.d/default.nix`).

All five control-plane operations are now *declarative*, and no longer "performed at runtime in
the admin console":

* *advertising* — `networking.headscale.advertiseRoutes`, derived from the catalog
  (`baremetal-segment.nix` for the `/20`, `cluster-vmnet.nix` for each `vmnet` `/21`);
* *approving* — `autoApprovers.routes` in the generated policy, keyed on `tag:nixos`, pushed by
  `manage-tailnet --sync-policy`;
* *authorising* — the policy's `grants` block, generated from the same catalog (it was `acls`
  until 2026-09-27 — see <<authorisation>>);
* *defining services* — `manage-tailnet --sync-services`, from
  `catalog.netplan.tailnet.services`. The vendor documents this one as admin-console-only;
  that is measurably false, and <<authorisation>> records the probe;
* *split-DNS* — `manage-tailnet --sync-dns`, which PATCHes only the zones this catalog declares.
  That was the last tailnet fact outside git, and its absence is what let the map keep pointing at a
  retired resolver through the 2026-09-23 fabric renumbering.
====

The corp-Mac side is *not* a nix-darwin configuration (the corp Mac has no darwin config —
it is JAMF-managed). Its addressing is delivered by the *baremetal-link* package
(`pkgs/baremetal-link.d/`): an idempotent script rendered from the catalog and delivered as
*text* over `ssh`, run as root — no nix runtime on the corp Mac, bash-3.2 compatible (see
<<setup>>).

All addresses are a single source of truth in `catalog/default.nix`
(`netplan.baremetal.nikopol`), consumed by the NixOS Incus host and the corp-Mac package by
derivation — never hard-coded twice.

== Address plan (single source of truth)

`catalog/default.nix` → `netplan.baremetal.<host>`. Consumed by the NixOS Incus host and
the corp-Mac package by derivation. `nikopol` (below) is the *complex* case — an off-tailnet
corp Mac reached over a `/30`; `bioskop` is the *simple* case (see below).

Every value below is *computed* from the host's `hostId` (nikopol 1) by <<target-carve,the
carve>> — the entry declares only what no arithmetic can know: the host's name, the nature of
its vz-host, and whether it is fixed to the home LAN.

[options="header"]
|===
| Field | Value | Role
| `domain` | `nikopol` | dnsmasq DNS zone + split-DNS domain
| `advertiseCidr` | `172.16.16.0/20` | the whole slice — ONE tailnet route per bare-metal
| `netCidr` | `172.16.16.0/21` | managed Incus network (dnsmasq) — slots 0-7, on `fabric-br`
| `netGateway` | `172.16.16.1` | Incus bridge + dnsmasq + split-DNS target
| `dynamicCidr` | `172.16.16.0/27` | DHCP pool; statics live above it (filled top-down)
| `dhcpRange` | `172.16.16.2-172.16.16.30` | dnsmasq range inside the dynamic `/27` — see the caution below
| `linkCidr` | `172.16.24.0/30` | static P2P link, corp Mac ↔ Incus host (slot 8)
| `hostAddress` | `172.16.24.1` | `nikopol-nixos` link end on `lan-br` (subnet router)
| `vzHostAddress` | `172.16.24.2` | `vzhost.nikopol` NIC alias + dnsmasq `host-record`
|===

The segment is also declared in `netplan.segments` (derived from `baremetal`) for `nnh`
flow attribution: `nikopol-baremetal-net` (the `/21`) + `nikopol-baremetal-link` (the `/30`),
under the `172.16.0.0/12` `baremetal` supernet.

=== Second host — bioskop (the same shape, a different reason)

`bioskop` is a *personal* Mac Mini already on the tailnet + home LAN, so unlike nikopol it is
reachable *without* the `/30` — and it declares one anyway, because its *tenants* are not. A
cluster node addressed in this segment cannot reach `192.168.1.129`: `baremetal-nat` masquerades
only public-bound egress (the LAN is in its exclusion set) and the home LAN has no return route to
`172.16.0.0/21`. So the vz-host takes a segment address on the same `/30` shape nikopol uses, and
the Mac *keeps* `192.168.1.129` — the alias is additional, the LAN identity untouched.

[options="header"]
|===
| Field | Value | Role
| `domain` | `bioskop` | dnsmasq DNS zone + split-DNS domain
| `advertiseCidr` | `172.16.0.0/20` | the whole slice — ONE tailnet route per bare-metal
| `netCidr` | `172.16.0.0/21` | managed Incus network (dnsmasq) — slots 0-7, on `fabric-br`
| `netGateway` | `172.16.0.1` | Incus bridge + dnsmasq + split-DNS target
| `dynamicCidr` | `172.16.0.0/27` | DHCP pool; statics live above it (filled top-down)
| `dhcpRange` | `172.16.0.2-172.16.0.30` | dnsmasq range inside the dynamic `/27` — see the caution below
| `linkCidr` | `172.16.8.0/30` | static P2P link: Mac Mini ↔ Incus host (slot 8)
| `hostAddress` | `172.16.8.1` | `bioskop-nixos` link end on `lan-br` (subnet router)
| `vzHostAddress` | `172.16.8.2` | `vzhost.bioskop` dnsmasq `host-record` (Mac Mini alias)
|===

[CAUTION]
====
`dhcpRange` is a *correctness* requirement, not tidiness. Without `ipv4.dhcp.ranges` dnsmasq
auto-ranges the whole managed net, so a `fabric-br` recreate can hand a *pinned* address to a DHCP
client — the exact failure that stalled the nnh pipeline on nikopol.
====

The split-DNS/advertise pattern applies identically on `bioskop-nixos` (its `.bioskop` zone), so
`ssh vzhost.bioskop` and `<inst>.bioskop` resolve uniformly across both bare-metals. The two
entries now differ only in `lanAttachment` (a physical fact: a roaming laptop must not advertise a
LAN it may leave); `staticHosts` is gone from both, derived from the published segments instead.

The numbering above IS <<target-carve,the carve>>, applied 2026-09-23. It replaced an arbitrary
literal pair — nikopol `172.16.6.0/25`, bioskop `172.16.7.0/25`, inverted against their `hostId`
0/1 — and a `/30` island at `.252`, outside the `/25` it looked adjacent to.

[NOTE]
====
*The order was CONSTRAINED, and not the way this section first predicted.* It said both hosts had to
move in the *same* change. Measured, the constraint was a *sequence*: bioskop's target `/21`
(`172.16.0.0/21`) **contains** nikopol's former `/25` (`172.16.6.0/25`), so moving bioskop first
would have made `172.16.6.x` on-link there and shadowed the tailnet route to nikopol's live segment.
nikopol's target `/20` contained nothing live, so it moved first and the containment dissolved
before bioskop claimed its range. "Together" would have worked too, but it is a stronger
requirement than the problem needs — and one that is harder to execute on two machines that are not
both reachable at the same moment.
====

[[target-carve]]
=== The carve — DERIVED from the bare-metal, with the link encoded in the address

[IMPORTANT]
====
*Applied 2026-09-23.* The tables above are this carve's output, not a separate plan. The motive was not
tidiness: it makes each bare-metal's segment the *sole* address authority for everything running behind
it, so a host on a mobile hotspot (nikopol) is as well-addressed as one on the home LAN. rke2lab's
cluster nodes are the segment's main tenant.

*The addresses stopped being allocated and started being derived* — from rke2lab's `hostId`
(`bioskop = 0`, `nikopol = 1`, `test = 2`), the same table that already generates the vmnet plane, the
ULA mirror and the MACs. So `netCidr`/`netGateway`/`linkCidr` are *projections* of rke2lab's blueprint.
The full plan, its invariants and the exhaustive check that guards it live in rke2lab's
`docs/architecture/atlas/netplan.adoc`.

The direction is forced, and worth stating because the reverse looks equally natural: ndh imports
rke2lab's blueprint at flake-eval time, so having rke2lab read `hostId` out of THIS catalog instead
would close an eval cycle.
====

Before this, an address did *not* tell you which link it was on: `netCidr` was a `/25` (`.0-.127`) on the
bridge while `linkCidr` sat at `.252` — **outside** that `/25`, on `lan-br` — and `.128-.251` was claimed
by nothing. The carve encodes the link *in the address*: one bit of the third octet.

....
172.16.<hostId*16>.0/20        advertiseCidr — ONE tailnet route per bare-metal
│                                bioskop .0/20 · nikopol .16/20 · test .32/20
├── slots 0-7  →  ON fabric-br   (the Incus L2, gateway .1, dnsmasq zone .<domain>)
│   ├── slot 0   .0/24          HOST INFRA — ndh owns
│   │            ├── .1         fabric-br gateway (address is .1/21, covering slots 0-7)
│   │            ├── .2-.30     dynamic DHCP pool (= dynamicCidr .0/27)
│   │            └── .124-.126  nnh pinned collector (nikopol)
│   ├── slots 1-4 .1-.4 .0/24   ONE /24 PER CLUSTER — rke2lab owns (slot = 1 + roleId)
│   │                             mgmt slot 1 · wrkld slot 2 · two spare role slots
│   └── slots 5-7               spare, on fabric-br
└── slots 8-15 →  OFF fabric-br  (other links)
    └── slot 8   .0/30          static P2P link, on lan-br: Incus host .1 ↔ vz-host .2
....

Read it as: *third-octet offset < 8 ⇒ on `fabric-br`; ≥ 8 ⇒ another link.* That is the property the `.252`
island lacked.

Per-host consequences — every value derived, none chosen:

|===
| Field | nikopol (`hostId 1`) | bioskop (`hostId 0`)

| `advertiseCidr` | `172.16.6.0/24` → `172.16.16.0/20` | `172.16.7.0/24` → `172.16.0.0/20`
| `netCidr` (fabric-br) | `172.16.6.0/25` → `172.16.16.0/21` | `172.16.7.0/25` → `172.16.0.0/21`
| `netGateway` | `.6.1` → `172.16.16.1` | `.7.1` → `172.16.0.1`

| `linkCidr` | `172.16.6.252/30` → `172.16.24.0/30` | `172.16.7.252/30` → `172.16.8.0/30`
| `hostAddress` | `.6.254` → `172.16.24.1` | `.7.254` → `172.16.8.1`

|===

[IMPORTANT]
====
*The left-hand values are historical* — the renumbering landed 2026-09-23 and the right-hand
column is what the catalog derives today. It was a pure renumbering: both entries already shared one
shape, only the numbers were allocated rather than derived.

The ORDER mattered, and the constraint was a sequence rather than atomicity — see the note under the
address plan above. It also had two out-of-repo consequences, both since discharged: nnh's pinned
literals (its `/30` and the instance addresses, now declared once) and a redeploy of each vz-host's
`baremetal-link` daemon.
====

Three notes on why these are not cosmetic:

* *bioskop's `dhcpRange` was a correctness gap, not an omission* (now closed). Without
  `ipv4.dhcp.ranges` dnsmasq auto-ranges the whole managed net, so a `fabric-br` recreate can hand a
  *pinned* address to a DHCP client — the exact failure that stalled the nnh pipeline (see the
  `staticHosts` rationale, now in `modules/nixos/baremetal-segment.nix`). rke2lab's addressing is entirely pinned, so this
  had to land *before* the first cluster node attaches.
* *bioskop's vz-host gained a segment address for a functional reason, not for symmetry* (now landed
  at `172.16.8.2`). Once the cluster nodes live in the fabric they cannot reach `192.168.0.0/16`
  (excluded from `baremetal-nat`'s masquerade, and the LAN has no return route), so a `vzhost.bioskop`
  answering only at a LAN address would be unreachable from the tenants now sharing its host. The Mac
  *keeps* `192.168.1.129`.
* *`192.168.1.0/24` is a frozen input.* No device on the home LAN renumbers. The only LAN-side effects
  are deletions — rke2lab stops claiming `192.168.1.128/25`, and the `kind = "rke2"` reservations leave
  the bbox. Both reversible.

== Usage patterns

=== Derive addresses from the catalog — never hard-code

✅ *DO* — read `netplan.baremetal.<host>` in the module/package:

[source,nix]
----
let bm = ndh.context.catalog.netplan.baremetal.nikopol;
in { /* bm.netGateway, bm.hostAddress, bm.vzHostAddress, bm.advertiseCidr, bm.domain */ }
----

❌ *DON'T* — repeat `172.16.24.2`/`172.16.24.1`/the CIDRs in the corp-Mac package, the NixOS host,
and the split-DNS entry. Three copies drift.

=== Name the vz-host's NIC by SERVICE, from `hardware.vmBridgeService`

The `/30` alias must land on the adapter the vz guest is *bridged* onto — that is what puts the
link's two ends (the Mac's alias, the guest's `lan-br`) on a shared L2. So it is read from the one
declaration Tart's bridge mode already uses:

[source,nix]
----
# hosts/<host>/hardware.nix — the single source
vmBridgeService = "Thunderbolt Ethernet Slot 1";   # bioskop; nikopol is "Wi-Fi"
----

✅ *DO* — declare a macOS *service* name and resolve it to a device at run time
(`networksetup -listnetworkserviceorder`), as `baremetal-link`'s `link-up.sh` does on every
`WatchPaths` burst.

❌ *DON'T* — write an `enX` device name anywhere. Two independent reasons, both measured on
2026-09-23:

* *It is not the same device on two Macs.* `baremetalLinkVars` carried a flat `interface = "en0"`,
  accidentally right for nikopol and silently wrong for bioskop, whose bridged adapter is `en9`.
* *It is not stable on one Mac.* Numbering follows adapter enumeration. On bioskop, `Wi-Fi` is
  **`en1`** and `en0` is the built-in `Ethernet` — so the hardcoded `en0` would not merely have
  missed the target, it would have aliased a different, LAN-facing NIC. Resolving per run also
  makes the link self-heal after a dock is added or removed, with no redeploy.

=== Managed Incus network, never bridged

✅ *DO* — a managed bridge (`fabric-br`, Incus dnsmasq bound to it), isolated from the Wi-Fi
L2 → no DHCP collision with the local network.
❌ *DON'T* — bridge/macvlan the instances onto `en0`.

=== Reach `vzhost.nikopol` by DNS name

✅ *DO* — `vzhost.nikopol` is a real DNS name (dnsmasq `host-record`, split-DNS'd into the
tailnet). SSH resolves it via the tailnet resolver; no `HostName`/`ProxyJump`/resolver
needed.
❌ *DON'T* — resolve the corp Mac's live Wi-Fi IP via an ARP lookup or a virtiofs published
file (the retired resolver), or hard-code a `HostName`.

== Setup

=== Declarative (in this repo)

. *Catalog* — `netplan.baremetal.nikopol` (done): domain, CIDRs, both `/30` ends,
  `advertiseCidr` — all DERIVED from `hostId`, see <<target-carve,the carve>>.
. *Incus host* (`hosts/nikopol/nixos.nix`) — `fabric-br` managed `/21` with
  `dns.domain=nikopol` + `raw.dnsmasq` `host-record=vzhost.nikopol,172.16.24.2`;
  `172.16.24.1/30` secondary on `lan-br`; `ip_forward`.
. *baremetal-link package* (`pkgs/baremetal-link.d/`) — deployed with
  `nix run .#nikopol-baremetal-link-deploy` (teardown: `… -- --uninstall`). It delivers the
  catalog-rendered install script as *text* over `ssh vzhost.nikopol` (first-run bootstrap
  fallback `nikopol-vzhost.lan`, since the alias isn't set yet) and runs it as root. The script
  installs the `io.seedmatic.baremetal-link` *WatchPaths* LaunchDaemon that (re-)applies the
  NIC alias `172.16.24.2/30` + routes `172.16.16.0/21 via 172.16.24.1` and
  `100.64.0.0/10 via 172.16.24.1` at load and on every Wi-Fi re-association. No nix runtime on the corp Mac; every
  address derives from `netplan.baremetal.nikopol` — never hand-typed.

=== Reconciled onto the Tailscale SaaS controller

Not a console step among them any more — each is generated from the catalog and pushed:

. *advertise* — `networking.headscale.advertiseRoutes` carries `172.16.16.0/20` on
  `nikopol-nixos`; consumers set `acceptRoutes`. Neither is a `tailscale up` flag.
. *approve* — `autoApprovers.routes` maps the `/20` to `tag:nixos`, so the route is approved as
  soon as it is advertised. Pushed by `manage-tailnet --sync-policy --apply`.
. *split-DNS* — `manage-tailnet --sync-dns --apply` PATCHes `nikopol` → `172.16.16.1`.

⚠️ The approver must follow the *advertiser*: an `autoApprovers.routes` entry left keyed on the
tag of a retired announcer leaves the route PENDING for ever, silently. That is exactly what the
`vmnet` family did while it was still mapped to `tag:k8s` after the announcing `Connector` pod was
removed on 2026-09-27.

NOTE: Headscale is HIBERNATING, not next in line. Were it revived, these same catalog values would
drive its daemon's `dns.nameservers.split` + the client `--advertise-routes`. Its policy file
`catalog/tailnet/acl.hujson` is a SEPARATE artefact from the generated SaaS policy and does not
track it — do not read one for the other.

== Authorisation model, and reaching a screen from off-site

Decided AND shipped 2026-09-27, verified live the same evening. Recorded here because the
reasoning is what dates, not the syntax.

=== Verified live, 2026-09-27 evening

[options="header"]
|===
| Service | Virtual IP | MagicDNS name | Type inferred
| `svc:bbox` | `100.70.201.227` | `bbox.mammoth-skate.ts.net` | `http`
| `svc:rdp-bioskop` | `100.73.113.146` | `rdp-bioskop.mammoth-skate.ts.net` | `vnc`
| `svc:rdp-nikopol` | `100.77.231.247` | `rdp-nikopol.mammoth-skate.ts.net` | `vnc`
| `svc:rdp-vzhost-nikopol` | `100.102.16.100` | `rdp-vzhost-nikopol.mammoth-skate.ts.net` | `vnc`
|===

`curl -k https://bbox.mammoth-skate.ts.net/api/v1/device` answers *HTTP 200*, and
`bbox-reconcile` reads `/dhcp/clients` over it — so the `Host:` header doubt is settled: the
router does not care which name was dialled. `192.168.1.0/24` therefore has no remaining
reason to be routed, the bbox having been the last thing on that LAN any code needed.

Three traps this cost, all of which look like something else:

Mixed autogroup spellings:: The first `--sync-policy --apply` was REJECTED — _"ACLs contain a mix
of old-style `autogroup:members` and new-style `autogroup:member`; use one or the other."_
Consistency is a property of the WHOLE policy, so translating `grants` was not enough: the
`ssh` block carried the plural, and so did `nodeAttrs`, a field this reconcile PRESERVES
(Tailscale's own Funnel/Taildrive defaults). ★ A canonical that owns only some fields cannot
by itself guarantee a whole-file property — the same lesson as the merged `autoApprovers`,
arriving from the opposite direction.

`--all` before the filename:: `serve set-config` parses flags only up to the first positional
argument, so `set-config <file> --all` makes `--all` a second positional and fails with
_"must specify filename"_ — while the CLI's own usage line prints `set-config <file> [--all]`,
the order that does NOT work. ⚠️ The activation is deliberately non-fatal (it must not fail
because the daemon is logged out), which means a wrong invocation is indistinguishable from a
logged-out daemon: bioskop advertised NOTHING while all four services existed.

`addrs` on update:: Tailscale auto-allocates the address pair on create and REJECTS a later
update that omits it, so `--sync-services` fetches the live object first and merges ours on
top. Writing the catalog's object verbatim would have worked exactly once.

=== `acls` → `grants`: the reason to stay on the legacy block has expired

The generated policy has always used the legacy `acls` block, and the rationale was explicit in
`manage-tailnet.d/default.nix`: *"so the same tag vocabulary stays usable by the headscale
controller too"*. Headscale does not understand `grants`. With Headscale hibernating and its policy
now known to be a separate artefact that nothing syncs, that coupling is gone — so `grants` is
available.

Two things this does NOT buy, stated so nobody re-derives them:

* It is *not* a prerequisite for Tailscale Services. A `svc:` destination is accepted in *both*
  syntaxes; the vendor documents the legacy form too (`{"src": …, "dst": ["svc:web-server"],
  "ip": ["443"]}`).
* It does *not* make advertising the home LAN safe. Grants' `via` *chooses between* routers; it
  does not withhold a prefix from a peer. The 2026-09-27 LAN outage is not addressed by it.

⚠️ *The migration trap is in the reconciler, not the policy.* `sync_policy` does
`.acls = canonical.acls` — a REPLACE — and touches only the keys it names, preserving everything
else. So a canonical `.grants` block would be *silently dropped*, while the superseded `.acls`
stayed live; and since the effective policy is the permissive union of the two, the old block would
keep granting. The migration is therefore: write `.grants`, and `del(.acls)` in the *same* change.
Anything less is inoperative and more permissive than it looks.

⚠️ *Open defect, one line.* The segment CIDRs sit in the `dst` of the `console` rule only; the
`headless` rule's `dst` is just `tag:headless:*`. A node installs only the routes it is
ACL-permitted to reach, so `acceptRoutes = true` on the hosts (added the same day) is INERT for
host-to-host traffic — neither NixOS host may reach the other's segments, nor a `console` host at
all. Fix: add `baremetalCidrs ++ vmnetCidrs` to that rule's `dst`.

★ *Read that defect from the policy, never from a port probe.* A denial by the tailnet packet filter
is a DROP, so it TIMES OUT. `Connection refused` is an RST, which means the packet ARRIVED and
nothing was listening — it proves reachability, not denial. Conflating the two is what briefly made
this defect look confirmed by measurement when the measurement said the opposite.

=== Tailscale Services — the mechanism for a remote screen

The need: reach `bioskop`'s shared screen, and `vzhost.nikopol`'s, while `nikopol` is roaming.
Every simpler path was eliminated by measurement — `tailscale serve` alone is localhost-only, the
SaaS forbids arbitrary MagicDNS records, a dnsmasq `cname` refuses an upstream target, and
`apertures` is AI-agent governance. Services answer because a service has *its own virtual IP and
name*, several nodes may advertise one (HA), and — the decisive property — those virtual IPs are
*accepted by clients regardless of `--accept-routes`*. No route is installed, so the class of
failure that caused the LAN outage becomes structurally impossible.

Three facts confirmed against the *fork we build* (`overlays/tailscale.nix`, clone at
`7b962478b`, the exact commit of the installed 1.102.3 binary) rather than the documentation:

Name syntax:: `svc:<name>` — `tailscale serve drain --help` states *"`<service>` should be a
service name (e.g., `svc:my-service`)"*.

Remote target:: *Supported* — and here the documentation is WRONG. The configuration-file page
describes targets as local; `isRemote()` in `cmd/tailscale/cli/serve_v2.go:1176` exists precisely
to single out targets that are *not* `localhost`/`127.0.0.1`/`::1`. ⚠️ The platform guard is
*fatal*, not a warning (`return err`): a **Mac App Store or system-extension** tailscaled refuses a
remote target outright, as does **Linux without `SO_MARK`**. Our Macs run the standalone build from
this overlay, so they are eligible — but a switch to the Mac App Store client would break this
silently at the CLI.

ACL shape:: Three requirements, of which the middle one is the trap. (a) A service host *must* be a
tagged node — *"You cannot use a device authenticated with a user account as a Service host"*;
`bioskop`/`nikopol` already carry `tag:console`. (b) `autoApprovers.services` must map the service
to the advertiser's tag, or it stays PENDING admin approval for ever — the *same* "approver follows
advertiser" defect as `autoApprovers.routes` above. (c) Access is granted by naming the service in
`dst`, with its prefix.

[source,json]
----
"autoApprovers": { "services": { "svc:rdp-bioskop": ["tag:console"] } },
"grants": [ { "src": ["autogroup:member"], "dst": ["svc:rdp-bioskop"], "ip": ["5900"] } ]
----

Delivery is *declarative by file*, which is why this fits the repo: there is no
`--advertise-services` flag (the pref is set by `serve` itself), but `tailscale serve set-config
<file>` / `get-config` exist to *"declaratively set configuration for a service host"*:

[source,json]
----
{ "version": "0.0.1",
  "services": { "svc:rdp-bioskop": {
      "endpoints": { "tcp:5900": "tcp://localhost:5900" },
      "advertised": true } } }
----

★ The vocabulary already exists: `catalog.netplan.tailnet.hosts.<host>.serviceNames` today feeds
Headscale `dns.extra_records` CNAMEs (which is why tailscaled is patched at all — see
`overlays/tailscale.nix`). Only the *delivery* moves to the Services API. And the catalog already
settled the split: `vzhost.<host>` is deliberately absent from tailnet DNS, so *`vzhost` stays a
fabric-zone name and the screen alias belongs to tailnet DNS*. A `rdphost` record was written into
the fabric zone and reverted — it duplicated a naming already designed, and was only honest for the
host that never moves.

=== Why Services, even where a direct path already works

Measured 2026-09-27 from `bioskop` toward `nikopol` — both `tag:console`, the mirror of the roaming
case: `nc -vz 100.100.216.24 5900` *succeeds*. Console-to-console screen access over the tailnet is
already permitted, and listening. Nothing is urgently broken.

That reading is location-independent, which is the non-obvious part: the ACL is enforced by the
receiving node's packet filter from its netmap, so sitting on the same home LAN does not flatter the
result. What *does* require going off-site is latency and local-route behaviour — never the right of
access.

So Services are not a fix for a broken path. They are the target shape for reasons reachability
cannot express:

* *One uniform operator view across both bare-metals* — the deciding reason. Today the two screens
  are reached by two different MECHANISMS: `bioskop` is a MagicDNS host name, while
  `vzhost.nikopol` is a fabric-zone record behind a subnet route. As Services they become the same
  kind of name, resolved the same way, wherever the operator stands. The asymmetry being removed is
  in the mechanism, not merely the spelling.
* *No route is installed*, so the LAN-displacement failure of 2026-09-27 cannot recur.
* *The alias follows the service, not the machine*, and several nodes may advertise one.
* `vzhost.nikopol` has no other honest path: it is not a tailnet member, so it needs an advertiser
  holding a REMOTE target — and the fabric address is the only stable one, since its LAN address
  while roaming would designate a stranger's machine in a hotel.

[options="header"]
|===
| Service | Advertiser | Endpoint target
| `svc:rdp-bioskop` | `bioskop` (`tag:console`) | `tcp://localhost:5900`
| `svc:rdp-nikopol` | `nikopol` (`tag:console`) | `tcp://localhost:5900`
| `svc:rdp-vzhost-nikopol` | `nikopol-nixos` (`tag:headless`) | `tcp://vzhost.nikopol:5900` — REMOTE
|===

`vzhost.bioskop` needs no row: it *is* `bioskop`, the same machine at its fabric address, so its
screen is the first row's local target. `vzhost.nikopol` is a distinct corp Mac that never joins the
tailnet. That is precisely the asymmetry the Services layer hides from the operator — and the reason
the third row is the one that depends on remote-target support, hence on this fleet keeping the
standalone macOS/Linux clients rather than the App Store one.

== Troubleshooting

`vzhost.nikopol` / `<inst>.nikopol` doesn't resolve::
Check the split-DNS entry (`nikopol → 172.16.16.1`) in the tailnet DNS config, and that the
`172.16.16.0/20` route is approved. On `nikopol-nixos`, `incus network get fabric-br
dns.domain` should be `nikopol` and dnsmasq should serve the `host-record`.

Resolves but unreachable::
On `nikopol-nixos` check `net.ipv4.ip_forward=1` and that the route is advertised/approved.
On the corp Mac check the two routes via `172.16.24.1` exist (`route -n get 172.16.16.3` /
`route -n get 100.64.0.1`) — no NAT means replies must be routed back explicitly.
