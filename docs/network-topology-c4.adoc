= Baremetal Instance Segments & vz-host Access (C4-Style UML)
:toc: left
:toclevels: 3
:icons: font

== Overview

Each *baremetal host* owns a per-host *instance segment*: an Incus managed network with
its own dnsmasq, a DNS domain `.<host>`, and a subnet route advertised into the tailnet.
This lets any tailnet peer resolve `<instance>.<host>` (split-DNS to that segment's
dnsmasq) and reach the instances — and, for `nikopol`, the *corporate bare-metal Mac*
`vzhost.nikopol` that cannot join the tailnet.

The `nikopol` segment concretely:

* `nikopol-nixos` (the Incus host VM, a tailnet member) runs a *managed Incus network*
  `bare-br` = `172.16.6.0/25` (dnsmasq, `dns.domain = nikopol`) carrying the netflow
  instances (collector `nnh`, …). Its dnsmasq also holds a static `host-record` for
  `vzhost.nikopol → 172.16.6.253`.
* A static `/30` point-to-point link (`172.16.6.252/30`) on the shared Wi-Fi L2 joins
  `vzhost.nikopol` (`.253`) to `nikopol-nixos` (`.254` on `lan-br`); `nikopol-nixos` forwards
  (`ip_forward`) between the `/30` and the `/25`.
* `nikopol-nixos` *advertises* the aggregate `172.16.6.0/24` into the tailnet, and
  *split-DNS* points the `.nikopol` domain at its dnsmasq (`172.16.6.1`). A tailnet peer
  thus resolves `collector.nikopol` / `vzhost.nikopol` and reaches them — the corp Mac
  included — without the Mac ever being a tailnet member.

*No NAT anywhere* — source IPs are preserved end-to-end (the point of the netflow
project). The corp Mac carries a return route to the tailnet range (`100.64.0.0/10 via
.254`), so replies find their way back without masquerading.

[IMPORTANT]
====
*Controller: Tailscale SaaS today; Headscale is a future migration.* The fleet's live
control-plane is *Tailscale SaaS* (the `mammoth-skate` tailnet). Self-hosted Headscale is
scaffolded in the repo but *not deployed*. Consequently the three control-plane operations
— advertising `172.16.6.0/24`, approving the subnet route, and the `.nikopol` split-DNS —
are performed *at runtime in the Tailscale admin/CLI today* (see <<setup>>), and become
*declarative* (Headscale daemon `dns.nameservers.split` + client `--advertise-routes`)
once Headscale is the live controller.
====

The corp-Mac side is *not* a nix-darwin configuration (the corp Mac has no darwin config —
it is JAMF-managed). Its addressing is delivered by the *baremetal-link* package
(`pkgs/baremetal-link.d/`): an idempotent script rendered from the catalog and delivered as
*text* over `ssh`, run as root — no nix runtime on the corp Mac, bash-3.2 compatible (see
<<setup>>).

All addresses are a single source of truth in `catalog/default.nix`
(`netplan.baremetal.nikopol`), consumed by the NixOS Incus host and the corp-Mac package by
derivation — never hard-coded twice.

== Address plan (single source of truth)

`catalog/default.nix` → `netplan.baremetal.<host>`. Consumed by the NixOS Incus host and
the corp-Mac package by derivation. `nikopol` (below) is the *complex* case — an off-tailnet
corp Mac reached over a `/30`; `bioskop` is the *simple* case (see below).

[options="header"]
|===
| Field | Value | Role
| `domain` | `nikopol` | dnsmasq DNS zone + split-DNS domain
| `netCidr` | `172.16.6.0/25` | managed Incus network (dnsmasq) — netflow instances
| `netGateway` | `172.16.6.1` | Incus bridge + dnsmasq + split-DNS target
| `linkCidr` | `172.16.6.252/30` | static P2P link, corp Mac ↔ Incus host
| `hostAddress` | `172.16.6.254` | `nikopol-nixos` link end on `lan-br` (subnet router)
| `vzHostAddress` | `172.16.6.253` | `vzhost.nikopol` en0 alias + dnsmasq `host-record`
| `advertiseCidr` | `172.16.6.0/24` | aggregate advertised into the tailnet
|===

The segment is also declared in `netplan.segments` (derived from `baremetal`) for `nnh`
flow attribution: `nikopol-baremetal-net` (`/25`) + `nikopol-baremetal-link` (`/30`), under
the `172.16.0.0/12` `baremetal` supernet.

=== Second host — bioskop (the same shape, a different reason)

`bioskop` is a *personal* Mac Mini already on the tailnet + home LAN, so unlike nikopol it is
reachable *without* the `/30` — and it declares one anyway, because its *tenants* are not. A
cluster node addressed in this segment cannot reach `192.168.1.129`: `baremetal-nat` masquerades
only public-bound egress (the LAN is in its exclusion set) and the home LAN has no return route to
`172.16.7.0/25`. So the vz-host takes a segment address on the same `/30` shape nikopol uses, and
the Mac *keeps* `192.168.1.129` — the alias is additional, the LAN identity untouched.

[options="header"]
|===
| Field | Value | Role
| `domain` | `bioskop` | dnsmasq DNS zone + split-DNS domain
| `netCidr` | `172.16.7.0/25` | managed Incus network (dnsmasq) — bioskop instances
| `netGateway` | `172.16.7.1` | Incus bridge + dnsmasq + split-DNS target
| `dynamicCidr` | `172.16.7.0/27` | DHCP pool; statics live above it (filled top-down)
| `dhcpRange` | `172.16.7.2-172.16.7.30` | dnsmasq range inside the dynamic `/27` — see the caution below
| `linkCidr` | `172.16.7.252/30` | static P2P link: Mac Mini ↔ Incus host
| `hostAddress` | `172.16.7.254` | `bioskop-nixos` link end on `lan-br` (subnet router)
| `vzHostAddress` | `172.16.7.253` | `vzhost.bioskop` dnsmasq `host-record` (Mac Mini alias)
| `advertiseCidr` | `172.16.7.0/24` | aggregate advertised into the tailnet
|===

[CAUTION]
====
`dhcpRange` is a *correctness* requirement, not tidiness. Without `ipv4.dhcp.ranges` dnsmasq
auto-ranges the whole managed net, so a `bare-br` recreate can hand a *pinned* address to a DHCP
client — the exact failure that stalled the nnh pipeline on nikopol.
====

The split-DNS/advertise pattern applies identically on `bioskop-nixos` (its `.bioskop` zone), so
`ssh vzhost.bioskop` and `<inst>.bioskop` resolve uniformly across both bare-metals. The two
entries now differ only in `lanAttachment` (a physical fact: a roaming laptop must not advertise a
LAN it may leave); `staticHosts` is gone from both, derived from the published segments instead.

The *numbering* is still the legacy one. <<target-carve,The target carve>> below keeps this shape
and re-derives the addresses from rke2lab's `hostId`; both hosts must move in the *same* change,
because bioskop's target `/21` (`172.16.0.0/21`) covers nikopol's current `/25` — a half-migration
would make `172.16.6.x` on-link on bioskop and shadow the tailnet route to nikopol's segment.

[[target-carve]]
=== Target carve — DERIVED from the bare-metal, with the link encoded in the address

[IMPORTANT]
====
*Decided 2026-09-23, not yet applied.* The tables above describe the live catalog. This section describes
the target. The motive is not tidiness: it makes each bare-metal's segment the *sole* address authority
for everything running behind it, so a host on a mobile hotspot (nikopol) is as well-addressed as one on
the home LAN. rke2lab's cluster nodes become the segment's main tenant.

*The addresses stop being allocated and start being derived* — from rke2lab's `hostId` (`bioskop = 0`,
`nikopol = 1`, `test = 2`), the same table that already generates the vmnet plane, the ULA mirror and the
MACs. Consequence for this catalog: `netCidr`/`netGateway`/`linkCidr` become *projections* of rke2lab's
blueprint, like the `kind = "rke2"` reservation rows already are. The full plan, its invariants and the
exhaustive check that guards it live in rke2lab's `docs/architecture/atlas/netplan.adoc`.
====

Today an address does *not* tell you which link it is on: `netCidr` is a `/25` (`.0-.127`) on `bare-br`
while `linkCidr` sits at `.252` — **outside** that `/25`, on `lan-br` — and `.128-.251` is claimed by
nothing. The target encodes the link *in the address*: one bit of the third octet.

....
172.16.<hostId*16>.0/20        advertiseCidr — ONE tailnet route per bare-metal
│                                bioskop .0/20 · nikopol .16/20 · test .32/20
├── slots 0-7  →  ON bare-br   (the Incus L2, gateway .1, dnsmasq zone .<domain>)
│   ├── slot 0   .0/24          HOST INFRA — ndh owns
│   │            ├── .1         bare-br gateway (address is .1/21, covering slots 0-7)
│   │            ├── .2-.30     dynamic DHCP pool (= dynamicCidr .0/27)
│   │            └── .124-.126  nnh pinned collector (nikopol)
│   ├── slots 1-4 .1-.4 .0/24   ONE /24 PER CLUSTER — rke2lab owns (slot = 1 + roleId)
│   │                             mgmt slot 1 · wrkld slot 2 · two spare role slots
│   └── slots 5-7               spare, on bare-br
└── slots 8-15 →  OFF bare-br  (other links)
    └── slot 8   .0/30          static P2P link, on lan-br: Incus host .1 ↔ vz-host .2
....

Read it as: *third-octet offset < 8 ⇒ on `bare-br`; ≥ 8 ⇒ another link.* That is the property the `.252`
island lacked.

Per-host consequences — every value derived, none chosen:

[cols="1,2,2",options="header"]
|===
| Field | nikopol (`hostId 1`) | bioskop (`hostId 0`)

| `advertiseCidr` | `172.16.6.0/24` → `172.16.16.0/20` | `172.16.7.0/24` → `172.16.0.0/20`
| `netCidr` (bare-br) | `172.16.6.0/25` → `172.16.16.0/21` | `172.16.7.0/25` → `172.16.0.0/21`
| `netGateway` | `.6.1` → `172.16.16.1` | `.7.1` → `172.16.0.1`
| `dynamicCidr` | `172.16.6.0/27` → `172.16.16.0/27` | `172.16.7.0/27` → `172.16.0.0/27`
| `dhcpRange` | `.2-.30` → `172.16.16.2-172.16.16.30` | `.7.2-.7.30` → `172.16.0.2-172.16.0.30`
| `linkCidr` | `172.16.6.252/30` → `172.16.24.0/30` | `172.16.7.252/30` → `172.16.8.0/30`
| `hostAddress` | `.6.254` → `172.16.24.1` | `.7.254` → `172.16.8.1`
| `vzHostAddress` | `.6.253` → `172.16.24.2` | `.7.253` → `172.16.8.2`
| nnh's pinned hosts | `.6.125/.126` → `172.16.16.125/.126` — declared by *nnh*, not here | *(none)*
|===

[IMPORTANT]
====
*The left-hand values are the live ones as of 2026-09-23*: bioskop's `/30`, `dynamicCidr` and
`dhcpRange` have LANDED at the legacy numbering, so the two entries already share one shape and only
the *numbers* are still to be derived. What remains is therefore a pure renumbering — and it must move
*both* hosts in the same change, because bioskop's target `netCidr` (`172.16.0.0/21`, covering
`172.16.0.0`–`172.16.7.255`) contains nikopol's current `172.16.6.0/25`. Move bioskop alone and
`172.16.6.x` becomes on-link on `bioskop-nixos`, shadowing the tailnet route to nikopol's segment and
breaking `nnh-inlet.nikopol` from bioskop. The renumbering also has two out-of-repo consequences:
nnh's five pinned literals (its `/30` and the two instance `ipv4Address`es) and a redeploy of each
vz-host's `baremetal-link` daemon.
====

Three notes on why these are not cosmetic:

* *bioskop's `dhcpRange` was a correctness gap, not an omission* (now closed). Without
  `ipv4.dhcp.ranges` dnsmasq auto-ranges the whole managed net, so a `bare-br` recreate can hand a
  *pinned* address to a DHCP client — the exact failure that stalled the nnh pipeline (see the
  `staticHosts` rationale, now in `modules/nixos/baremetal-segment.nix`). rke2lab's addressing is entirely pinned, so this
  had to land *before* the first cluster node attaches.
* *bioskop's vz-host gained a segment address for a functional reason, not for symmetry* (now landed
  at `172.16.7.253`). Once the cluster nodes live in the fabric they cannot reach `192.168.0.0/16`
  (excluded from `baremetal-nat`'s masquerade, and the LAN has no return route), so a `vzhost.bioskop`
  answering only at a LAN address would be unreachable from the tenants now sharing its host. The Mac
  *keeps* `192.168.1.129`.
* *`192.168.1.0/24` is a frozen input.* No device on the home LAN renumbers. The only LAN-side effects
  are deletions — rke2lab stops claiming `192.168.1.128/25`, and the `kind = "rke2"` reservations leave
  the bbox. Both reversible.

== Usage patterns

=== Derive addresses from the catalog — never hard-code

✅ *DO* — read `netplan.baremetal.<host>` in the module/package:

[source,nix]
----
let bm = ndh.context.catalog.netplan.baremetal.nikopol;
in { /* bm.netGateway, bm.hostAddress, bm.vzHostAddress, bm.advertiseCidr, bm.domain */ }
----

❌ *DON'T* — repeat `172.16.6.253`/`.254`/the CIDRs in the corp-Mac package, the NixOS host,
and the split-DNS entry. Three copies drift.

=== Name the vz-host's NIC by SERVICE, from `hardware.vmBridgeService`

The `/30` alias must land on the adapter the vz guest is *bridged* onto — that is what puts the
link's two ends (the Mac's alias, the guest's `lan-br`) on a shared L2. So it is read from the one
declaration Tart's bridge mode already uses:

[source,nix]
----
# hosts/<host>/hardware.nix — the single source
vmBridgeService = "Thunderbolt Ethernet Slot 1";   # bioskop; nikopol is "Wi-Fi"
----

✅ *DO* — declare a macOS *service* name and resolve it to a device at run time
(`networksetup -listnetworkserviceorder`), as `baremetal-link`'s `link-up.sh` does on every
`WatchPaths` burst.

❌ *DON'T* — write an `enX` device name anywhere. Two independent reasons, both measured on
2026-09-23:

* *It is not the same device on two Macs.* `baremetalLinkVars` carried a flat `interface = "en0"`,
  accidentally right for nikopol and silently wrong for bioskop, whose bridged adapter is `en9`.
* *It is not stable on one Mac.* Numbering follows adapter enumeration. On bioskop, `Wi-Fi` is
  **`en1`** and `en0` is the built-in `Ethernet` — so the hardcoded `en0` would not merely have
  missed the target, it would have aliased a different, LAN-facing NIC. Resolving per run also
  makes the link self-heal after a dock is added or removed, with no redeploy.

=== Managed Incus network, never bridged

✅ *DO* — a managed bridge (`bare-br`, Incus dnsmasq bound to it), isolated from the Wi-Fi
L2 → no DHCP collision with the local network.
❌ *DON'T* — bridge/macvlan the instances onto `en0`.

=== Reach `vzhost.nikopol` by DNS name

✅ *DO* — `vzhost.nikopol` is a real DNS name (dnsmasq `host-record`, split-DNS'd into the
tailnet). SSH resolves it via the tailnet resolver; no `HostName`/`ProxyJump`/resolver
needed.
❌ *DON'T* — resolve the corp Mac's live Wi-Fi IP via an ARP lookup or a virtiofs published
file (the retired resolver), or hard-code a `HostName`.

== Setup

=== Declarative (in this repo)

. *Catalog* — `netplan.baremetal.nikopol` (done): domain, CIDRs, `.253`/`.254`,
  `advertiseCidr`.
. *Incus host* (`hosts/nikopol/nixos.nix`) — `bare-br` managed `/25` with
  `dns.domain=nikopol` + `raw.dnsmasq` `host-record=vzhost.nikopol,172.16.6.253`; `.254/30`
  secondary on `lan-br`; `ip_forward`.
. *baremetal-link package* (`pkgs/baremetal-link.d/`) — deployed with
  `nix run .#nikopol-baremetal-link-deploy` (teardown: `… -- --uninstall`). It delivers the
  catalog-rendered install script as *text* over `ssh vzhost.nikopol` (first-run bootstrap
  fallback `nikopol.local`, since `.253` isn't set yet) and runs it as root. The script
  installs the `io.seedmatic.baremetal-link` *WatchPaths* LaunchDaemon that (re-)applies the
  `en0` alias `172.16.6.253/30` + routes `172.16.6.0/25 via .254` and `100.64.0.0/10 via
  .254` at load and on every Wi-Fi re-association. No nix runtime on the corp Mac; every
  address derives from `netplan.baremetal.nikopol` — never hand-typed.

=== Runtime, on the Tailscale SaaS controller (today)

. On `nikopol-nixos`: `tailscale up --advertise-routes=172.16.6.0/24` (+ `--accept-routes`
  on consumers).
. In the Tailscale admin console: *approve* the `172.16.6.0/24` subnet route.
. In the Tailscale admin console → DNS: add a *split-DNS* nameserver for domain `nikopol`
  → `172.16.6.1`.

NOTE: when Headscale becomes the live controller, steps 1–3 move into the Headscale daemon
`dns.nameservers.split` + the client `--advertise-routes` (declarative), driven from the
same catalog values.

== Troubleshooting

`vzhost.nikopol` / `<inst>.nikopol` doesn't resolve::
Check the split-DNS entry (`nikopol → 172.16.6.1`) in the tailnet DNS config, and that the
`172.16.6.0/24` route is approved. On `nikopol-nixos`, `incus network get bare-br
dns.domain` should be `nikopol` and dnsmasq should serve the `host-record`.

Resolves but unreachable::
On `nikopol-nixos` check `net.ipv4.ip_forward=1` and that the route is advertised/approved.
On the corp Mac check the two routes via `.254` exist (`route -n get 172.16.6.3` /
`route -n get 100.64.0.1`) — no NAT means replies must be routed back explicitly.
