== Key Concepts

=== Tailscale
Identity-based VPN using WireGuard, provides SSH with automatic key management, subnet routing via gateways.

=== Headscale
Self-hosted Tailscale control server for internal LAN, compatible with Tailscale clients, lower latency on LAN.

=== Gateways
Advertise subnet routes to make internal networks accessible via Tailscale/Headscale, deployed as Incus instances in Lima VMs.

=== Hybrid Approach
Use Tailscale for external access and mobile devices, use Headscale for fast local SSH, both provide identity-based authentication.

== Network Architecture Summary

[source]
----

    ↓

    ↓
Lima VMs (NixOS)
    ↓
Tailscale Gateways (Incus)
    ↓
RKE Clusters (Incus instances)

Internal LAN (Headscale - optional)
    ↓
All LAN hosts connected
    ↓
Fast local SSH
----

== Common Tasks

=== Deploy Tailscale Gateway

[source,bash]
----
# In Lima VM
limactl shell default
sudo deploy-tailscale-gateway
----

See: link:network-setup.adoc#step-1-tailscale-gateways-in-lima-vms[Tailscale Gateway Setup]

=== Setup Headscale Server

[source,nix]
----
services.headscale-custom = {
  enable = true;
  serverUrl = "http://headscale.local:8080";
  baseDomain = "home.arpa";
};
----

See: link:network-setup.adoc#step-3-optional-headscale-for-internal-lan[Headscale Setup]

NOTE: The reserved `.home.arpa` suffix avoids conflicts with Bonjour/mDNS, so adopt hostnames like `bioskop.home.arpa` for LAN-only MagicDNS.

=== Connect to Network

[source,bash]
----
# Tailscale
sudo tailscale up --ssh

# Headscale
hs-connect
----

See: link:network-setup.adoc#ssh-access[SSH Access Methods]

[source,bash]

# Via Headscale

=== Refresh linux-builder After SSH Key Changes

When you rotate or edit the builder SSH keys, remove the cached VM state so the updated keys are baked into the rebuilt image.

[source,bash]
----
# @codebase
sudo rm -rf /var/cache/linux-builder
darwin-rebuild switch --flake .
----

Then verify the builder picks up the new keys (e.g., check the updated `builder_keys.pub` inside the VM) before retrying remote builds.

=== Bootstrap Recap (linux-builder)

Minimal sequence to bring up the builder VM from a host checkout:

[source,bash]
----
# @codebase (from hosts/<host>)
nix run nixpkgs#darwin.linux-builder -L -v -v

# Copy generated builder keys into place for the daemon
sudo cp keys/builder_ed25519 /etc/nix/builder_ed25519
sudo cp keys/builder_ed25519.pub /etc/nix/builder_ed25519.pub
sudo chmod 600 /etc/nix/builder_ed25519

# Build and activate the host configuration
nix build .#darwinConfiguration.system -L -v -v -o darwin 2>&1 | tee /tmp/log
sudo rm -fr /var/lib/linux-builder
sudo pkill qemu || true
sudo ./darwin/activate
----

This sequence ensures fresh keys are installed, the cached builder VM is cleared, and activation restarts the builder VM with the updated config.

== Binary Cache Workflow (bioskop builds, others pull)

* Build host (bioskop)
** Generate a signing key (once):
[source,bash]
----
# @codebase
nix-store --generate-binary-cache-key bioskop-cache-1 /etc/nix/cache-priv.key /etc/nix/cache-pub.key
----
** Run nix-serve and expose the port (e.g., 8080):
[source,bash]
----
# @codebase
nix-serve -p 8080 -k /etc/nix/cache-priv.key
----

* Clients (alcide, nikopol)
** Configure substituters and trusted keys (nix.conf or module settings):
[source,conf]
----
# @codebase
substituters = https://cache.nixos.org http://bioskop:8080
trusted-public-keys = cache.nixos.org-1:<nixos-key> bioskop-cache-1:<bioskop-pub-key>
----
** Pull and switch directly from GitHub:
[source,bash]
----
# @codebase
darwin-rebuild switch --flake github:nxmatic/nix-darwin-home#alcide
----

* Publish closures (run on bioskop before clients pull)
[source,bash]
----
# @codebase
nix build .#hosts/alcide .#hosts/nikopol
----
* Keep built paths alive if needed
[source,bash]
----
# @codebase
ln -s /nix/store/<path> /nix/var/nix/gcroots/bioskop-cache-keep
----

== Repository Structure

=== Git Subtree Integration

The `modules/nixos/rke2lab/` directory is managed as a **git subtree**, integrating the standalone `rke2lab` repository for RKE2 deployment.

==== Working with the Subtree

**Helper script:**
[source,bash]
----
# Pull updates from upstream
./.git-subtree-sync.sh pull

# Push changes back to upstream
./.git-subtree-sync.sh push

# Check subtree status
./.git-subtree-sync.sh status
----

**Development workflow:**

1. **RKE2-specific development** → Work in standalone `../rke2lab/` repo
+
[source,bash]
----
cd ../rke2lab
# Make changes, test, commit
git add .
git commit -m "Update RKE2 deployment"
git push
----

2. **Sync to nix-darwin-home**
+
[source,bash]
----
cd ../nix-darwin-home
./.git-subtree-sync.sh pull
----

3. **Integration changes** → Work in `modules/nixos/rke2lab`
+
[source,bash]
----
cd modules/nixos/rke2lab
# Modify for integration needs
# Commit to nix-darwin-home
git commit -m "Integration update"
----

4. **Optional: Push improvements back**
+
[source,bash]
----
./.git-subtree-sync.sh push
----

**Manual commands:**
[source,bash]
----
# Pull from upstream
git subtree pull --prefix=modules/nixos/rke2lab \
  ../rke2lab main --squash

# Push to upstream
git subtree push --prefix=modules/nixos/rke2lab \
  ../rke2lab main
----

NOTE: Both repositories remain active. The standalone repo is ideal for focused RKE2 development, while the subtree provides integration with NixOS modules.

=== Secrets & Credentials

* All automation secrets now reside in the SOPS-filtered YAML at `modules/nixos/rke2lab/.secrets` (fields for `tailscale.*`, `github.*`, and `docker.configJson` — store the base64-encoded Docker config JSON here). Edit the file in place with `sops` so encrypted data never leaves disk unprotected.
* Run `modules/nixos/rke2lab/bin/migrate-legacy-secrets.sh <legacy-secret-dir>` to import any remaining flat files into the YAML (the helper boots a template if missing, copies current plaintext values, and leaves the original files untouched so you can compare before cleaning up).
* `rke2-cluster-repo-sync` and `rke2-kpt-package-sync` bootstrap `gh auth login --with-token`/`gh auth setup-git`, so git now leans on `gh auth git-credential` for HTTPS operations (falling back to `GIT_ASKPASS` only if the CLI is unavailable).
* Porch manifests consume the GitHub PAT (`cluster-github-token`) and image pull secret (`porch-docker-config-json`) via `rke2-kpt-deploy`, so the Kubernetes Secrets materialize from runtime env vars instead of being tracked in git.
* When rotating credentials, change the `.secrets` YAML, re-run `sops --in-place`, and restart the Incus nodes (or rerun the relevant systemd units) to propagate the refreshed values end-to-end.
