== Overview

This document covers the complete network infrastructure setup using Tailscale and Headscale for secure SSH access across subnets and external locations.


=== Recent Change (2025-10-12): Dual-NIC Incus Cluster Refactor (Bridged → Macvlan/VLAN)

The Incus RKE2 cluster networking inside the Lima NixOS guest was refactored from using Incus-managed bridges (with dnsmasq/DHCP) to direct macvlan (vlan) attachments:

* `lan0` – Now a macvlan interface attached directly to the host's vmlan0 (physical LAN). No Incus bridge is created.
* `wan0` – Now a macvlan interface attached directly to the host's vmwan0 (physical WAN/NAT). No Incus bridge is created.

**Key implications:**

* No Incus-managed bridge or DHCP/DNS (dnsmasq) is present for lan0/wan0. The instance will only get an IP if a DHCP server is present on the parent network, or if static IPs are set.
* The macvlan setup provides L2 isolation per instance, but the instance cannot communicate with the host via the parent interface (macvlan limitation).
* This avoids Linux bridge errors ("Only unconfigured network interfaces can be bridged") and bridge name length issues.
* Deterministic, per-node interface naming (lan0/wan0) is preserved.

**Migration steps:**

1. Clean old instances (Incus cannot hot‑rename NICs):
  ```
  make -C modules/nixos/rke2lab clean-all
  ```
2. Re‑generate preseed & recreate master:
  ```
  make -C modules/nixos/rke2lab preseed@incus NAME=master start
  ```
3. Launch peers if desired:
  ```
  make -C modules/nixos/rke2lab NAME=peer1 start
  ```
4. Verify inside container:
  ```
  incus exec master -- ip -brief addr show lan0 wan0
  incus exec master -- grep vip_interface /var/lib/rancher/rke2/server/manifests/kube-vip.yaml.tmpl
  ```
5. Confirm Cilium announcements (after cluster up):
  ```
  kubectl -n kube-system logs -l k8s-app=cilium | grep -i wan0 || true
  ```

**DHCP/DNS Note:**

* If you need DHCP/DNS for lan0/wan0, you must run a DHCP server (e.g., dnsmasq) on the Lima VM for vmlan0/vmwan0, or ensure an upstream DHCP server is present. Otherwise, configure static IPs in the instance.

Rollback: revert device names and macvlan config in the Incus preseed & cloud-config YAML, then re‑create instances (not recommended unless legacy tooling mandates `eth0`).

Planned Enhancements:

* Inject `CONTAINER_LAN_IFACE` / `CONTAINER_VIP_IFACE` env variables for further abstraction.
* Optional policy routing table to pin internal service traffic to `lan0` while leaving VIP + egress on `wan0`.

All subsequent references in this document to the control plane VIP / egress should be assumed to operate on `wan0` unless explicitly stated otherwise.

=== Components

Tailscale (External)::
Identity-based SSH with automatic key management, subnet routing via gateways in Lima VMs, mobile device support

Headscale (Internal, Optional)::
Self-hosted Tailscale alternative for LAN, lower latency, privacy-focused

=== Why No Teleport?

Both Tailscale and Headscale provide built-in SSH with:

* ✅ Identity-based authentication
* ✅ Automatic SSH key management
* ✅ ACL-based access control
* ✅ Encrypted WireGuard tunnels
* ✅ MagicDNS hostname resolution

This eliminates the need for a separate authentication layer like Teleport.

== Installation and Configuration

=== Step 1: Tailscale Gateways in Lima VMs

==== Configuration

Edit `/etc/nixos/configuration.nix` in each Lima VM:

.alcide's Lima VM
[source,nix]
----
{ config, pkgs, lib, ... }:
{
  imports = [
    ./hardware-configuration.nix
  ];

  # Enable Incus
  virtualisation.incus = {
    enable = true;
    ui.enable = true;
  };

  # Tailscale gateway configuration
  services.incus-tailscale-gateway = {
    enable = true;
    instanceName = "tailscale-gateway";
    authKeyFile = "/run/secrets/tailscale-authkey";
    hostname = "alcide-gateway";
    
    # Advertise alcide's subnets
    routes = [
      "192.168.5.0/24"    # Lima shared network
      "192.168.106.0/24"  # Incus bridge (RKE cluster)
    ];
    
    tags = [ "gateway" "lima" "alcide" ];
    exitNode = false;
  };

  # Enable IP forwarding
  boot.kernel.sysctl = {
    "net.ipv4.ip_forward" = 1;
    "net.ipv6.conf.all.forwarding" = 1;
  };

  networking = {
    hostName = "lima-alcide";
    firewall = {
      enable = true;
      trustedInterfaces = [ "incusbr0" ];
    };
  };

  environment.systemPackages = with pkgs; [
    incus
    tailscale
    kubectl
    k9s
  ];

  system.stateVersion = "24.05";
}
----

.bioskop's Lima VM
[source,nix]
----
{ config, pkgs, lib, ... }:
{
  # Similar configuration, but different subnets
  services.incus-tailscale-gateway = {
    enable = true;
    hostname = "bioskop-gateway";
    routes = [
      "192.168.5.0/24"
      "192.168.107.0/24"  # Different Incus bridge

    tags = [ "gateway" "lima" "bioskop" ];

  # ... rest of config similar to alcide
}
----

==== Deployment

[source,bash]
----
# On alcide
limactl shell default

# Store Tailscale auth key
echo "tskey-auth-xxxxx-alcide" | sudo tee /run/secrets/tailscale-authkey
sudo chmod 600 /run/secrets/tailscale-authkey

# Rebuild NixOS
sudo nixos-rebuild switch

# Deploy gateway
sudo deploy-tailscale-gateway

# Check status
sudo tailscale-gateway-status
----

Repeat for bioskop with its auth key.

{
  "tagOwners": {

    "tag:darwin": ["you@example.com"],
    "tag:nixos": ["you@example.com"],
    "tag:lima": ["you@example.com"]
  },
  
  "acls": [
    {
      "action": "accept",
      "comment": "Allow all access between your devices",
      "src": ["you@example.com"],
      "dst": ["*:*"]
    }
  ],
  
  "ssh": [
    {
      "action": "accept",
      "comment": "SSH access to all devices",
      "src": ["you@example.com"],
      "dst": ["tag:darwin", "tag:nixos", "tag:lima"],
      "users": ["autogroup:user", "root"]
    }
  ]
}
----

=== Step 3: Optional Headscale for Internal LAN

==== Deploy Headscale Server

Choose an always-on host (NAS, server, or dedicated host):

[source,nix]
----
{ config, pkgs, ... }:
{
  imports = [
    ../../modules/nixos/headscale-server.nix
  ];

  services.headscale-custom = {
    enable = true;
    serverUrl = "http://192.168.1.10:8080";
    baseDomain = "mammoth-skate.home.arpa";
  };

  networking.firewall.allowedTCPPorts = [ 8080 ];
}

NOTE: `home.arpa` is reserved for private home networks (RFC 8375), so using a `*.home.arpa` suffix keeps MagicDNS separate from macOS `.local` mDNS traffic.

==== Initialize Headscale

[source,bash]
----
# Create user/namespace
sudo headscale users create default

# Generate auth keys
sudo headscale-preauth default --reusable > /tmp/gateway-key.txt
sudo headscale-preauth default > /tmp/client-key.txt
----

== Reference

=== Deterministic CIDR Derivation (ipcalc removal – 2025-10-18)

Previously the dynamic allocation of hierarchical cluster networks relied on `ipcalc --split` JSON output. This dependency has been removed to simplify bootstrap environments (especially remote Incus execution inside constrained Lima images) and to make the allocation logic fully transparent. All splits are now derived arithmetically from the fixed supernet `10.80.0.0/18`.

Allocation model (@codebase):

* Host Supernet: `10.80.0.0/18` (capacity: 16,384 addresses)
* Cluster Networks: 8 × /21 blocks. Index `i` maps to `10.80.(i*8).0/21` for `i=0..7`.
* Node Networks (per selected cluster): 4 × /23 blocks within the /21. Index `n` maps to `third_octet + n*2`. Example: cluster index 1 ⇒ base third octet 8 ⇒ node0 `10.80.8.0/23`, node1 `10.80.10.0/23`, node2 `10.80.12.0/23`, node3 `10.80.14.0/23`.
* VIP Network: Last /24 of the /21 (`third_octet + 7`). Example: cluster 1 ⇒ VIP `10.80.15.0/24`, gateway `10.80.15.1`.
* LoadBalancer Network: Second /26 slice of node0's /23 ⇒ `10.80.<cluster_third>.64/26` with gateway convention kept at `.129` (historical choice pending review).
* Node Broadcast (for /23): Spans its two constituent /24 blocks: `10.80.(third_octet+1).255`.

Rationale:

* Eliminates an external binary (smaller closure, fewer remote requirements).
* Improves determinism (no parsing of tool JSON, pure arithmetic).
* Speeds up `make summary@network` and `rebuild@rke2-networks` by avoiding 5+ subprocess calls.
* Enhances diff readability – changes to the allocation logic are plain shell arithmetic.

Validation Targets (@codebase):

* `load@network` loads generated exports from `.run.d/network/_assign.mk`.
* `summary@network` prints the currently selected cluster/node CIDRs using the new derivation.
* (Optional) Future `test@network-arith` will assert expected counts (8 clusters, 4 nodes) and CIDR patterns.

Impact:

* Only `network/rules.mk` changed for derivation logic; Incus lifecycle (`incus/rules.mk`) already free of `ipcalc` since prior cleanup.
* External rebuild sequences and higher-level targets remain unchanged.

If a need arises for dynamic supernet sizing or non-linear allocation, a lightweight pure‑Nix or shell function can be introduced without re‑adding `ipcalc`.

===== Network Configuration Notes

* **Hostname Strategy**: Cluster nodes register on LAN with cluster-prefixed hostnames (e.g., `bioskop-master-control-node.lan`, `alcide-master-control-node.lan`) to prevent DNS conflicts when both clusters are active on the same home network.

* **System Hostnames**: Internal system hostnames and RKE2 node names remain unprefixed (e.g., `master-control-node`) for consistency across clusters.

* **DHCP Configuration**: Cluster-prefixed hostnames are sent to DHCP via systemd-networkd drop-in on the `lan0` interface:
+
[source,ini]
----
# /etc/systemd/network/10-netplan-lan0.network.d/10-hostname.conf
[DHCP]
SendHostname=yes
Hostname=${RKE2_CLUSTER_NAME}-${RKE2_NODENAME}-control-node
----

* **Static Reservations**: Darwin hosts and Lima VMs should have static DHCP reservations configured in the Bbox router to ensure stable IPs across reboots.

* **Block Capacity**: Each /27 block provides 30 usable IPs, sufficient for:
  - Darwin host (1 IP)
  - Lima VM (1 IP)
  - Up to 4 RKE2 control nodes (4 IPs)
  - Additional infrastructure (24 IPs remaining)

sudo headscale users create <name>           # Create user
sudo headscale-preauth <user> --reusable     # Generate auth key
sudo headscale nodes list                    # List nodes
sudo headscale routes list                   # List routes
sudo headscale routes enable <route> <node>  # Enable route
sudo headscale policy check                  # Validate policy
----

== Security Considerations

=== Authentication

Both Tailscale and Headscale provide:

* Identity-based authentication (no shared secrets)
* Automatic key rotation
* Per-device authentication
* SSO integration (Tailscale)

=== Access Control

* Use ACLs to restrict access
* Apply principle of least privilege
* Use tags for grouping
* Regular ACL audits

=== Network Security

* All traffic encrypted (WireGuard)
* No exposed ports required
* Firewall remains active
* Subnet isolation via ACLs

=== Best Practices

1. Use tags for device categorization
2. Implement granular ACLs
3. Regularly rotate auth keys
4. Monitor access logs
5. Keep software updated
6. Use MFA for Tailscale account
7. Backup Headscale database

== Conclusion

This setup provides:

✅ Secure SSH access from anywhere (Tailscale)::
Identity-based authentication, no manual key management

✅ Fast local SSH (Headscale)::
Lower latency when on same LAN, self-hosted

✅ Subnet routing (Gateways)::
Access to RKE clusters and Lima VM networks

✅ Mobile access (Tailscale)::
Official app for iOS/Android

✅ Simplified architecture::
No need for separate authentication layer (Teleport)

✅ Highly secure::
WireGuard encryption, ACL-based access control

The hybrid approach using both Tailscale and Headscale provides the best balance of external accessibility, local performance, and security.
