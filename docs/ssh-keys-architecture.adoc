[NOTE]
====
This document describes the current SSH key management system with split runtime outputs:

* per-user private material: `/run/secrets-per-user/<user>/ssh-keys/`
* per-user public/trust material: `/run/secrets-per-user/<user>/ssh-system-keys/`

`/run/secrets.d` is an internal sops-nix generation path and is not a consumer-facing API.
====

== Executive Summary

The SSH key management system automates deployment of cryptographic keys and certificates from a SOPS-encrypted source (`keys.yaml`) to runtime directories under `/run/secrets-per-user/<user>/` at activation time. The pipeline ensures:

* **Fresh activation-time extraction** of key material from profile-scoped YAML
* **Split ownership model** (private vs public/trust outputs)
* **Minimal manual intervention** (integrated into `home-manager switch`)
* **Ephemeral runtime files** (not stored in git)
* **Runtime compatibility** with SSH agent auto-loading

|===
|Component|Purpose

|SOPS Decryption
|Decrypts `nxmatic-ssh-keys.yaml` to plaintext profile YAML at activation time (mode 0400, read-only)

|Main Nix module that wires up all components and activation scripts

|Generate Profile YAML (Stage 1)
|Selects current profile/host keys from SOPS source and writes generated `keys.yaml`

|Parses generated YAML and writes private keys to per-user dir and public/trust files to system dir

|`/run/secrets-per-user/<user>/ssh-keys/` (private) and `/run/secrets-per-user/<user>/ssh-system-keys/` (public/trust)

== C3: Component Architecture (Generate → Extract → Authorize)

=== Stage 1: Generate Profile YAML

[cols="2,3"]
|===
h|Aspect|Details

|Input
|SOPS decrypted source YAML (`/run/secrets/nix-darwin-home/nxmatic-ssh-keys.yaml`)

|Process
|* Parse source YAML with yq
* Select active profile + host
* Write generated profile YAML to `/run/secrets-per-user/<user>/ssh-keys/keys.yaml`

|Output
|Generated profile YAML for extraction

|Script
|`ssh-generate-keys-yaml.sh`
|===

=== Stage 2: Key Extraction and Materialization

[cols="2,3"]
|===
h|Aspect|Details

|Input
|Generated profile YAML + output directories

|Process
|For each key entry:
* Write private material to `/run/secrets-per-user/<user>/ssh-keys/`
* Write public/cert/CA material to `/run/secrets-per-user/<user>/ssh-system-keys/`
* Normalize file modes (private `0600`, public `0644`)

|Output
|Runtime key material in split per-user directories

|Script
|`ssh-extract-keys.sh`
|===

=== Stage 3: Authorization

[cols="2,3"]
|===
h|Aspect|Details

|Input
|Extracted runtime key material

|Process
|* Ensure `~/.ssh/authorized_keys` exists and is mutable
* Enforce strict permissions (`0600`)

|Output
|Mutable `~/.ssh/authorized_keys`

|`ensure-authorized-keys.sh`
|===

== Key Design Decisions

=== Decision 1: Ephemeral Certificates

**Decision:** Certificates are regenerated at each activation, never stored in git

**Rationale:**
* Ensures fresh serial numbers (security best practice)
* Avoids tracking generated artifacts
* Simplifies backup/restore (no stale cert confusion)

**Trade-off:** Slightly slower activation (cert generation ~100ms per key)

=== Decision 2: Embedded Authorities

**Decision:** Authority CA keys are embedded in the profile YAML (under `<key>.authorities.<ca-name>`)

**Rationale:**
* Single source of truth (keys + CAs in one YAML file)
* No separate CA key management
* Decryption happens once, CAs available inline

**Trade-off:** Larger YAML payload (CA keys only ~4KB each, not significant)

=== Decision 3: Activation-Time Generation

**Decision:** Certificates generated during `home-manager switch`, not at build time

**Rationale:**
* Timestamps/serial numbers reflect actual deployment time
* Fresh CA signatures always current
* No pre-built artifacts to manage or cache

**Trade-off:** Can't verify certs without running full home-manager activation

=== Decision 4: Stable Symlinks

**Decision:** `<key>-cert.pub` → `<key>-<authority>-user-cert.pub`

**Rationale:**
* SSH agent auto-loads sidecar `<key>-cert.pub` when loading `<key>` private key
* One symlink per key instead of hard-coding authority-specific name
* Easy to rotate CAs (just update symlink target)

**Trade-off:** Adds symlink maintenance step in cert regeneration

== Common Operations & Troubleshooting

=== Adding a New Key

. *Edit `nxmatic-ssh-keys.yaml` (encrypted):*
+
[source,bash]
----
sops modules/home-manager/ssh.d/keys.yaml
----

. *Add key entry under appropriate profile:*
+
[source,yaml]
----
profiles:
  committed:
    my-new-key:
      type: ssh-ed25519
      usage: [ssh-user]
      comment: my-new-key@bioskop
      public: AAAAC3NzaC1lZDI1NTE5...
      private: |
        -----BEGIN OPENSSH PRIVATE KEY-----
        ...
        -----END OPENSSH PRIVATE KEY-----
----

. *Activate:*
+
[source,bash]
----
home-manager switch
----

. *Verify:*
+
[source,bash]
----
ls -la /run/secrets-per-user/$USER/ssh-keys/my-new-key*
ssh-add -l | grep my-new-key
----

=== Adding Authority Signing

. *Add authority CA keys under target key:*
+
[source,yaml]
----
profiles:
  committed:
    rke2-cluster:
      type: ssh-ed25519
      public: ...
      private: ...
      authorities:
        mammoth-skate:  # Add this authority
          type: ssh-ed25519
          private: |  # CA private key
            -----BEGIN OPENSSH PRIVATE KEY-----
            ...
            -----END OPENSSH PRIVATE KEY-----
          public: ...   # CA public key
----

. *Activate to regenerate certs:*
+
[source,bash]
----
home-manager switch
----

. *Verify cert generated:*
+
[source,bash]
----
ls -la /run/secrets-per-user/$USER/ssh-system-keys/rke2-cluster-mammoth-skate-user-cert.pub
ssh-keygen -L -f /run/secrets-per-user/$USER/ssh-system-keys/rke2-cluster-cert.pub
----

=== Debugging Pipeline

**Check extraction (Stage 1):**
[source,bash]
----
# Manually test extract-keys.sh
yq eval '.profiles.committed' /run/secrets/.../keys.yaml > /tmp/profile.yml
bash modules/home-manager/ssh-key.d/ssh-extract-keys.sh /tmp/profile.yml /tmp/extracted-user /tmp/extracted-system
ls -la /tmp/extracted-user /tmp/extracted-system
----

**Check generated profile YAML (Stage 1):**
[source,bash]
----
# Test generate-keys-yaml.sh
bash modules/home-manager/ssh-key.d/ssh-generate-keys-yaml.sh committed bioskop /run/secrets/nix-darwin-home/nxmatic-ssh-keys.yaml /tmp/keys.yaml nikopol,bioskop,nikopol
ls -la /tmp/keys.yaml
----

== Architecture Evolution Notes

=== Current Status (v1.0)

* ✓ Keys + certificates deployed to runtime
* ✓ Certificates regenerated on every activation
* ✓ Symlink-based cert auto-loading
* ✓ Integrated with home-manager lifecycle

=== Potential Future Enhancements

. **Certificate Renewal Strategy**
   * Monitor cert expiry
   * Pre-regenerate certs before expiry
   * Alert on expired certs in use

. **Multi-Profile Key Rotation**
   * Support dynamic profile switching
   * Isolated key sets per profile
   * Key transition workflows

. **Hardware Token Integration**
   * Support FIDO2/YubiKey keys
   * Hybrid key + token auth

. **Distributed CA Management**
   * External CA authority integration
   * Federated identity scenarios
   * Cross-host cert coordination

== Questions for Future Contributors

When modifying this system, consider:

. **Where does the new logic fit?** (Extract / Regenerate / Deploy / Authorize phases)
. **Does it touch private key material?** (If yes, ensure temp files use `chmod 400`)
. **Should it regenerate on every activation?** (Or only on config change?)
. **How does it affect rsync --delete logic?** (Be careful not to delete needed files)
. **Is there a simpler way?** (Avoid complexity for edge cases)
