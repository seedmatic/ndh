= SSH Keys — the Keys That Remain
:toc: left
:toclevels: 3
:icons: font

**Status:** 📐 target — decided 2026-10-06 +
**Scope:** which keys exist once access is granted by the control plane, who owns each, how they travel

[NOTE]
====
Access to the fabric is granted by the control plane — see
link:fabric-control-plane-spec.adoc[Fabric Control Plane]. This spec covers only what is left as
key material. The migration from today's inventory (an SSH authority, certificates signed at every
activation, the whole keyring copied into rke2lab) is in the rke2lab atlas,
`docs/architecture/atlas/fabric-control-plane.adoc`.
====

== Overview

Three rules carry the whole model:

**No SSH key reaches the fabric.** The out-of-band paths need none, the managed paths are grants, and
the emergency path is a screen (link:fabric-control-plane-spec.adoc#_the_emergency_path_is_a_screen_not_a_key[Fabric
Control Plane § The emergency path is a screen]). What follows is the material that remains for
everything else — the bridge, GitHub, the cluster PKI — and three rules govern it:

. **A key is generated by the machine that uses it**, and its private half never leaves that
  machine. Only the public half is declared in `keys.yaml`.
. **A key is stable.** It is rotated by an operator gesture, in two phases, and the retired
  generation is revoked in the same change — never at activation.
. **A key reaches only the role that needs it.** Secret material travels as per-role
  *projections* of `keys.yaml`, each encrypted for its own recipients.

There is no SSH authority and no certificate: a key is authorised where it is used, by a
restricted `authorized_keys` line.

== The inventory

[cols="2,1,2,2",options="header"]
|===
| Key | Kind | Owner — generates it, holds the private | Authorised at

| bridge, one per gateway
| WireGuard, static
| bioskop-nixos, nikopol-nixos
| the other gateway's WireGuard peer list

| service keys — only if Tailscale SSH cannot carry the flow
| SSH, static
| the machine running the service
| the target, `restrict` + `command=` / `internal-sftp`

| `github-signing`, `github-authentication`
| SSH, static
| the seats
| GitHub

| `rke2-cluster`
| SSH key used as an age identity
| shared — the seats and the cluster
| Flux's sops identity, the cellar cipher

| control-plane TLS leaf, one per segment
| ECDSA P-256, static
| the headscale container — generated there, the private never leaves
| its own `tls_cert_path` / `tls_key_path`; signed on a seat from the root below

| `mammoth-skate-tls`
| TLS root
| the seats
| the **shared** authority: the cluster PKI *and* the control-plane leaves — not an access key
|===

The control-plane leaf is the one certificate this model keeps, and the reasoning is in
link:fabric-control-plane-spec.adoc#control-tls[Fabric Control Plane § TLS on the control URL]: it
authenticates the server at first contact, headscale implements neither `tailscale cert` nor an ACME
path usable on a private name, and the root is already in every member's trust store.

[IMPORTANT]
====
The service keys exist only for a flow that is *measured* unable to ride Tailscale SSH — the open
cases are sftp for `sshfs` and `nix-daemon --stdio` for the `ssh-ng` builders. Each one that
qualifies gets its own key, its own owner, and a line that permits that flow only.
====

configuration at evaluation. Privates do not travel, except the genuinely shared material
(`rke2-cluster`, the TLS root), which moves only inside a projection.

[cols="1,3",options="header"]
|===
| Field | Meaning

| `owner`
| the role that generates and keeps the private half

| `acceptedBy`
| the roles whose machines authorise the public half

| `grants`
| what the authorisation permits — login, forced command, source address

| `slots`
| dated generations; one when settled, two during a rotation — see
link:ssh-keys-renewal-spec.adoc[the renewal model]

| `revoked`
| retired generations, refused by every verifier; an entry is written in the same change that
removes its slot
|===

== Projections

A projection is the subset of `keys.yaml` one role needs, encrypted **whole** for that role's own
recipients. Two properties follow:

* **encryption is a property of the file**, not of a marker comment matched by a regex inside a
  path-matched rule — so a misrouted `creation_rule` cannot yield a readable secret;
* **a compromised machine yields only its role's projection.** The blast radius of an intrusion is
  computable: the keys its projection holds, times the machines that accept them.

[mermaid]
....

The guest's age identity reaches it through the vz host's **virtiofs share** — the delivery that
already needs no ssh. What the share carries is that guest's own identity, a recipient of that
guest's projection only, never an identity that opens every file.

rke2lab receives its projection as the `.ndh-ssh.d/` subtree: the four items it reads
(`mammoth-skate-tls` root, `rke2-cluster`, `github-signing`, the tailnet domain), never the whole
registry.

== The pipeline

[mermaid]
....
sequenceDiagram
  autonumber
  participant S as virtiofs share
  participant D as sops decrypt
  participant X as extract
  participant H as sshd and WireGuard

  S->>D: this machine's age identity
  D->>D: open this role's projection
  D->>X: the material this role holds
  X->>H: privates of keys this machine owns
  Note over H: authorised publics and revocations come from the evaluated configuration
....

Nothing in this pipeline generates or signs: generation is an operator gesture on the owning
machine, and there is nothing to sign.

== Usage patterns

=== ✅ Generate a key on its owner, declare the public

[source,bash]
----
ssh-keygen -t ed25519 -N "" -f /var/lib/ndh/ssh-keys/{key}   # on the owning machine
# then add the public under keys.{key}.slots.{YY-MM-DD}.public, and commit
----

=== ✅ Authorise for one flow only

[source]
----
restrict,from="172.16.24.2",command="networkctl reconfigure lan-br" ssh-ed25519 AAAA…
----

=== ❌ An empty slot that "activation will fill"

A key generated at activation is never recorded, so it can be neither revoked nor evicted. A
slot holds a public, or the key does not exist.

=== ❌ One key for two roles

A key that both authenticates an operator and identifies a host makes one leak a total one.

=== ❌ An identity that opens every file, shared into a guest

The virtiofs share carries the guest's own identity — never the operator's.

== Troubleshooting

[cols="2,2,2",options="header"]
|===
| Symptom | Cause | Fix

| `evaluation refuses: revoked but still carried by a slot`
| a generation was revoked before its slot was removed
| remove the slot in the same change

| A retired generation still authenticates
| its slot was removed without a `revoked` entry
| add the entry; phase 2 always writes both

| A guest cannot decrypt its projection
| its own age identity is not a recipient yet
| re-encrypt the projection for the guest's public, from a seat
|===
