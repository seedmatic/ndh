== Overview

This session closed the bringup-image unification arc that began in
the 2026-05-16 session note and the design proposal in
link:../bringup-image-unification.adoc[bringup-image-unification.adoc].
The single shared `nerd-nixos-bringup-zfs-systemd-disk` flake output
is now empirically verified end-to-end on bioskop, the per-host
backwards-compat aliases are removed, and the bioskop-nixos NixOS
guest is fully on the tailnet.

A handful of related fixes landed alongside the unification work:
ZFS extra-pool hostid drift on the bringup→full handoff, headscale
preauth-key rotation for three (`nixos`, `incus`, `rke2`) of the four
kinds, and the retirement of the Darwin-side mDNS publisher that
became redundant once the headscale `dns.extra_records` mechanism
took over LAN+tailnet structured names.

The notable finding was that **Phase 4 of the original plan turned
out to be unnecessary**: there is no need for a per-host cloud-init
seed to inject hostname/hostId at first boot.  The full-system push
via `nixos-rebuild --target-host root@nerd-nixos.local --flake
.#bioskop-tart` carries the host-specific `networking.hostName` and
the host-derived `networking.hostId` through the flake attribute
itself; identity flips at full-system activation, no first-boot
intervention needed.  The mDNS `nerd-nixos.local` advertised by the
generic bringup image is the operator's SSH target; once the push
lands, mDNS re-advertises under `bioskop-nixos.local` (or
`nikopol-nixos.local` for the second host).

=== 2. ZFS extra-pool hostid drift fix ✅

Phase 5 verification surfaced a known risk from the plan note (R2):
the bringup image creates ZFS pool labels with `hostid=00000000`
(the placeholder), and the full system boots with a host-derived
hostid.  `forceImportRoot = true` covered the root pool but not
extra pools (`recover`); `zfs-import-recover.service` failed.

Fix: `boot.zfs.forceImportAll = true` in
`modules/nixos/zfs.nix` (commit `2e3a9e4a`).  Every pool import
now re-stamps its hostid label on first boot, after which subsequent
boots are clean.  Trade-off documented in the comment: loses the
safety check that catches accidental import-on-wrong-host —
acceptable for a single-operator fleet where hostid changes are
deliberate.

Operator side, the existing bioskop-nixos pool needed a one-shot
`sudo zpool import -f recover` to bootstrap; future bringups are
self-healing.

Note on `nixos-rebuild` semantics that bit during the rotation:
when the working tree carries `M .secrets`, `nixos-rebuild --flake
.#…` evaluates against the **previously-committed** `.secrets`
content, not the working tree.  This is by design — flakes default
to clean-tree evaluation.  Symptom: the deployed key on the VM
stayed the old (dead) value despite a successful-looking rebuild.
Resolution: commit `.secrets` first, then push.  The committed
state changes the source-tree store path, the new path's `.secrets`
is what `sops-install-secrets` reads, the new key reaches the VM.

== Technical Details

=== The `.secrets` rebuild gotcha

This caught me twice.  The mechanism, summarised:

. `sops` decryption happens at activation time, not at build time —
  the encrypted `.secrets` file is shipped via the flake source
  tree, decrypted on the target host using the host's age key.
. The flake source tree is realised as a single store path
  `/nix/store/<hash>-source/` containing the entire repo content.
  `sopsFile = "${self}/.secrets"` resolves to
  `/nix/store/<hash>-source/.secrets`.
. The `<hash>` is content-addressable over the entire tree,
  excluding gitignored content.  `nixos-rebuild --flake` evaluates
  against the **committed** state of the tree (the dirty-tree
  warning notwithstanding — actual eval uses the committed
  content).
. Editing `.secrets` without committing leaves the source-tree
  hash unchanged from the flake's perspective.  `sops-install-
  secrets` decrypts the **old committed `.secrets` blob** and the
  deployed value on the VM reflects the old content.
. Only after `git add .secrets && git commit` does the source-tree
  hash change, the new `<hash>-source/.secrets` is shipped, and
  the new content gets decrypted.

The pattern when rotating any sops-encrypted secret:

[source,bash]
----
sops .secrets                # edit
git add .secrets
git commit -m "chore(.secrets): rotate <kind>"
nixos-rebuild switch --target-host root@<host>.local --flake .#<config>
----

=== Pushing to the right SSH target

A separate gotcha: between bringup and full activation, the VM's
hostname changes from `nerd-nixos` to `<host>-nixos`.  Both
hostnames register in mDNS.  The push must target the **active**
hostname:

* During bringup: `root@nerd-nixos.local`
* After full activation: `root@<host>-nixos.local`
* For incremental updates (the daily case): always
  `root@<host>-nixos.local`

I pushed to the wrong target once, which is why the live config
didn't update despite a successful local rebuild.  No corrective
action needed in the codebase; just an operator-aware reminder.

=== Boot generations after the unification

`bootctl list` on bioskop-nixos shows two clean entries:

* Gen 1: built from `nerd-nixos-bringup-zfs-systemd-disk` (the
  bringup image; hostname `nerd-nixos`)
* Gen 2: built from the bioskop-tart full system (hostname
  `bioskop-nixos`); selected default

Gen 1 is preserved as a fallback path: the operator can boot back
into the bringup state if the full system breaks.  No automatic
GC on it; manual `nix-collect-garbage --delete-old` would clean it
once gen 2 is trusted.
