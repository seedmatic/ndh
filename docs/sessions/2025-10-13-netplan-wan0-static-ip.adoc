== Problem Summary

The `wan0` interface in RKE2 cluster Incus containers was not receiving its static IP configuration (`10.80.16.3/24`) despite proper netplan configuration in cloud-init user-data. Cloud-init was falling back to auto-detection and only configuring `lan0` with DHCP.

== Root Cause Analysis

=== Primary Issue: Cloud-Init Instance ID

The fundamental issue was that cloud-init was not treating recreated instances as "new instances" due to:

1. **Static Instance ID**: The `instance-id` in metadata was hardcoded to `master`
2. **Event System Blocking**: Cloud-init's event system denied network configuration updates for non-new instances
3. **Fallback Network Detection**: When network config updates were blocked, cloud-init used fallback auto-detection

=== Secondary Issues Discovered

1. **Interface Name Confusion**: Initial confusion between Lima VM interfaces (`vmlan0`/`vmwan0`) vs container interfaces (`lan0`/`wan0`)
2. **Renderer Selection**: Cloud-init was selecting legacy `eni` renderer instead of `networkd`
3. **Template Processing Complexity**: Earlier architectural changes had simplified template processing but this wasn't related to the network issue

== Solution Implementation

=== Current Network Configuration

The netplan configuration in `cloud-config.common.yaml` is correct:

[source,yaml]
----
network:
  version: 2
  renderer: networkd
  ethernets:
    lan0:  # LAN (primary) - DHCP for home network access
      dhcp4: true
      dhcp6: true
      dhcp-identifier: mac
      optional: true
    wan0:  # WAN (secondary) - Static IP for cluster communication
      dhcp4: false
      addresses:
        - ${RKE2_CLUSTER_RKE2_NODEINET}/24
      routes:
        - to: 0.0.0.0/0
          via: ${RKE2_CLUSTER_INET_GATEWAY}
      nameservers:
        addresses:
          - ${RKE2_CLUSTER_INET_GATEWAY}
          - 1.1.1.1
      optional: true
----

=== Instance ID Fix Applied

Modified the Makefile to generate unique instance IDs:

**File**: `/Users/nxmatic/Gits/nxmatic/nix-darwin-home/modules/nixos/rke2lab/Makefile`

[source,makefile]
----
# BEFORE:
define METADATA_INLINE :=
instance-id: $(RKE2_CLUSTER_RKE2_NODENAME)
local-hostname: $(RKE2_CLUSTER_RKE2_NODEDN)
endef

# AFTER:
define METADATA_INLINE :=
instance-id: $(RKE2_CLUSTER_RKE2_NODENAME)-$(shell date +%s)
local-hostname: $(RKE2_CLUSTER_RKE2_NODEDN)
endef
----

This ensures each instance recreation gets a unique timestamp-based instance-id, forcing cloud-init to treat it as a new instance.

== Technical Context

=== File Locations

- **Main Config**: `cloud-config.common.yaml` - Contains correct netplan configuration
- **Makefile**: Modified to generate unique instance-ids  
- **Generated Metadata**: `.run.d/master/nocloud/meta-data.yaml` - Now has timestamp-based instance-id
- **Generated Userdata**: `.run.d/master/nocloud/user-data.yaml` - Contains merged cloud-config

=== Network Architecture

- **Lima VM Host**: Interfaces `vmlan0` (Lima LAN) and `vmwan0` (Lima WAN)
- **Container**: Interfaces `lan0` (mapped from vmlan0) and `wan0` (mapped from vmwan0)
- **IP Ranges**:
  - `lan0`: DHCP from home network (192.168.1.0/24)  
  - `wan0`: Static cluster IPs (10.80.16.0/24)
  - Master: `10.80.16.3/24` with gateway `10.80.16.1`

=== Cloud-Init Event System

Cloud-init has event scopes that control when configuration can be applied:

- `boot-new-instance`: Allows network configuration (what we want)
- `boot-legacy`: Denies network configuration changes (what was happening)

The instance-id determines which event type is triggered.
