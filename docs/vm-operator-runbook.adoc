= VM Operator Runbook
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge

== Overview

This runbook covers the full lifecycle of the Lima/Tart NixOS VM:
initial disk image build, VM materialisation, day-to-day reset workflow,
and emergency-mode debugging via the virtio-serial debug shell.

== Architecture

[source]
----
macOS host (bioskop / nxmatic-mbp)
└── lima / tart runtime
    └── nerd-nixos (NixOS Lima VM)
        ├── /dev/vda  → boot.img    (EFI, ~600 MiB)
        ├── /dev/vdb  → tank1.img   (ZFS raidz1 member, 100 GiB)
        ├── /dev/vdc  → tank2.img   (ZFS raidz1 member, 100 GiB)
        ├── /dev/vdd  → tank3.img   (ZFS raidz1 member, 100 GiB)
        └── /dev/vde  → recover.img (ZFS single-disk recovery pool, 100 GiB)

Disk images are built by a nested QEMU VM (linux-builder) running inside a
Nix derivation.  The resulting store path seeds the Lima external disks on
first import, then is expanded to the full 100 GiB target size.
----

== Prerequisites

* `limactl` installed (via Homebrew or Nix)
* `nix` with flakes enabled
* `socat` on the host (for debug shell access)
* `nix-darwin-home` git checkout present (required by `run.sh`)

== Phase 1 — Lima Config Materialisation (first-time only)

Before any VM can start, Lima needs its `lima.yaml` config file in
`~/.lima/nerd-nixos/`.  This is generated by running the Lima materialiser
activation from the NDH flake.

[source,bash]
----
# From the nix-darwin-home checkout (must be the nxmatic/nix-darwin-home remote):
nix run .#bioskop-nixos-lima-vm-materialize
----

This writes `~/.lima/nerd-nixos/lima.yaml` and registers the external Lima
disks (`nerd-nixos-tank1` … `nerd-nixos-recover`) with `limactl disk create`.

NOTE: The materialiser must run at least once before `vm:reset` or `vm:start`
will work.  If `lima.yaml` is missing, `run.sh` will exit with an error.

== Phase 2 — Full VM Reset / First Boot

`vm:reset` is the canonical operator command for both first-time provisioning
and subsequent disk rebuilds.  Run it from inside the NDH checkout:

[source,bash]
----
cd /path/to/nix-darwin-home
./modules/darwin/lima-config.d/run.sh vm:reset
----

What `vm:reset` does (in order):

. `vm:kill` — force-stop the VM (`limactl stop -f`)
. `host:disk:image:build` — runs `nix build` for the ZFS bringup disk image
  (attribute: `nixosDiskImages.<host>.bringup.zfsSystemd`)
. `host:lima:tank:disks:import` — copies `tank1/2/3/recover.img` from the
  Nix store into `~/.lima/_disks/nerd-nixos-<disk>/datadisk`, then extends
  each disk to `LIMA_EXTERNAL_DISK_SIZE` (default 100 GiB)
. `host:lima:config:ensure` — verifies `lima.yaml` exists
. `vm:factory:reset` — runs `limactl factory-reset nerd-nixos` and starts the VM

[NOTE]
====
External tank disks are *preserved* during `vm:factory:reset` for `nerd-nixos`
(policy: `vm:external:disks:should:reset` returns false).  Only the root disk
is reset.  Tank disks are refreshed only by `host:lima:tank:disks:import`.
====

=== Environment overrides for vm:reset

[cols="2,1,3"]
|===
|Variable |Default |Description

|`NDH_VZ_HOST_FLAKE_REF`
|auto (git root)
|Override the NDH flake path.  Must not include `#attr`.

|`LIMA_NIXOS_DISK_IMAGE_ATTR`
|`nixosDiskImages.<host>.bringup.zfsSystemd`
|Override the bringup disk image attribute.

|`LIMA_EXTERNAL_DISK_SIZE`
|`100G`
|Target size to which each imported tank disk is extended.

|`NDH_NIX_CLI_ARGS`
|`-L -v -v`
|Extra args passed to all managed `nix` invocations (build, run).
|===

== Phase 3 — NixOS Bootstrap After First Boot

After `vm:reset`, the Lima VM boots into the ext4/btrfs bootstrap system.
The ZFS pool is already imported from the seeded tank disks.  To activate
the ZFS system:

[source,bash]
----
# 1. Apply ZFS boot generation:
./modules/darwin/lima-config.d/run.sh vm:nixos:boot:zfs

# 2. Switch to ZFS generation live (stays on old root until reboot):
./modules/darwin/lima-config.d/run.sh vm:nixos:switch

# 3. Trigger idempotent ZFS bootstrap activation unit:
./modules/darwin/lima-config.d/run.sh vm:nixos:zfs-bootstrap
----

== Monitoring the Nested QEMU Build

During `nix build` of the disk image, the nested QEMU VM writes all output
to the nix build log via `-nographic` stdio.  Watch it with:

[source,bash]
----
nix build .#nixosDiskImages.bioskop.bringup.zfsSystemd -L
# or via log-capture helper:
nix run .#bioskop-nixos-log-capture -- --name bringup-zfs -- \
  nix build .#nixosDiskImages.bioskop.bringup.zfsSystemd -L
----

=== Connecting to the Debug Shell

The nested QEMU guest exposes an interactive root shell via a virtio-serial
Unix socket (`shell.sock`).  Connect from the linux-builder host:

[source,bash]
----
# Find the QEMU PID (run on linux-builder, not macOS):
qpid=$(pgrep --newest qemu)

# Connect (Ctrl+] to disconnect):
sudo socat UNIX-CONNECT:/proc/$qpid/root/build/shell.sock \
  -,raw,echo=0,escape=0x1d
----

NOTE: The socket is inside the linux-builder's nix sandbox
(`/proc/<qpid>/root/build/shell.sock`).  You need `sudo` to enter the build
sandbox namespace.

==== First thing after connecting — fix terminal size

[source,bash]
----
resize
----

This sends an escape sequence to auto-detect the VS Code terminal dimensions
and calls `stty` to match them inside the guest.

=== Perf / Debug Tools Available in the Shell

[cols="2,3"]
|===
|Command |Purpose

|`iostat -x 1`
|Per-disk utilisation, await, queue depth

|`mpstat -P ALL 1`
|Per-CPU breakdown

|`pidstat -d 1`
|Per-process I/O rates

|`iotop-c`
|Live top-style I/O monitor (C rewrite, no Python needed)

|`htop`
|Interactive CPU / memory / process overview

|`vmstat 1`
|Memory pressure + block I/O summary

|`zpool iostat -v 1`

|`lsof`
|Open files, sockets, ZFS file handles

|`strace -p <pid>`
|Syscall trace on any guest process
|===

== ZFS Install-Time Tuning

The bringup install script applies temporary kernel parameters and pool
properties to maximise write throughput during `nixos-install`.  These are
all reset to production values before pool export:

[cols="2,1,1,3"]
|===
|Parameter |Install value |Production default |Rationale

|`sync` (pool)
|`disabled`
|`standard`
|Skip ZIL flush per write — biggest throughput gain on virtio disks

|`logbias` (pool)
|`throughput`
|`latency`
|Avoid indirect ZIL for large sequential blocks

|`zfs_arc_max`
|2/3 RAM
|~1/2 physical RAM
|More metadata cached → fewer re-reads during install

|`zfs_txg_timeout`
|`5` s (default)
|`5` s
|Keep at default — extending to 30s defers all dirty data into a massive
end-of-install flush; `txg_sync` dominates iotop and install appears stuck.
`sync=disabled` is the real throughput win; frequent 5s flushes spread I/O evenly.

|`zfs sync` (explicit drain)
|before property reset
|—
|Drain remaining dirty TXGs while `sync=disabled` is still active.
Without this, restoring `sync=standard` triggers an uncontrolled final flush.

|`recordsize` (nerd/nix)
|`16K` (permanent)
|`128K`
|Nix store files are small (<64K); 128K causes write amplification

|`primarycache` (nerd/nix)
|`metadata` (permanent)
|`all`
|Store files are write-once; keep ARC for metadata not data blocks
|===

NOTE: `recordsize` and `primarycache` on `nerd/nix` are permanent dataset
properties (set in disko config) — appropriate for production too.

== Emergency Mode Troubleshooting

=== VM fails to start

[source,bash]
----
# Check Lima logs:
tail -f ~/.lima/nerd-nixos/serial*.log

# Verify disk registration:
limactl disk ls

# Force-reset if stuck:
limactl stop -f nerd-nixos
./modules/darwin/lima-config.d/run.sh vm:factory:reset
----

=== ZFS pool not importing

Connect to the debug shell (see above) and run:

[source,bash]
----
# List block devices:
lsblk -f

# Try manual import:
zpool import -d /dev/disk/by-partlabel tank
zpool import -d /dev/disk/by-partlabel recover

# Check pool status:
zpool status -v
zpool events
----

=== nixos-install hung or slow

[source,bash]
----
# In the debug shell — check what nix is doing:
pidstat -d 1        # which process is doing I/O?
iotop-c             # live I/O breakdown
zpool iostat -v 1   # ZFS throughput per vdev
iostat -x 1         # raw virtio disk stats
----

==== txg_sync dominates at end of install

If `iotop-c` shows `txg_sync` with high IO% but 0 B/s current write after
`nixos-install` completes, this is ZFS flushing deferred dirty TXGs before
pool export.  Normal duration is ~30-60s.

*Root cause*: the tuning script sets `zfs_txg_timeout=5s` and calls
`zfs sync` explicitly before restoring `sync=standard`, which drains dirty
data while optimisations are still active.  If this stall recurs, check
that the `zfs sync` drain step ran before `zfs set sync=standard`.

=== Stuck build — find the nested QEMU PID

[source,bash]
----
# On linux-builder (inside the Nix sandbox namespace):
ps aux | grep qemu
# or:
pgrep -a qemu-system
----

== Reference: run.sh Commands

[source]
----
./modules/darwin/lima-config.d/run.sh <command>

vm:disk:nixos:build   Build disk image + ensure Lima config + boot VM
vm:reset              Stop VM + build image + import tank disks + factory-reset + start
vm:start              Start Lima VM
vm:kill               Force-stop VM (limactl stop -f)
vm:nixos:switch       Remote NixOS switch (nixos-rebuild --build-host/--target-host)
vm:nixos:boot         Remote NixOS boot generation update
vm:nixos:boot:ext4    Boot into ext4/btrfs bootstrap target
vm:nixos:boot:zfs     Boot into ZFS target (switch + zfs-bootstrap run separately)
vm:nixos:zfs-bootstrap Start zfs-bootstrap-activation.service on the VM
vm:disk:create [name] Create one/all Lima external disks
vm:disk:unlock [name] Unlock one/all Lima external disks
socket:run            Start socket_vmnet bridge (bridged → en0)
----
