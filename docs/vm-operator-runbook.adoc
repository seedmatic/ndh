= VM Operator Runbook
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge

== Overview

This runbook covers the full lifecycle of the Tart NixOS VM:
initial disk image build, VM materialisation, day-to-day reset workflow,
and emergency-mode debugging via the virtio-serial debug shell.

== Architecture

[source]
----
macOS host (bioskop / nxmatic-mbp)
└── tart runtime (Apple Virtualization framework)
    └── nerd-nixos (NixOS Tart VM, ~/.tart/vms/nerd-nixos/)
        ├── /dev/vda  → disk.img    (root — EFI System Partition + systemd-boot)
        ├── /dev/vdb  → tank1.img   (ZFS raidz1 member, 100 GiB)
        ├── /dev/vdc  → tank2.img   (ZFS raidz1 member, 100 GiB)
        ├── /dev/vdd  → tank3.img   (ZFS raidz1 member, 100 GiB)
        └── /dev/vde  → recover.img (ZFS single-disk recovery pool, 100 GiB)

vda (disk.img) holds the EFI System Partition + systemd-boot.
All ZFS data lives on the uniform tank disks (vdb/vdc/vdd), keeping them
seedable and identical — no dual boot+data role on any tank disk.
----

== Prerequisites

* `tart` installed (Apple Virtualization framework CLI)
* `nix` with flakes enabled
* `socat` on the host (for the serial PTY bridge and debug shell access)
* `nix-darwin-home` git checkout present

== Phase 1 — Tart VM Materialisation (first-time + disk rebuilds)

Before any VM can start, the Tart VM directory (`~/.tart/vms/nerd-nixos/`)
must be materialised.  This is a fixed-name flake app (not per-host):

[source,bash]
----
# From the nix-darwin-home checkout:
nix run .#nerd-tart-vm-materialize
----

It builds the ZFS bringup disk image, creates the root disk `disk.img`
(via `tart create`), creates any missing data disks
(`tank1.img` … `tank3.img` + `recover.img`), writes `config.json` and the
generated run wrapper `~/.tart/vms/nerd-nixos.sh`, and syncs the bringup
image into the VM directory.

Per-host operators use `nerd-tart-<host>-deploy`, which copies the same
bundle to a vz host and runs the identical activation there.

NOTE: The materialiser must run at least once before the run wrapper or the
bootstrap installer will work — the installer aborts if
`~/.tart/vms/nerd-nixos.sh` is missing.

== Nested QEMU CPU Architecture

Understanding the CPU stack is important for tuning the bringup build:

[source]
----
Apple M4 Pro (12 cores, bare metal, macOS)
  └── linux-builder (outer QEMU, accel=tcg, 8 vCPUs)
        └── nixos-install nested QEMU (accel=tcg, 2 vCPUs)
----

* **Outer QEMU** (`nix.linux-builder`): 8 vCPUs, each a macOS thread scheduled
  natively on the M4 Pro cores.  Uses TCG because macOS has no Linux hypervisor.
  Configured via `inventory.builder.vmCpuCores = 8` (clamped at 8 by mach-virt limit).

* **Nested QEMU** (bringup disk image build): 2 vCPUs (MTTCG threads), running
  inside the linux-builder guest.  More vCPUs = more TCG lock contention with no
  throughput benefit — the workload is I/O-bound (ZFS virtio writes), not CPU-bound.
  Overridable per host via `nixosDiskImageVmCpuCores` in `hostProfile`.

* **Real parallelism**: 8 outer vCPUs × macOS scheduler → 12 bare-metal cores.
  The 2 nested TCG threads get ~2/8 of those 8 outer vCPUs, leaving 6 for the
  linux-builder kernel, virtiofsd, ZFS I/O path.

=== Future: nerd-nixos on Tart as the build machine

Once nerd-nixos runs inside Tart (Apple Virtualization framework), the build
stack changes fundamentally:

[source]
----
Apple M4 Pro (12 cores, bare metal)
  └── nerd-nixos (Tart/VZ — native aarch64, KVM available)
        └── nested QEMU (accel=kvm — real hardware vCPUs, no TCG)
              └── nixos-install
----

With KVM, nested QEMU vCPUs execute natively — the 2-vCPU limit no longer
applies.  `nixosDiskImageVmCpuCores` should be revisited upward (4-6) and
`nixosDiskImageVmMemSizeMiB` can be increased to use nerd-nixos's larger
memory allocation.

linux-builder becomes redundant for `aarch64-linux` once nerd-nixos is
stable on Tart.  The migration path:

. nerd-nixos boots on Tart (current work)
. Add nerd-nixos as a remote builder in `distributed-builds.nix`
. Verify bringup disk image builds succeed via nerd-nixos builder
. Set `linuxBuilderMode = "remote"` in bioskop host profile
. Disable embedded linux-builder (`nix.linux-builder.enable = false`)

== Phase 2 — Full VM Reset / First Boot

Re-running the materialiser is the canonical path for both first-time
provisioning and subsequent disk rebuilds.  For a full reset — stop + delete
the VM and wipe its directory before recreating — set `VM_FACTORY_RESET=true`:

[source,bash]
----
cd /path/to/nix-darwin-home
VM_FACTORY_RESET=true nix run .#nerd-tart-vm-materialize
----

What the materialiser does (in order):

. Builds the ZFS bringup disk image (`nix build`).
. When `VM_FACTORY_RESET=true`: stops + deletes the VM and `rm -rf`s
  `~/.tart/vms/nerd-nixos/` before recreating.
. Creates the root disk `disk.img` via `tart create`.
. Creates any missing data disks (`tank1/2/3.img` + `recover.img`) and
  syncs the bringup image into the VM directory.
. Writes `config.json` and the run wrapper `~/.tart/vms/nerd-nixos.sh`.

Then start the VM with the generated run wrapper:

[source,bash]
----
~/.tart/vms/nerd-nixos.sh
----

[NOTE]
====
`VM_FACTORY_RESET` is consumed as a shell command, so the only meaningful
truthy value is the literal `true`.  Without it, an existing `disk.img` and
the tank/recover disks are left in place and only *missing* disks are
created — a plain re-run never destroys populated data disks.
====

=== Environment overrides for the materialiser

[cols="2,1,3"]
|===
|Variable |Default |Description

|`VM_FACTORY_RESET`
|`false`
|Set to `true` to stop+delete the VM and wipe its directory before recreating.
|===

== Phase 3 — NixOS Activation After First Boot

The VM first boots the generic bringup system (hostName `nerd-nixos`), which
imports the ZFS pool from the seeded tank disks and brings up network + SSH.
There is no host→guest orchestration wrapper: activation is a plain remote
`nixos-rebuild` from the build host (bioskop) against the guest, reached over
mDNS as `<host>-nixos.local`.  The minimal bringup image has no `/etc/nixos`,
so the first activation must be `--target-host` (the prebuilt toplevel is
shipped via `nix copy`):

[source,bash]
----
nixos-rebuild switch --target-host root@<host>-nixos.local
----

The ZFS bootstrap is no longer an operator-invoked step: it runs
automatically at first boot of the ZFS target via the
`zfs-bootstrap-activation` systemd unit (NixOS options
`zfsOverlays.bootstrapActivation.*`).

For day-2 in-guest rebuilds — once `modules/nixos/etc-nixos-flake.nix` has
materialised `/etc/nixos/flake.nix` — `nixos-rebuild-guest
[switch|boot|test|build]` runs inside the guest, and `nixos-rebuild-gh` wraps
`nixos-rebuild` with a `gh auth token` for private flake refs.

== Monitoring the Nested QEMU Build

=== Prerequisites

Enable Vector on your Darwin host (one-time, then `darwin-rebuild switch`):

[source,nix]
----
# In your bioskop host profile:
bringupObserve.enable = true;
----

This installs `vector` and exports `NDH_VECTOR_HTTP_PORT` / `NDH_VECTOR_API_PORT`
into the user session.

=== Running a Monitored Build

Use `bin/nix-build-observe.sh` instead of bare `nix build`.  It starts an
ephemeral Vector instance, collects macOS VZ-host metrics in real-time, and
ingests builder + guest YAML telemetry after the build completes.

[source,bash]
----
cd /path/to/nix-darwin-home

# Standard monitored build:
bin/nix-build-observe.sh .#nixosDiskImages.bioskop -L -v -v

# With post-install pause (see section below) and verbose nix output:
env NDH_BRINGUP_PAUSE=true \
  bin/nix-build-observe.sh .#nixosDiskImages.bioskop -L -v -v

# Plain `nix build` requires --impure so flake eval can read the env var:
env NDH_BRINGUP_PAUSE=true \
  nix build --impure .#bioskop-tart-vm-materialize -L -v -v
----

[IMPORTANT]
.Operator gates require `--impure` in plain `nix build`
====
All `NDH_*` operator gates are read at flake evaluation time via
`builtins.getEnv`, which returns the empty string in pure mode.  The
wrapper `bin/nix-build-observe.sh` already passes `--impure --impure-env`
automatically.  When running **bare** `nix build`, pass `--impure`
yourself or the gate will silently be baked in as its default (`false`
for both `NDH_BRINGUP_PAUSE` and `NDH_BUILD_OBSERVE`).

All boolean gates use canonical `"true"` / `"false"` strings — anything
else is rejected at eval time.  `"1"` and `"0"` are not accepted.
====

==== What the observer collects

[cols="1,2,3"]
|===
|Layer |Source |Metrics

|`vz-host`
|macOS, real-time every 5 s
|`vm_stat` (free/wired/compressed pages), BSD `iostat` per disk, nix-daemon cpu%/RSS

|`builder`
|linux-builder, real-time via Vector agent forwarding
|QEMU pid cpu%/RSS, host `iostat`, host dirty/writeback/avail memory

|`guest`
|nested QEMU, real-time via socat relay to Vector agent
|ZFS ARC hit%, vdev latency, disk I/O, memory pressure, install phase markers
|===

~/.local/share/ndh/build-obs/

  latest.ndjson             ← symlink to most recent session

==== Real-time event streaming

The Vector LaunchAgent exposes a GraphQL API for live event inspection via the `vector tap` command.

First, verify the Vector API is reachable:

[source,bash]
----
# Check Vector is running and API is responding
curl -s http://127.0.0.1:8686/graphql -X POST \
  -H "Content-Type: application/json" \
  -d '{"query": "{ health }"}' | jq

# Expected output: {"data": {"health": true}}
----

If the API isn't reachable, ensure the LaunchAgent is running and has the correct config:

[source,bash]
----
# Check LaunchAgent status
launchctl list | grep bringup-observe-vector

# Restart if needed
launchctl kickstart -k gui/$(id -u)/io.nxmatic.nix-darwin-home-bringup-observe-vector

# Verify config has API enabled (should show: enabled = true)
grep -A2 "^\[api\]" ~/.local/share/nix-build-observe/vector-config.toml
----

Stream events in real-time:

[source,bash]
----
# Stream events from the HTTP source (all incoming events)
vector tap --url http://127.0.0.1:8686/graphql \
  --outputs-of 'nix_bld_http' --format json --meta

# Monitor what's being written to the NDJSON file
vector tap --url http://127.0.0.1:8686/graphql \
  --inputs-of 'ndjson_file' --format json --meta

# Tail all components with quiet output (events only)
vector tap --url http://127.0.0.1:8686/graphql '*' \
  --format json --quiet

# Or tail the NDJSON file directly
tail -f ~/.local/share/nix-build-observe/latest.ndjson | jq -c .
----

[NOTE]
.Canonical boolean encoding
====
All `NDH_*` gates listed above are boolean and encoded as the literal
strings `"true"` or `"false"`.  Legacy `"1"` / `"0"` forms are rejected
at flake evaluation with an explanatory error.  Internally the resolved
value is baked into shell scripts as a literal `true` / `false` token
that is **run as a bash command** (relying on the `true` / `false`
builtins) rather than string-compared.
====

=== Post-Install Pause — Inspecting the Nested QEMU Guest

When `NDH_BRINGUP_PAUSE=true`, the bringup install script creates a lock file
inside the shared `xchg/` virtiofs volume after `nixos-install` completes.
The QEMU VM blocks until the operator removes the lock — `/mnt/zfs-root` remains
mounted for inspection.

==== Connecting to the Debug Shell

The nested QEMU guest exposes an interactive root shell via a virtio-serial
Unix socket.  Connect from inside the linux-builder (not from macOS):

[source,bash]
----
# Find the QEMU PID (run on linux-builder):
qpid=$(pgrep --newest qemu)

# Connect (Ctrl+] to disconnect):
sudo socat UNIX-CONNECT:/proc/$qpid/root/build/shell.sock \
  -,raw,echo=0,escape=0x1d
----

NOTE: The socket lives inside the linux-builder's Nix sandbox namespace.
`/proc/<qpid>/root/build/shell.sock` and `/proc/<qpid>/cwd/shell.sock` name the
same file — the QEMU cwd is the sandbox's `/build`, so both forms resolve
identically. `sudo` is required to enter the namespace either way.

==== First thing after connecting — fix terminal size

[source,bash]
----
resize
----

==== Inspecting the installed system

[source,bash]
----
# The ZFS root is still mounted at /mnt/zfs-root:
ls /mnt/zfs-root
zpool status -v
zfs list -r tank

# Check what nixos-install wrote:
ls /mnt/zfs-root/nix/var/nix/profiles/
cat /mnt/zfs-root/boot/loader/loader.conf
----

==== Resuming the build

[source,bash]
----
# From inside the debug shell:
rm /tmp/xchg/pause.lock
----

The build resumes, calls `zfs sync`, restores production pool properties, exports
the pools, and the QEMU VM exits normally.

== ZFS Install-Time Tuning

The bringup install script applies temporary kernel parameters and pool
properties to maximise write throughput during `nixos-install`.  These are
all reset to production values before pool export:

[cols="2,1,1,3"]
|===
|Parameter |Install value |Production default |Rationale

|`sync` (pool)
|`disabled`
|`standard`
|Skip ZIL flush per write — biggest throughput gain on virtio disks

|`logbias` (pool)
|`throughput`
|`latency`
|Avoid indirect ZIL for large sequential blocks

|`zfs_arc_max`
|2/3 RAM
|~1/2 physical RAM
|More metadata cached → fewer re-reads during install

|`zfs_txg_timeout`
|`5` s (default)
|`5` s
|Keep at default — extending to 30s defers all dirty data into a massive
end-of-install flush; `txg_sync` dominates iotop and install appears stuck.
`sync=disabled` is the real throughput win; frequent 5s flushes spread I/O evenly.

|`zfs sync` (explicit drain)
|before property reset
|—
|Drain remaining dirty TXGs while `sync=disabled` is still active.
Without this, restoring `sync=standard` triggers an uncontrolled final flush.

|`recordsize` (nerd/nix)
|`16K` (permanent)
|`128K`
|Nix store files are small (<64K); 128K causes write amplification

|`primarycache` (nerd/nix)
|`metadata` (permanent)
|`all`
|Store files are write-once; keep ARC for metadata not data blocks
|===

NOTE: `recordsize` and `primarycache` on `nerd/nix` are permanent dataset
properties (set in disko config) — appropriate for production too.

== Emergency Mode Troubleshooting

=== VM fails to start

[source,bash]
----
# Check the serial log (written by the run wrapper):
tail -f ~/.tart/vms/nerd-nixos/serial.log

# List Tart VMs and inspect the target:
tart list
ls -la ~/.tart/vms/nerd-nixos/

# Force-reset if stuck (stop + wipe + recreate):
tart stop nerd-nixos || true
VM_FACTORY_RESET=true nix run .#nerd-tart-vm-materialize
----

=== ZFS pool not importing

Connect to the debug shell (see above) and run:

[source,bash]
----
# List block devices:
lsblk -f

# Try manual import:
zpool import -d /dev/disk/by-partlabel tank
zpool import -d /dev/disk/by-partlabel recover

# Check pool status:
zpool status -v
zpool events
----

=== nixos-install hung or slow

[source,bash]
----
# In the debug shell — check what nix is doing:
pidstat -d 1        # which process is doing I/O?
iotop-c             # live I/O breakdown
zpool iostat -v 1   # ZFS throughput per vdev
iostat -x 1         # raw virtio disk stats
----

Check the observer output on the macOS host for a macro view:

[source,bash]
----
# Last 20 events across all layers:
tail -n 20 ~/.local/share/ndh/build-obs/latest.ndjson | \
  yq -p json '{ts: .ts, layer: .source_layer, type: .type}' -o yaml

# Builder memory pressure (from the linux-builder layer):
yq 'select(.source_layer == "builder" and .mem != null) | .mem' \
  -p json -o yaml \
  ~/.local/share/ndh/build-obs/latest.ndjson
----

==== txg_sync dominates at end of install

If `iotop-c` shows `txg_sync` with high IO% but 0 B/s current write after
`nixos-install` completes, this is ZFS flushing deferred dirty TXGs before
pool export.  Normal duration is ~30-60s.

*Root cause*: the tuning script sets `zfs_txg_timeout=5s` and calls
`zfs sync` explicitly before restoring `sync=standard`, which drains dirty
data while optimisations are still active.  If this stall recurs, check
that the `zfs sync` drain step ran before `zfs set sync=standard`.

=== Stuck build — find the nested QEMU PID

[source,bash]
----
# On linux-builder (inside the Nix sandbox namespace):
ps aux | grep qemu
# or:
pgrep -a qemu-system
----

== VM Rescue: Inspect a Non-Booting VM via Debian Live

Use this procedure whenever `nerd-nixos` fails to boot (bad bootloader,
missing EFI entry, ZFS import failure, kernel panic before serial is up).
A Debian live VM is used as the rescue environment because its EFI firmware
and tools (efibootmgr, chroot, ZFS DKMS) are available without touching the
broken guest.

The in-guest steps (ZFS import, chroot, efibootmgr) are engine-independent.

=== Why Debian, not another NixOS VM?

`efibootmgr` manipulates the EFI NVRAM variables of the _guest_ firmware.
A Debian VM image already has `zfsutils-linux`, ZFS DKMS, and `efibootmgr`
packaged and ready — no Nix build required.  Tart stores the guest EFI NVRAM
in a file on the host (not in macOS firmware), so manipulating it from a
rescue VM that attaches the same disks works.

=== Step 1 — Prepare the Debian rescue VM

[source,bash]
----
# Pull a ready-made Debian ARM64 image (first time only):
tart pull ghcr.io/cirruslabs/debian:latest

# Clone it to a disposable rescue VM:
tart clone ghcr.io/cirruslabs/debian:latest debian-rescue
----

=== Step 2 — Locate the target's disk images

[source,bash]
----
VM_DIR="${HOME}/.tart/vms/nerd-nixos"
ls "${VM_DIR}"
# disk.img   tank1.img  tank2.img  tank3.img  recover.img  config.json  nvram.bin  …
----

NOTE: The guest EFI NVRAM file that `tart create` writes alongside
`config.json` (Tart's canonical name is `nvram.bin`) holds the guest boot
variables — verify the exact filename on a fully-created VM before editing it.

=== Step 3 — Start the rescue VM with the target's data disks attached

Serial console + VNC/display must both be active for this procedure: the
display gives access to the EFI shell / bootloader menu; the serial console
provides a login prompt once Debian userspace is up.

[WARNING]
====
Never attach `nerd-nixos` disks while `nerd-nixos` itself is running —
simultaneous writes from two VMs will corrupt the ZFS pools.
====

[source,bash]
----
VM_DIR="${HOME}/.tart/vms/nerd-nixos"

# Disable headless so the EFI/bootloader UI is visible:
NO_GRAPHICS=0 \
tart run debian-rescue \
  --vnc-experimental \
  --serial \
  --disk "${VM_DIR}/disk.img" \
  --disk "${VM_DIR}/tank1.img" \
  --disk "${VM_DIR}/tank2.img" \
  --disk "${VM_DIR}/tank3.img" \
  --disk "${VM_DIR}/recover.img"
----

Add `:ro` to any disk to mount read-only: `--disk "${VM_DIR}/disk.img:ro"`.

=== Step 4 — Connect the serial console

[source,bash]
----
# Tart prints the PTY path on startup.  Attach with screen:
screen /dev/ttySXX     # replace with the PTY path printed at startup
# Or reattach if the auto-screen session was started:
screen -r debian-rescue-serial
----

TIP: Resize immediately after connecting: `resize && reset`

=== Step 5 — Identify the attached disks

[source,bash]
----
lsblk -f
# Expected layout (ARM64 virtio):
#   vda  → disk.img      (nerd-nixos EFI + systemd-boot)
#   vdb  → tank1.img
#   vdc  → tank2.img
#   vdd  → tank3.img
#   vde  → recover.img
#   vdf  → debian rescue root
----

=== Step 6 — Force-import the ZFS pools

[source,bash]
----
# Install ZFS if not already present in the image:
apt-get install -y zfsutils-linux   # only if missing

# Force-import tank pool to alternate root /mnt:
zpool import -f -R /mnt tank

# Force-import recover pool (optional):
zpool import -f -R /mnt recover

# Confirm:
zpool status -v
zfs list -r tank
----

NOTE: `-R /mnt` re-roots all dataset mountpoints so the rescue environment's
own root is unaffected.

=== Step 7 — Inspect the NixOS system

[source,bash]
----
ls /mnt                         # bin → nix/store, boot, etc, …
ls /mnt/boot                    # EFI + loader entries
cat /mnt/boot/loader/loader.conf

# Which NixOS generation is the default:
ls -la /mnt/nix/var/nix/profiles/system*

# Last boot errors (if journal is on ZFS):
journalctl --directory=/mnt/var/log/journal -b -1 -p err
----

=== Step 8 — Enter the NixOS chroot environment

The NixOS system includes a `zfs-recovery-chroot` script (provisioned in both
minimal and full configurations) that automates the chroot setup. You can use
this script or perform manual chroot as described below.

==== Option A: Using the zfs-recovery-chroot script (Recommended)

[source,bash]
----
# The script is available in the mounted NixOS store:
find /mnt/nix/store -name "zfs-recovery-chroot" -type f

# Or from the system profile:
/mnt/nix/var/nix/profiles/system/bin/zfs-recovery-chroot

# The script handles:
# - Pool import with altroot
# - Network preservation (copies /etc/resolv.conf)
# - Automatic chroot via nixos-enter
# - Clean teardown on exit
----

.Script options
[source,bash]
----
zfs-recovery-chroot --help

Options:
    -p, --pool POOL         ZFS pool name (default: tank)
    -d, --dataset DATASET   Root dataset (default: tank/nerd)
    -r, --root PATH         Chroot root path (default: /mnt/zfs-root)
    -n, --no-network        Don't preserve network access
    -c, --cleanup           Only perform cleanup
    -h, --help              Show this help message
----

NOTE: If you've already imported the pool manually at `/mnt` (as in Step 6),
you can use `nixos-enter` directly (see Option B1 below) or re-import with
the script's altroot.

==== Option B1: Using nixos-enter (Manual)

`nixos-enter` is the NixOS-native way to enter a chroot. It automatically
handles all virtual filesystem mounts (`/proc`, `/sys`, `/dev`).

[source,bash]
----
# Preserve network configuration
cp /etc/resolv.conf /mnt/etc/resolv.conf

# Enter the NixOS environment
# nixos-enter handles /proc, /sys, /dev mounts automatically
nixos-enter --root /mnt

# Inside the chroot:
ls /nix/store | head
ls -la /nix/var/nix/profiles/system
----

==== Option B2: Using Traditional Chroot (Fallback)

[source,bash]
----
# Mount the EFI partition (adjust device to match lsblk output):
mount /dev/vda1 /mnt/boot    # vda is disk.img (root/EFI); adjust to match lsblk

# Preserve network configuration
cp /etc/resolv.conf /mnt/etc/resolv.conf

# Bind the virtual filesystems:
mount --bind /dev  /mnt/dev
mount --bind /proc /mnt/proc
mount --bind /sys  /mnt/sys

# Enter chroot:
chroot /mnt /bin/bash

# Inside the chroot:
ls /nix/store | head
ls -la /nix/var/nix/profiles/system
----

=== Step 9 — Common Recovery Tasks in Chroot

Once inside the chroot environment, perform recovery operations as needed:

==== Repair NixOS Configuration

[source,bash]
----
# Edit configuration files
nano /etc/nixos/configuration.nix

# Rebuild the system (creates new boot entry)
nixos-rebuild boot

# Or switch immediately (also updates running system if booted)
nixos-rebuild switch
----

==== Reset Root Password

[source,bash]
----
# Set a new password for root
passwd root

# Or unlock root account (if locked)
passwd -u root
----

==== Inspect System State

[source,bash]
----
# Check disk usage
df -h
zpool list
zfs list -r tank/nerd

# View system logs
journalctl -xe

# Check systemd services
systemctl list-units --failed
----

==== Network Troubleshooting

[source,bash]
----
# Test network connectivity
ping -c 3 1.1.1.1

# If DNS doesn't work, manually configure:
echo "nameserver 1.1.1.1" > /etc/resolv.conf
echo "nameserver 8.8.8.8" >> /etc/resolv.conf
----

==== Restore from ZFS Snapshots

[source,bash]
----
# List available snapshots
zfs list -t snapshot -r tank/nerd

# Rollback to a previous snapshot
zfs rollback tank/nerd/root@snapshot-name

# Or clone a snapshot to a new dataset
zfs clone tank/nerd/root@snapshot-name tank/nerd/root-recovered
----

==== Clean Up Disk Space

[source,bash]
----
# Remove old NixOS generations
nix-collect-garbage -d

# Delete old ZFS snapshots
zfs destroy tank/nerd/root@old-snapshot

# Check freed space
df -h
zpool list tank
----

=== Step 10 — Repair EFI boot entries with efibootmgr

Run from the _Debian rescue_ shell (outside the chroot) so `efibootmgr` can
write directly to the guest EFI NVRAM.

[source,bash]
----
apt-get install -y efibootmgr dosfstools

# List existing entries:
efibootmgr -v

# Delete a stale/broken entry (e.g. Boot0001):
efibootmgr -b 0001 -B

# Create a new entry pointing at systemd-boot on the boot disk (vda):
#   Disk: /dev/vda  Partition: 1 (EFI)  Loader: \EFI\systemd\systemd-bootaa64.efi
efibootmgr \
  --disk /dev/vda \
  --part 1 \
  --create \
  --label "Linux Boot Manager" \
  --loader '\EFI\systemd\systemd-bootaa64.efi'

# Set explicit boot order (put the new entry first, e.g. Boot0002):
efibootmgr --bootorder 0002,0001,0000

# Verify:
efibootmgr -v
----

NOTE: Changes are committed to the guest NVRAM file on disk (the EFI-vars
file `tart create` writes under `~/.tart/vms/nerd-nixos/`, canonically
`nvram.bin` — verify the exact name on your VM).  They take effect on the
next `nerd-nixos` boot.

=== Step 11 — Teardown

[source,bash]
----
# Exit chroot if open:
exit

# If using zfs-recovery-chroot script, it handles cleanup automatically
# Otherwise, manually unmount and export:
umount /mnt/boot /mnt/sys /mnt/proc /mnt/dev
zpool export tank
zpool export recover   # if imported

# Stop the rescue VM:
tart stop debian-rescue
----

NOTE: The `zfs-recovery-chroot` script automatically handles cleanup (unmount
virtual filesystems, export pools) when you exit the chroot.

=== Step 12 — Boot the repaired nerd-nixos VM

[source,bash]
----
# Start the VM via the generated run wrapper, then attach the serial console:
~/.tart/vms/nerd-nixos.sh
screen -r nerd-nixos
----

=== Cleanup — remove the rescue VM when no longer needed

[source,bash]
----
tart delete debian-rescue
----

== Reference: Tart operator surface

The Tart provider has no lifecycle-orchestrator script.  The operator surface
is a small set of flake apps plus the generated per-VM run wrapper:

[source]
----
nix run .#nerd-tart-vm-materialize
    Build the bringup image, create disk.img + tank/recover disks, write
    config.json and the run wrapper.  VM_FACTORY_RESET=true wipes + recreates.

nix run .#nerd-tart-<host>-deploy
    Copy the materialised bundle to a vz host and run the same activation there.

nix run .#nerd-tart-vm-bootstrap-installer -- [--vm N] [--repo P] [--iso P] [--tag T]
    Boot the VM in recovery mode with the installer ISO (:ro) and the repo
    mounted rw over virtiofs.  Requires the run wrapper to exist first.

~/.tart/vms/nerd-nixos.sh
    Generated run wrapper: `tart run` with the data disks, the SOPS host share
    (tag ndh-sops-age → /srv/host/sops.d), and optional serial/bridge/nested
    flags.  Serial is off by default; gate it with SERIAL_ENABLE / SERIAL_PATH
    / SERIAL_BRIDGE_ENABLE and reattach with `screen -r nerd-nixos`.

nixos-rebuild switch --target-host root@<host>-nixos.local
    Activate the guest from the build host (no wrapper; plain nixos-rebuild).
    zfs-bootstrap-activation runs automatically at first boot of the ZFS target.
----
