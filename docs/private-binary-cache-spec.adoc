= Private Binary Cache — build once, substitute everywhere
:toc: left
:toclevels: 3
:icons: font

**Status:** 📐 target architecture — decided 2026-10-10, amended 2026-10-11, not built +
**Scope:** how the seedmatic hosts stop rebuilding the same paths, and where those paths are kept

[NOTE]
====
This spec states the *target* only. The way there from today's state (each host builds, and a
`cachix watch-store` daemon published every new store path to the public `nxmatic` cache) is
described in the rke2lab migration atlas, `docs/architecture/atlas/fabric-control-plane.adoc`,
section _The private binary cache_.

Every figure marked *measured* was read on 2026-10-10 from store paths that already existed, or on
2026-10-11 in an isolated throwaway store. No flake of ours was evaluated to get it.
====

== Overview

The seedmatic hosts share most of one configuration, so they run mostly the same packages. Today
each host builds them again. The cache makes a path **built once and substituted everywhere**:

* **one builder**, bioskop, builds every host's configuration from a **pushed revision**, never from
  a working tree, and **sends** each host its closure (`nix copy`). The other hosts never build from
  source (see <<revisions-only>>);
* what the builder **trusts enough to publish** goes to the **public** `nxmatic` cachix. That covers
  an allow-list of named outputs, built and not added, which passed a content guard. The builder
  signs those paths with a publication key and pushes them itself (see <<public-private-split>>);
* **everything else** stays in the **private** cache: an **attic** server in an Incus container on
  bioskop, filled by an `attic watch-store` on every host, every read of which needs a token.

[cols="1,3",options="header"]
|===
| Property | What it gives

| One build per path
| The four host closures add up to 32 GiB, but their union is 15.7 GiB, and only 1.6 GiB of that union
is not already on cache.nixos.org (measured, see <<sizing>>). That 1.6 GiB is the part the hosts
rebuild today.

| The active session only
| The cache keeps what the current coding session needs, for a few hours, not a history and not
the previous day (see <<retention>>). It skips the paths whose signature says an upstream cache
serves them.

| Trusted paths public, the rest private
| The publication key marks a path as published. attic's upstream filter skips that key, so a
published path is never kept privately, and a path the builder did not publish is never served by
nobody (see <<public-private-split>>).

| Every host writes the private cache
| Each of the four hosts uploads to attic, with a write token of its own. The price is trust: attic
is as trustworthy as its least trusted writer (see <<trust-model>>). The clusters read the public
tier only, and hold **no** attic token: their nodes and workloads build through their nerd-nixos
builder (see <<cluster-builds>>, design only). The infrastructure containers hold none either.

| Private by authentication
| The cache is created **without** `--public`, so an anonymous request is refused (see
<<read-test>>). Listening on the fabric segment only, never on a public port, adds to that. It does
not replace it.
|===

The motive is the incident of 2026-10-10. A daemon pushed every new store path to the public cache.
On a machine whose git config smudge-decrypts sops files, evaluating a dirty rke2lab tree copies
`.secrets` and `.ndh-ssh.d/keys.yaml` in clear into the store, so 52 such copies became public. The
daemon was disabled on every host in `395b34a1`.

It is not only a dirty tree. Measured on 2026-10-11: **any** evaluation that names a decrypted
checkout (`.`, `.#x`, a bare `git+file://`) copies the files from disk, clean tree or dirty. Only a
revision read from git objects stays encrypted (see <<revisions-only>>).

This spec brings the cache back and narrows that shape in layers:

* the builder evaluates revisions only;
* only what it built from one, and not a path added from a tree, can be published;
* everything else stays behind a read token.

None of these proves a path's content clean. That is the job of the content guard on the way to
the public cache, and of an attic fork that refuses such paths at upload (see <<attic-fork>>).
Upstream of all of it: no plaintext on disk in a flake tree.

== Vocabulary

[cols="1,3",options="header"]
|===
| Term | Meaning

| *nerd-nixos*
| The Tart NixOS guest on a bare-metal (`bioskop-nixos`, `nikopol-nixos`). It hosts Incus. Its
`/nix/store` is an overlay of read-only EROFS layers over a ZFS upper.

| *Incus cluster*
| The one Incus service, which ndh configures as part of nerd-nixos. Its members are the two
nerd-nixos: `bioskop` (database leader) and `nikopol` (`database-client`), both online on
2026-10-10. It hosts the rke2lab cluster nodes (project `rke2lab`) and the infrastructure containers
below.

| *attic-nixos*
| The Incus container that runs attic. It exists **on bioskop only**.

| *headscale-nixos*
| The Incus container that runs headscale. There is one **on each bare-metal**; see
link:fabric-control-plane-spec.adoc[the fabric control plane].

| *Builder*
| bioskop: a dedicated fill job on the darwin host evaluates every host's configuration, and builds
the Linux parts on bioskop's nerd-nixos, its remote builder (see <<who-fills>>). No other host
builds from source.

| *Revision*
| A commit read from git objects: `github:seedmatic/{repo}/{sha}`, or
`git+file:///Volumes/git-bare-store/seedmatic/{repo}.git?ref=develop&rev={sha}` (host-registry id
`{repo}-bare/develop/{sha}`). Never a working tree (see <<revisions-only>>).

| *Publication key*
| `seedmatic-publish-1`, the signing key that means "the fill job built this from a revision, and it
passed the guard: publish it". It is **not** in `secret-key-files`. The fill job applies it
explicitly (see <<public-private-split>>).

| *Added path*
| A path that entered the store by `addToStore`, not by a build: a flake `-source`, a
`builtins.path`, a `builtins.toFile`, a sops-nix file. It has no deriver, and no key signs it.

| *Fill*
| One builder run: build from a revision, select and sign the paths to publish, push them to
cachix, send each host its closure, then keep the private remainder alive.

| *Public tier, private tier*
| `nxmatic.cachix.org`, readable by anyone, which holds only what the fill job published; and attic,
readable with a token, which holds everything else.

| *Read token*
| An attic token that can pull from the cache and nothing else. Every substituter of attic holds one
(see <<secrets>>).

| *Ours*
| A path that has no `cache.nixos.org-1` or flox signature in the local Nix DB.

| *Truly ours*
| A path that is ours **and** whose narinfo returns 404 on cache.nixos.org. Only these belong in the
cache.

| *Live set*
| The paths attic must keep while a session is active: for each host, the closure of its latest
built generation, minus what the public tier serves.
|===

[[who-fills]]
== Who fills the cache — every host, into one common cache

**Decided by the operator on 2026-10-10**, through the question prompt and with the price below in
front of them: an `attic watch-store` daemon runs on **each of the four hosts** (bioskop, nikopol,
bioskop-nixos, nikopol-nixos). Every host uploads what it builds, dev builds included.

The reason is the topology. bioskop-nixos is bioskop's Linux builder (`/etc/nix/machines` →
`ssh-ng://root@bioskop-nixos`), so it already receives the builds of bioskop's dirty trees. Whether
a dirty build lands on the dev seat or on its builder is a difference of degree, not of kind.

The builder still exists. It builds every host's configuration from a pushed revision, so that a
host's switch finds its closure already in the cache. What the hosts upload on top is what they
build themselves.

[IMPORTANT]
====
**Amended by the operator on 2026-10-11.** The watch-stores stay, and the cache gains a public
tier above them:

* **the other hosts never build from source**: bioskop builds and **sends** each host its closure,
  with `nix copy --to ssh-ng://nix-store.{host}` under the existing `nix-store` identity (see
  <<revisions-only>>);
* what the fill job trusts enough to publish goes to the public `nxmatic` cachix, and the
  watch-stores fill attic with **everything else** (see <<public-private-split>>).

So attic is the **private tier**: the hosts' own builds, dev builds included, and whatever the fill
job built but did not publish.
====

[cols="1,3",options="header"]
|===
| | What the decision gives, and what it costs

| Gain
| every build on any host is shared, dev builds included: the most the cache can do for "build once"

| Price — trust
| a write token on every host, so the cache is as trustworthy as the **least trusted of the four
writers** (see <<trust-model>>), and tokens that cannot yet be revoked one by one, so a single loss
means rotating them all (see <<write-tokens>>)

| Price — the corporate side
| the write token inside nikopol, the darwin VM that runs on the corporate bare-metal (see
<<trust-model>>)

| Price — exposure
| every dev seat's dirty evaluations reach the cache, confined by authenticated reads (see
<<watch-store-sees>>)
|===

[[write-tokens]]
=== One common cache, one write token per host

**Decided by the operator on 2026-10-10**: one common cache, `seedmatic`, and **a write token per
host**, each with its own subject. attic issues as many tokens for one cache as needed:

[source,bash]
----
atticadm make-token --sub bioskop       --validity "3 months" --pull seedmatic --push seedmatic
atticadm make-token --sub nikopol       --validity "3 months" --pull seedmatic --push seedmatic
atticadm make-token --sub bioskop-nixos --validity "3 months" --pull seedmatic --push seedmatic
atticadm make-token --sub nikopol-nixos --validity "3 months" --pull seedmatic --push seedmatic
----

What a per-host token does **not** give yet is revocation of that host alone. attic's tokens are
**stateless JWTs**: the server checks a token's signature and expiry, and keeps no list of issued
tokens (attic `token/src/lib.rs:3-12`: _"simple and stateless […] We may revisit this later"_).
Ending one token means rotating the server secret (`ATTIC_SERVER_TOKEN_RS256_SECRET_BASE64`), which
ends every token, reads included, or waiting for its expiry. Revoking one host alone is left to a
later contribution to attic (see <<attic-fork>>). Access control is already far better than the
public cache.

[cols="1,3",options="header"]
|===
| A host's write token | Rule

| subject
| the host's name (`--sub {host}`), so that each token belongs to one host and none is shared

| scope
| `--push seedmatic` (plus `--pull seedmatic` for the keep-alive), nothing else: no `create-cache`,
`configure-cache`, `delete` or `destroy-cache`

| validity
| bounded (`--validity`, three months in the example), re-issued on a schedule. Until the
contribution, the validity is the only bound on how long a lost token keeps pushing. The value is
open below.

| a host is lost or compromised
| rotate the server secret, then re-issue every other host's write token and every read token (see
<<secrets>>)
|===

Considered and not chosen: a cache per writer. It would make a single host revocable (destroy its
cache) and give each writer its own signing key, at no disk cost, since attic deduplicates NARs
across caches. The operator kept one common cache.

[[watch-store-sees]]
=== What a host's watch-store uploads

The daemon watches the whole store, not the fill. Read in attic `client/src/command/watch_store.rs`
at `7a19204d`:

* when a path becomes valid, the daemon skips it if its name ends in `.drv` or `-source`. That is a
  test on the **name**, done once, when the path appears;
* for every path it keeps, it pushes the **closure** by default (`--no-closure` is a hidden flag).
  An output that references a flake source therefore carries that source, whatever its name.

With a daemon on every host, these origins all reach the cache:

[cols="1,1,2",options="header"]
|===
| Host | Origin | What lands in the cache

| every host
| its own builds
| the outputs of whatever it builds, dirty trees included. A dirty evaluation's `-source` copy,
plaintext included, is skipped by name, but an output that references one carries it in its closure.

| bioskop-nixos, nikopol-nixos
| the dev seats' remote builds (`ssh-ng`, `/etc/nix/machines` on the darwin hosts)
| the outputs of derivations their darwin host evaluated, dirty trees included

| bioskop-nixos, nikopol-nixos
| the cluster nodes' and pods' remote builds (see <<cluster-builds>>)
| what the nodes and their workloads build, the flox controller's realisations and unknown packages
included. Inputs are accepted only signed or content-addressed (see <<builder-tests>>).

| bioskop, bioskop-nixos
| the fill job
| what the fill job built but did not publish, plus a copy of what it did, by the race (see
<<public-private-split>>)
|===

This is **accepted under authenticated reads**. A plaintext copy that reaches the cache can be read
only by a holder of a read token, all of which are machines of the fabric (see <<secrets>>). It is
not fixed by them. The fix is the fork in <<attic-fork>>.

=== The darwin paths need a darwin builder

nerd-nixos is Linux, and some of the darwin hosts' paths exist only on darwin. Measured on the two
darwin system closures:

[cols="2,1",options="header"]
|===
| Darwin "ours" paths | Size

| shared by bioskop and nikopol | 0.97 GiB
| bioskop only | 0.20 GiB
| nikopol only | < 0.01 GiB
| of which truly ours (not on cache.nixos.org) | 0.78 GiB
|===

The two darwin hosts overlap almost completely, so **one Mac builds both**, and that Mac is bioskop.
nix-darwin builds `darwinConfigurations.nikopol.system` on any `aarch64-darwin` machine, and nikopol
is a guest on a foreign, MDM-managed bare-metal.

bioskop is also the dev seat, so the darwin fill does not run in the operator's session. It is a
dedicated launchd job:

* it runs under its own user, with its own fetcher cache (see <<revisions-only>>);
* it evaluates a revision, with `--option allow-dirty false` on its own command line;
* it holds no attic token, but the only cachix push token and the publication key: what it
  publishes goes to cachix, and bioskop's watch-store uploads the rest to attic.

The operator's `nix.conf` keeps `allow-dirty` at its default, because a global `false` would break
the Maven build of manifests-core (`nix run .#stage-*-crd`) and the whole dev loop.

[[public-private-split]]
== The public and the private tier — what the builder trusts goes public

**Decided by the operator on 2026-10-11.** The paths the fill job trusts go to the **public**
`nxmatic` cachix; everything else stays in the **private** attic. One signature does both jobs: it
lets a path through to the public tier, and it keeps that path out of the private one.

=== What makes a path publishable — the closure rule

`cachix push` uploads a path **and its closure**, so a path cannot be judged alone: a built output
that references an added `-source` at run time would drag that source to the public cache. A path
is publishable only if **every** path of its runtime closure is either already served by an upstream
public cache (a narinfo on cache.nixos.org or a flox cache answers 200), or itself meets all four
conditions:

[cols="1,3",options="header"]
|===
| Condition | Why

| in the closure of an output on the **allow-list**
| publication is a decision per named output, never "whatever was built"

| **built**, not added: it has a deriver
| an added path is a copy of something on disk, a flake `-source`, a sops-nix file, the ndh-ssh tree.
Measured on 2026-10-11: 15 of 15 added paths in bioskop's closure have no deriver, and no
`secret-key-files` key ever signs one (see <<signature-scope>>)

| built **from a revision**
| the fill job evaluates nothing else (see <<revisions-only>>)

| passes the **content guard**
| no private-key armour with a body, no `AGE-SECRET-KEY-1`, no JWT, no `tskey-`, `gh[opsu]_`,
`github_pat_`, `dckr_pat_` or `glpat-` shape outside an `ENC[` value (the shapes of rke2lab's
`.githooks/pre-commit` `token_shape_guard`), and no `# sops:encrypted` annotation followed by
anything but `ENC[`
|===

=== One signature for both tiers — the publication key

[cols="1,3",options="header"]
|===
| Step | Rule

| the key
| `seedmatic-publish-1`, generated with `nix key generate-secret`, its secret half sops-encrypted in
ndh and decrypted for the fill job's user only. **Never in a flake tree, never in
`secret-key-files`**

| signing
| `nix store sign --key-file {key}` over the publishable set only, after the build. Applied like the
layer key, by a step, never by the daemon

| the private tier's filter
| `seedmatic-publish-1` joins attic's `upstream-cache-key-names`, so a watch-store skips a path once
it is published. `nxmatic.cachix.org-1` joins it too, for paths substituted from the public tier

| the public tier's signature
| `nxmatic` is a cachix-**managed** signing cache: ndh holds its push token
(`cachix.nxmatic.token` in `.secrets`), not its private key. A published path therefore carries
`seedmatic-publish-1` **locally** and `nxmatic.cachix.org-1` on the narinfo cachix serves
|===

Which key is checked where:

[cols="1,2",options="header"]
|===
| Key | Checked by

| `nxmatic.cachix.org-1`
| every consumer of the public tier, in `trusted-public-keys`: the hosts and the clusters

| attic's cache key
| the hosts, in `trusted-public-keys`, for the private tier

| `seedmatic-publish-1`
| **nobody's** `trusted-public-keys`. It is read only locally, by attic's upload filter, as a
key name. It proves nothing to a consumer, and no consumer needs it
|===

[[signature-scope]]
=== What `secret-key-files` signs — measured, and why the key is not there

Measured on 2026-10-11 (nix 2.34.8):

* **in an isolated store** (its own store root, `HOME` and `XDG_CACHE_HOME`, a throwaway key, no
  substituters): a `builtins.path`, a `builtins.toFile`, a flake `path:` source and a
  `nix store add-path` receive **no** signature, only their `ca:` field. `nix store sign` on the
  same path works, so the key was read;
* **in bioskop's store**, 396 paths created since 2026-10-09: 69 of 69 built locally are signed by
  `io-nxmatic-nix-darwin-home`, 0 of 210 added paths are;
* fixed-output outputs (fetchers) are content-addressed too, but they have a deriver and are signed
  like any build.

And `secret-key-files` is **daemon-wide**. A publication key placed there would sign the operator's
dirty dev builds on bioskop, and the dirty remote builds bioskop-nixos receives. A built output that
copies `${self}` content into `$out` would be signed. So the key is applied by the fill job, never
by the daemon.

=== The limits

[cols="1,3",options="header"]
|===
| Limit | What it means

| the race
| a watch-store judges a path once, when it becomes valid, which is **before** the fill job signs
it. On bioskop and bioskop-nixos a fill output therefore also reaches attic. Harmless: a copy of
public content in the private tier, which the short retention removes

| publishing is final
| a public path may be copied or indexed even after a purge. The content guard is the last line. A
signature attests content, not how it was evaluated: a built output that copies `${self}` content
passes if the guard misses it. So <<revisions-only>> stays mandatory

| the cost
| the public tier counts against cachix's storage quota (the free plan's, to read on the account),
and every public path needs the internet

| the stale signatures
| about a hundred local paths still carry an `nxmatic.cachix.org-1` signature from before the purge.
attic's filter skips them, and cachix no longer serves them, so they are served by nobody until a
fill re-publishes them or a host rebuilds them
|===

[[cluster-builds]]
== The clusters write and read through their builder — design only

**Decided by the operator on 2026-10-10.** Cluster nodes and their workloads write to the cache
**through the remote builder**: the nerd-nixos of the node's own bare-metal, which has the same
architecture (bioskop-nixos for bioskop's clusters, nikopol-nixos for nikopol's). A node or a pod
does not build: it delegates (`max-jobs = 0`, `builders = ssh-ng://…`). The builder's watch-store
then uploads the result with that host's token. With `builders-use-substitutes = true`, the same
builder substitutes from attic on their behalf.

So **no attic token reaches a cluster**, neither read nor write. The four hosts remain the only
holders. What the clusters hold instead is a way to reach their builder (see <<secrets>>). Their
own substituters are the public ones only: cache.nixos.org, the flox caches and the public tier.
What they need from us is therefore what the allow-list must name (see <<public-private-split>>).

⚠️ **Design only today.** Measured on 2026-10-10: nothing declares `builders`, `max-jobs` or
`builders-use-substitutes`, neither rke2lab's `nixos/*.nix` nor flox-nri-plugin. The node-base nix
configuration that must carry them is **rke2lab's side**: it is a rke2lab follow-up, not something
this spec implements.

[[revisions-only]]
=== The builder evaluates revisions only — and with its own fetcher cache

**A hard rule, measured by develop-2a on 2026-10-11 (nix 2.34.8, a fresh store per case).** On a
machine whose git config smudge-decrypts sops files, **any** evaluation that names a checkout copies
its files from disk into the store, decrypted, **clean tree or dirty**. That covers `.`, `.#x` and a
bare `git+file://{worktree}`. Only a reference to a **revision** reads git objects, so the secrets
stay encrypted:

[source,bash]
----
# ✅ revisions — git objects
github:seedmatic/{repo}/{sha}
git+file:///Volumes/git-bare-store/seedmatic/{repo}.git?ref=develop&rev={sha}
{repo}-bare/develop/{sha}          # the same, by its host-registry id
# ❌ a working tree, clean or dirty
.   .#x   git+file://{worktree}
----

**The source-cache trap.** nix's fetcher cache keys a commit's source by its revision, and the
**first** evaluation wins. One `nix build .#x` in a decrypted worktree records a plaintext copy for
that revision, and every later evaluation of the same commit, by `?rev=` or by the bare repository,
reuses it as `${self}`. A revision reference is therefore safe only with a fetcher cache that no
worktree evaluation ever wrote. So:

. the fill job runs under its **own user**, with its own `XDG_CACHE_HOME`, which no operator
  session and no worktree evaluation shares;
. it evaluates only revisions, with `--option allow-dirty false` on its command line as a second
  lock;
. **no other host builds from source.** bioskop builds and sends each host its closure,
  `nix copy --to ssh-ng://nix-store.{host}`, under the existing `nix-store` identity. A host's
  switch then finds every path already local, added paths included. The receiving daemon accepts
  the copy without trusting the sender: the built paths carry `io-nxmatic-nix-darwin-home`, which
  every host of the fleet already trusts, and the added paths are content-addressed, which nix
  accepts without a signature.

The detector, while a worktree on disk is decrypted: a sweep of the store for new `-source` copies
of a seedmatic tree, `find /nix/store -maxdepth 1 -newerct {absolute date}`. Then count, never
print: `grep -c 'ENC\['` on its sops files, compared with the committed blob.

=== A build client cannot write into the builder's store — on three settings

A build over `ssh-ng` copies paths into the builder, and the builder's watch-store then uploads
whatever is in its store, signed by attic. If a node could import an arbitrary path there, it would
poison the cache without holding any token. Read in nix 2.34:

* for a client it does not trust, the daemon **forces signature checking** on every import
  (`src/libstore/daemon.cc:505-506`, `:907-908`). An unsigned, input-addressed path is refused;
* the daemon refuses an untrusted client's `buildDerivation` of an input-addressed derivation
  (`daemon.cc:632-633`: _"you are not privileged to build input-addressed derivations"_);
* `build-remote` handles that case: when the builder does not trust the client and the derivation
  is input-addressed, it copies the `.drv` closure, which is content-addressed and so accepted, and
  asks for `buildPaths` instead (`src/nix/build-remote/build-remote.cc:300-340`). **The builder
  computes the outputs itself.**

So, with these three settings on nerd-nixos:

. the build clients (nodes, pods) are **not** in `trusted-users`;
. `require-sigs = true` (nix's default, stated so that nobody turns it off);
. their input paths are signed by a trusted key or content-addressed.

[mermaid]
....
sequenceDiagram
  autonumber
  participant N as Node or pod (not a trusted user)
  participant B as Its builder ({host}-nixos)
  participant U as cache.nixos.org, attic
  participant W as watch-store on B
  participant A as attic-nixos
  N->>B: copy the .drv closure — content-addressed, accepted
  N->>B: buildPaths of the derivation
  B->>U: substitute the outputs if a cache has them
  B->>B: otherwise build them itself
  B-->>N: copy the outputs back
  W->>A: upload what B realised, with B's own token
  N-xB: nix copy of an unsigned input-addressed path
  Note over N,B: refused — the daemon forces signature checks<br/>on an untrusted client
....

A node can then only **request builds of derivations**. The builder computes or substitutes the
outputs, and nothing a node supplies reaches the cache unchecked. That is what makes this better
than a write token in the clusters, and **it holds only with these settings**: one build client in
`trusted-users`, and the property is gone.

One gap remains. A node gets **by build** only what it has the derivation for. A flox package
locked by its store path is **substituted**, not built. If it comes from cache.flox.dev or
cache.nixos.org, nothing more is needed. If only attic holds it, there are two ways:

* a read token on the node, which this design avoids;
* the builder as a substituter: `substituters = ssh-ng://{host}-nixos` with `require-sigs = true`.
  An untrusted client can substitute that way, as long as the path carries a key the node trusts.
  The builder serves only what **its own** store holds, and its own builds are signed with
  `io-nxmatic-nix-darwin-home`, not by attic, so that is the key the node must trust. Unverified;
  test 3 below.

[[builder-tests]]
=== The tests the implementation must pass — the builder

These sit next to <<read-test>>. Together they decide whether "the clusters hold no attic token"
holds.

[cols="1,2,2",options="header"]
|===
| Test | Gesture, from a node that is not a trusted user | Expected

| 1 — an untrusted client gets a build
| `nix build` of an input-addressed derivation, delegated to `ssh-ng://{host}-nixos`
| the build succeeds, through `build-remote`'s `buildPaths` path, and the output is computed by the
builder

| 2 — an untrusted client cannot import
| `nix copy --to ssh-ng://{host}-nixos {an unsigned, input-addressed path}`
| refused, for lack of a trusted signature

| 3 — an untrusted client substitutes, signed only
| with `substituters = ssh-ng://{host}-nixos`, realise a path the builder signed, then one it did not
| the signed path is substituted, the unsigned one is refused
|===

If test 1 **fails**, the design keeps no hole. It falls back to one of two shapes:

[cols="1,2,2",options="header"]
|===
| Fallback | What it is | Its cost

| A — content-addressed derivations
| what nodes build is content-addressed (nix's experimental `ca-derivations`). The builder builds it
for an untrusted client, and the outputs are checked by content, so nothing a node supplies is
taken on trust.
| maturity and coverage: the feature is experimental, and most of nixpkgs is input-addressed

| B — nodes never build ✅ (the default if test 1 fails)
| everything a node or a pod needs is built ahead by the host builder, from pushed commits, and
uploaded. Nodes and pods only substitute. It is the shape this spec already uses for the hosts'
closures, extended to the clusters.
| a workload that needs an unplanned build **fails** until the builder has built it. The gain: the
poisoning question disappears entirely.
|===

B is the default because it needs no experimental feature and fits the trust model.

[[trust-model]]
== Trust model — the cache is as trustworthy as its least trusted writer

This is a fact of the design, not a footnote. It applies to the **private** tier. The public tier
has one writer, the fill job, which builds from revisions only (see <<revisions-only>>) and
publishes only what passes the closure rule (see <<public-private-split>>).

attic signs, with **the cache's** key, every path a writer uploads. For an input-addressed path,
which most outputs are, nothing proves the uploaded content is what the derivation would produce.
Any writer can publish **arbitrary content under any input-addressed path**, and every consumer
accepts it, signed by attic. Content-addressed paths, such as a `-source`, are the exception: their
name is derived from their content, so a substitute for one cannot be swapped. With a write token on
four hosts, the cache is therefore exactly as trustworthy as the **least trusted** of the four.

[cols="1,3",options="header"]
|===
| Writer | What its token puts at stake

| bioskop, bioskop-nixos, nikopol-nixos
| a writer of the fabric: a compromise of any one of them can poison what all the others substitute

| nikopol
| its own write token (`--sub nikopol`) **inside the darwin VM that runs on the corporate
bare-metal**. It sits next to the fabric rule that the corporate machine holds no key. The token
lives in the VM, not on the bare-metal, and is scoped to pushing to `seedmatic` with a bounded
validity. It is nikopol's alone, but until attic can revoke one token, losing it still means
rotating every token (see <<write-tokens>>).
|===

**The plaintext the private tier accepts.** With a watch-store on every host, a plaintext
`-source` produced by one slipped `.#x` on bioskop lands in attic. It is an added path, so no key
signs it and `upstream-cache-key-names` never skips it. That is the risk the operator accepted on
2026-10-10, under three bounds: the tier is private, every read needs a token, and the retention is
short (see <<retention>>). It is detected, not prevented, by the store sweep of
<<revisions-only>>, and prevented only by the fork (see <<attic-fork>>). The public tier never
receives such a path: the closure rule refuses it.

What would restore the trust, neither of which this spec builds:

* a **content check at upload**, so that a writer cannot publish what the server rejects. That is
  the fork, <<attic-fork>>;
* **per-writer signing keys that consumers can tell apart**, so that a consumer trusts some writers
  and not others. attic gives one key per cache, so this means a cache per writer, which the operator
  did not choose (see <<write-tokens>>).

=== The upstream filter — signatures, for the watch-store and the push alike

attic's filter is a setting **of the cache**, on the server: `upstream-cache-key-names`. Both
`watch-store` and `push` read it. For each path of the closure, the client reads the path's
signatures **from the local Nix DB**, splits each at the `:`, and drops the path if the key name is
in the list. It asks no upstream server (attic `client/src/push.rs:449-466`).

The list is `cache.nixos.org-1`, `flox-cache-public-1`, `floxhub-1`, the layer key below, and the
two keys of the public tier: `seedmatic-publish-1` and `nxmatic.cachix.org-1` (see
<<public-private-split>>). It is **not** ndh's `trusted-public-keys` as they stand:

[cols="1,3",options="header"]
|===
| Key name | Why

| `io-nxmatic-nix-darwin-home` — out
| the fleet's own key, in `secret-key-files`, so nix signs **every local build** with it (about 1170
of our paths carry it, measured). In the list, it would leave the cache empty.

| `nxmatic.cachix.org-1` — in, since 2026-10-11
| the public tier is fed again, by the fill job only. A path substituted from it carries that key and
needs no private copy. The price: about a hundred local paths still carry it from before the purge
(690 of 690 truly-ours paths answered 404 after it), and those are served by nobody until a fill
re-publishes them.

| `seedmatic-publish-1` — in
| a path the fill job published carries it locally, before any consumer substitutes it from cachix
|===

The filter misses what upstream serves but no local signature says: **297 paths (0.66 GiB)** across
the four host closures. On bioskop-nixos, 96 of its 289 such paths are in the EROFS layers,
registered from `closureInfo` without signatures (`nix-store --load-db`,
`modules/nixos/bringup-disk-image-common.sh:131`). The others were built locally. They cost disk,
not a leak. No uploader can query upstream before uploading until the fork.

=== Excluding the EROFS layers' own paths — a layer key

A path that is in the layers is already on every consumer that mounts them, so it should not be
uploaded. Paths substituted from upstream into the layers would be excluded by their signature, if
the registration kept it. The paths **we** built into the layers carry only
`io-nxmatic-nix-darwin-home`, like every other build of ours. A key of their own separates them:

. **a dedicated key**, `nerd-erofs-layers-1`. It is generated with
  `nix key generate-secret --key-name nerd-erofs-layers-1`, and its secret half is sops-encrypted
  in ndh. It must **never** be in `secret-key-files`, or every build would be signed with it and
  excluded;
. **sign the layers only**, when their lower DB is generated, once per layer set: load the
  registration into a scratch store, then run
  `nix store sign --store 'local?root={scratch}' --key-file {key} --recursive {layer roots}`. That
  signed DB ships with the layers. ⚠️ This is a step on the builder, **not** a derivation: in a
  derivation, the secret key would enter the store, and from there the cache;
. **carry the signatures to nerd-nixos's own DB**, which is loaded from the unsigned registration
  today. Right after the load, `nix store copy-sigs -s 'local?root={signed lower}' -r {roots}`
  imports them without the secret. That `copy-sigs` accepts a local store as its source is to verify;
. **add `nerd-erofs-layers-1` to `upstream-cache-key-names`.** No fork is needed: attic compares
  key names only (`push.rs:449-466`). A real signature still proves where the path came from.

....

The upstream paths inside the layers can be signed with the layer key too, so that everything in a

Measured on bioskop-nixos, the gain is small today: 115 of its 611 ours paths are in the layers,
and the running generation is not, because the layers predate it. The key prevents duplicates; the
delta since the layers is what the cache is for.

=== The secret guard — no step left to run it in, so it is the fork

Every host's system closure already carries sops files **by design**: sops-nix puts the encrypted
file in the store. Measured, by counts only: `ndh-.secrets` (16 `ENC[` values), `keys.yaml` (10
`ENC[`, no `PRIVATE KEY` marker, its 77 plain values are public by design) and `cache-trust.yaml`
(2 `ENC[`). So a guard must judge **content, not names**. It would refuse a path that holds:

* a `# sops:encrypted` annotation followed by anything but an `ENC[` value (the rule of
  <<attic-fork>>);
* a private-key armour header followed by a body;
* a GitHub token shape (`gh[opsu]_…`, `github_pat_…`).

For the **public** tier it runs in the fill job, before signing, as the fourth condition of the
closure rule (see <<public-private-split>>). For the **private** tier, a watch-store on every host
leaves no push step to run it in, and attic offers no hook. So there the guard **is** the fork.

[[retention]]
== Retention — the active session, not a history

=== What attic actually does

Read in attic's source at `7a19204d` (2026-07-06), not taken from the usual summary:

[cols="1,3",options="header"]
|===
| Fact | Source

| An object is collected when **both** `created_at` and `last_accessed_at` are older than the
retention period.
| `server/src/gc.rs:108-123`

| Only a **NAR download** bumps `last_accessed_at`. A narinfo lookup does not.
| `server/src/api/binary_cache.rs:212` (bump) and `:115-160` (narinfo, no bump)

| A retention of **0 disables GC**, and 0 is the default.
| `gc.rs:95`, `config.rs:561-563`

| Re-pushing a path the cache already holds never reaches the server, so it refreshes nothing.
| `client/src/push.rs:478-484`

| There is **no pinning and no single-path delete**. The only DELETE destroys a whole cache.
| `server/src/api/v1/mod.rs:10-37`

| `attic cache configure` **without** `--retention-period` resets the cache's retention to the
global default.
| `client/src/command/cache.rs:225-229`

| On SQLite, a GC run reaps at most **500 chunks**; on PostgreSQL, 65535.
| `gc.rs:178-190`
|===

=== How "the active session only" is obtained

**Decided by the operator on 2026-10-11**: the private tier only has to stay in step **while a
coding session is active**. A slower restart after a pause is accepted, and no generation of the
previous day is kept. Since nothing can be pinned or deleted path by path, that is **a short
retention period plus a keep-alive**:

. per cache, `retention-period = 6 hours` (proposed, in the order of magnitude the operator set). It
  is set in the same declarative step as every other cache setting, so a later `configure` cannot
  reset it silently;
. at the end of every fill, the fill job **downloads the NAR** of every path of the private live set.
  It uses a plain HTTP GET of the narinfo's `URL`, because it already holds those paths locally and
  nix would never substitute them. A host substituting a path bumps it the same way;
. a path nobody fills or substitutes for 6 hours is collected at the next GC run, within 15 minutes.
  After a longer pause, attic holds nothing of the previous session: the first fill of the next one
  refills it, and that is the slower restart the operator accepted;
. a published path is not kept alive in attic. The public tier serves it, under cachix's own
  retention (see <<public-private-split>>).

[mermaid]
....
stateDiagram-v2
  [*] --> Uploaded: created_at set
  Uploaded --> Live: a fill or a substitution downloads its NAR
  Live --> Live: last_accessed_at bumped
  Live --> Idle: the session pauses, or a newer generation
  Idle --> Expired: 6 hours without a download
  Expired --> Orphaned: GC deletes the object, within 15 minutes
  Orphaned --> Reaped: no NAR or chunk holder left
  Reaped --> [*]: disk freed
....

An idle path goes back to _Live_ as soon as a fill or a host downloads it again. The disk is freed
only at the last step, which is why the GC cadence matters: SQLite reaps at most 500 chunks per GC
run.

[cols="1,3",options="header"]
|===
| Guarantee | Holds when

| a host never loses its running closure
| always: the fill job sends it with `nix copy` (see <<revisions-only>>), so it is local and needs
no cache

| a host re-substitutes from the private tier
| within 6 hours of the last fill or substitution of the path. After that, the next fill refills it
|===

=== GC cadence and database — SQLite, a GC every 15 minutes

attic runs **no database service of its own**. `atticd` keeps its metadata (caches, objects, NARs,
chunks, the GC's dates) in the database named by `[database] url`. The nixpkgs module's default is a
SQLite **file**, `sqlite:///var/lib/atticd/server.db`; PostgreSQL is an option, which attic's
template recommends for production (`server/src/config-template.toml:44`).

What decides is the GC's reap rate. On SQLite a run frees at most **500 chunks**, on PostgreSQL
65 535 (`gc.rs:178-190`). With a retention of hours, every session restart re-uploads the set that
expired during the pause, so the worst case is **one full set reaped per day**. One full set of
truly-ours paths is at most about 2.2 GiB of NAR (see <<sizing>>), roughly 36 000 chunks at
FastCDC's 64 KiB average:

[cols="1,1,1",options="header"]
|===
| GC interval on SQLite | Chunks reaped per day | Against one set a day (≈ 36 000)

| 12 hours (default) | ≈ 1 000 | no: the disk grows without bound
| 1 hour | ≈ 12 000 | no
| **15 minutes** | **≈ 48 000** | **yes, 1.3 times the need**
| 10 minutes | ≈ 72 000 | twice the need
|===

The margin at 15 minutes is thin against that upper bound, and wide in practice: the public tier
takes the packages (measured on bioskop, 341 of the 343 MiB we build), so attic reaps only the private
remainder and the dev builds. Watch the dataset's `used`, and shorten the interval if it climbs.

**Decided by the operator on 2026-10-10: SQLite, with `[garbage-collection] interval` at 15
minutes.** No database service is added; the SQLite file lives in the cache's dataset.
PostgreSQL (nixpkgs `services.postgresql`, 65 535 chunks per run) is the fallback, if write
contention appears. Four watch-store daemons and a frequent GC writing to one SQLite file could
answer _database is locked_; that is unverified.

| in-flight generation | a bump during a session replaces nearly the whole set: one more L~c~ | 0.57
| superseded tail | none: nothing outlives the session (see <<retention>>) | 0
| *steady-state worst case* | 2 × L~c~ | *1.15 + 0.52 U*
|===

The public tier then takes most of L out of attic. On bioskop's system closure, 341 of the 343 MiB we
build is publishable (see <<public-private-split>>). What stays private is the aggregates, the added
paths no upstream serves, and the dev builds. The four hosts' split is not measured yet.

Two things are deliberately left out:

* chunk dedup between successive versions of the same package, which only makes the real figure
  smaller;
* the SQLite file's footprint, for which attic publishes no guidance. It is small next to the chunks:
  one row per chunk and per object.

Measured on 2026-10-14 on the probe (attic `7a19204d`, the module's default chunking, zstd): one
`attic push` of a 572-path closure, 1260 MiB of NAR before the upstream filter, left **496 MiB** of
storage in 17 492 chunk files and a **4.4 MiB** SQLite file. The push also uploaded paths that
cache.nixos.org serves, such as `gcc-lib` and `incus`: they reached the probe's store through the
layers' registration, which carries no signature, so the upstream filter did not recognise them. That
is the 297-path, 0.66 GiB share measured on 2026-10-10, and it inflates the private tier until the
layers' paths carry their upstream signatures.

=== Quota — open until the split is measured

A dataset `tank/nerd/attic`, holding the chunk storage and the SQLite file. Two sizes are on the
table: **16G** or **about 8G**. Both are well above the upper bound (1.15 GiB + 0.52 U). The open
variable is U, the unmeasured package outputs and cluster closures, together with how much of them
the public tier takes. The operator decides once the public/private split is measured on the four
hosts.

It sits next to the other `nerd/*` datasets declared in `modules/nixos/zfs-disko-config.nix`, and is
passed to attic-nixos as an Incus disk device, mounted at `/var/lib/private/atticd`. The nixpkgs
module runs atticd under `DynamicUser`, and systemd hands ownership to its `StateDirectory` only. It
is **not** replicated to the `recover` pool, because a fill can refill the cache from scratch. The
signing key does not live on it (see <<secrets>>).

[[container-store]]
== The containers' `/nix/store` — an overlay on nerd-nixos's EROFS lowers

Both attic-nixos and headscale-nixos mount their `/nix/store` as an overlay **from the start** (the
operator's choice: there is no plain-store first increment). The lowers are the EROFS layers that
nerd-nixos already mounts. The upper is a per-container ZFS dataset. The containers' system closures
therefore overlap nerd-nixos's, and the upper receives only the **delta**. Implemented by
`modules/nixos/incus-nixos-container.nix`.

| Rule | Why

| the store overlay's lowers are the **EROFS layers, flat**, never nerd-nixos's merged `/nix/store`
and never an overlay of the layers
| the merged store changes as nerd-nixos activates generations, and in OverlayFS a lower that
changes while mounted is undefined. And an overlay as lowerdir mounts, but the kernel silently
falls back to `index=off` ("does not support file handles"), which loses the ESTALE refusal of a
changed lower. Measured on bioskop-nixos on 2026-10-11 (kernel 6.18.55): flat lowers keep
`index=on`

| one **layer contract**, `/etc/ndh/store-layers.json`, rendered by `erofs-store-mount.nix`
| the ordered lowerdirs (newest first, `.003:.002:.ro-store`) and the options a consumer must find
on its mount. A second, hand-written list would drift. The flox NRI plugin's pod stores are a
candidate second consumer

| the store unit **asserts** the effective mount against the contract and fails hard
| it replaces nix's `check-mount`, which must be off: nix wants lowerdir to be the lower store's
single directory, and flat lowers are three

| nix's lower store is a separate **read-only metadata view**: an overlay of the layers plus a shim
holding an empty `.links`, and a DB
| nix reads paths and metadata there, never through overlayfs. The shim: nix 2.34 creates `.links`
even in a read-only store (`src/libstore/local-store.cc:139`), and the layers carry none

| the view's DB is generated **at runtime, once per layer set**, keyed by a fingerprint of each
layer's paths and of the layers' order, from nerd-nixos's own DB (`nix-store --dump-db` then
`--load-db`)
| decided by the operator on 2026-10-11. Not shipped with the layers: the running generation cannot
name the layers' union closure, which holds its own toplevel (`unionClosureInfo` in
`bringup-zfs-disk-image.nix`). Measured: 1842 paths

| the container's `/nix/var/nix` lives on its dataset, beside the upper
| nerd-nixos then delivers into the container's store with a host-side `nix copy`, no SSH needed

| the view enters the container as **two plain read-only binds**, its store and its DB
| the view's store is a mount of its own, and the kernel refuses a recursive read-only bind
("Recursive read-only bind-mounts aren't currently supported by the kernel", measured 2026-10-14)

| the store unit runs **only once the container's dataset is mounted**
| `create` makes the dataset, and zfs-mount mounts it, not a mount unit, so `RequiresMountsFor`
cannot wait for it. Without the condition the unit ran at first boot on the root fs, and the dataset
then hid that upper (measured 2026-10-14)

| the host-side store URL names the **resolved** view, never `.lower/current`
| nix refuses a symlink on a store path or its parents

| an extra device states its **`type`**, and never targets `/run` or `/tmp`; both are asserted at
evaluation
| Incus wants the type positionally and refuses it among the keys ("Unsupported device type"); the
container's systemd mounts tmpfs on `/run` and `/tmp` at boot, over the device (attic's environment
file at `/run/attic` was simply not there, 2026-10-14)

| a device's **source must exist before Incus autostarts** the instance
| a missing source fails the autostart three times, then gives up ("Missing source path", measured
after a reboot of the probe). sops-nix decrypts into `/run/secrets` during activation, before any
service, so a sops secret qualifies; a file written by a later service would not

| the containers' firewall is **nftables**
| the iptables firewall needs `xt_*` modules a container cannot load; nerd-nixos had loaded
`xt_pkttype` only by chance, and after its reboot the firewall unit failed in every container

| a delivery copies **without checking signatures**
| its source is nerd-nixos's own store, which built or validated every path, and most carry no
signature: a checked copy refused the first path of the first real delta (test 6, 2026-10-14)
|===

**The overlap needs layers from the same lock.** Measured on 2026-10-14 on a throwaway nerd-nixos
whose layers were built from the container's own lock: the container's closure is 535 paths, **all
535 in the layers**; `deliver` copied none, and the upper stayed empty. On 2026-10-11, against layers
from an older lock, 525 of the same 535 were outside them. How that overlap evolves over nerd-nixos's
life is the next section.

⚠️ **Privileged**, by the operator's decision of 2026-10-11, against the recommendation: the
container's root is nerd-nixos's root. The question of uid shifting on an overlay does not arise
there, and comes back with `shift=true` or a `raw.idmap`.

layers and pools, its first boot hands over to the target configuration and reboots, and from then
on a generation is either switched inside the VM or delivered as an **appended** layer; replacing a
layer's content means re-provisioning. Each event does something different to a container:

but **not implemented**: the layer list is fixed at three in `modules/nixos/erofs-store-layers.nix`,
one source the whole fleet shares. Today a nerd-nixos lives through A, and through C when it is
re-provisioned; the operator has always updated systems inside the VM.
A probe that rebuilds the image tests **C**, not B: the materializer refuses it, which says nothing
about an append (a wrong conclusion drawn exactly that way on 2026-10-14, discarded before push).

=== The tests the implementation must pass — the container

Tests 1 to 5 passed on 2026-10-14 on a throwaway nerd-nixos (`incus-probe`, standalone Incus, layers
from the container's lock). Test 6 passed the same day **synthetically**: a runtime drop-in gave
the lower and store units a contract one layer short, which changes the layer set as an append does,
then the real contract again. Both ways the store unit refused before mounting and named `reset`;
after `reset` and `deliver` the container ran (95 paths copied one way, none on the way back). The
materializer's append itself is exercised once it exists.

Four conditions:

. **share the paths, not the boot.** nerd-nixos's generation is a VM's (kernel, initrd, EROFS mounts

  `boot.isContainer` configuration, evaluated by nerd-nixos's generation;
. **build the containers and the layers from the same lock**, or the upper fills with copies;
. **the delta does not come from the cache that does not exist yet.** attic's own container is filled
  by `nix copy`, not by substitution;
. **the container never evaluates a flake.** Evaluation, the incident's vector, stays on nerd-nixos.

The Incus service already belongs to ndh: it is part of nerd-nixos's configuration

=== Placement is stated, never left to Incus

In a cluster, an instance created without a `target` lands on a member that Incus chooses. These
containers depend on things that exist on **one** member only: their lowers (that member's
`/nix/.ro-store*`), and for attic the `nerd/attic` dataset. So:

* attic-nixos has `target = bioskop`;
* each headscale-nixos has the member of its own bare-metal as its target;
* none of them migrates when its member is evacuated. Incus's instance option `cluster.evacuate`
  should be `stop`; that option name and value are to verify against the pinned Incus.

attic-nixos and headscale-nixos are the first two instances ndh declares, and they share one module:

== Secrets, tokens and substituters

* attic's server secret (`ATTIC_SERVER_TOKEN_RS256_SECRET_BASE64`, through `services.atticd`'s
  `environmentFile`), the cache's signing key, the layer key, the publication key
  `seedmatic-publish-1`, the cachix push token and every attic token are **sops-encrypted at rest**,
  in ndh. They are decrypted only into `/run/secrets` (tmpfs, root-only, mode 0400), and never sit in a
  flake tree.
* The publication key and the cachix push token are decrypted for the **fill job's user only**. No
  host's watch-store, no consumer and no container holds either.
* attic-nixos gets its `environmentFile` from nerd-nixos: decrypted there by sops-nix, and passed
  as a read-only Incus disk device. The container holds no age key and evaluates nothing.
* The cache is created **without** `--public`. Tokens come from `atticadm make-token`: **a write
  token per host** (`--sub {host} --push seedmatic --pull seedmatic`, see <<write-tokens>>), and a
  **read token** (`--pull seedmatic` only) per consumer class.
* Each host's write token sits on that host only, in the attic client configuration of its
  watch-store service (`attic login`). That configuration is written at service start from the
  sops-decrypted token, and is readable only by the service. No token is shared between hosts.
* nix reads a token from its `netrc-file`, as the `password` of the attic host's `machine` entry. That
  is the same entry `attic use` writes (`client/src/command/use.rs:54-68`, `nix_netrc.rs:96`).
* Substituter order on a host: cache.nixos.org and the flox caches, then the public tier
  (`nxmatic.cachix.org`, key `nxmatic.cachix.org-1`), then attic (its fabric URL, its cache key, and
  a `netrc-file` pointing at the decrypted read token). On a cluster: the public ones only, with no
  attic entry.
* `seedmatic-publish-1` is in **no** `trusted-public-keys`: it is a key name for attic's upload
  filter, not a key any consumer checks (see <<public-private-split>>).

=== Revocation — when a host is lost

attic tokens cannot be revoked one by one (see <<write-tokens>>), so losing any host, or any token,
means ending them all and re-issuing the rest:

. rotate the server secret: a new `ATTIC_SERVER_TOKEN_RS256_SECRET_BASE64`, sops-encrypted, then
  restart atticd. Every token, write and read, stops working at that moment;
. mint new write tokens for the remaining hosts, one each, and new read tokens
  (`atticadm make-token`, same subjects and scopes, bounded validity);
. re-encrypt them with sops for every host except the lost one, and switch the remaining hosts;
. check with <<read-test>> that the old read token gets 401 and the new one 200.

Until step 3 reaches a host, that host can neither upload nor substitute from attic. It falls back to
cache.nixos.org and to building.

[[read-test]]
=== The test the implementation must pass — an anonymous read is refused

[source,bash]
----
# a path known to be in the cache: {hash} of the fill's last system closure
curl -s -o /dev/null -w '%{http_code}\n' "https://{attic}/{cache}/{hash}.narinfo"
# → 401  (anonymous: refused)
curl -s -o /dev/null -w '%{http_code}\n' --netrc-file {netrc} "https://{attic}/{cache}/{hash}.narinfo"
# → 200  (read token)
----

attic answers **401** to a client without the permission. A **200 without a token** means the cache
was created or reconfigured `--public`: the cache is then not private, and this spec's condition for
the watch-store no longer holds.

⚠️ **The anonymous answer still tells present from absent.** This spec read attic's source as masking
a missing object behind the same `Unauthorized` (`server/src/error.rs:194-205`, `:218`). Measured on
2026-10-14 against attic `7a19204d` on the probe, anonymous:

[cols="2,1,1",options="header"]
|===
| Request | Object in the cache | Object absent

| `GET` or `HEAD` `/{cache}/{hash}.narinfo`
| 401
| **404**

| `GET` `/{cache}/nar/{hash}.nar`, `/{cache}/nix-cache-info`, an unknown cache
| 401
| 401
|===

So anyone who reaches the port can test whether a store hash they already know is cached, without
reading anything of it. Reaching the port is the fabric segment only, and a hash has to be known
first, so the exposure is small; it is still one more reason never to listen beyond the fabric. The
read test therefore uses a hash **known to be in the cache**, as written above: an absent one answers
404 and proves nothing.

⚠️ **nix caches narinfo answers**, positive ones included, under `~/.cache/nix`. A substitution test
run after a successful one answers from that cache and looks authorised without a token. Run it with
an empty `XDG_CACHE_HOME` and `narinfo-cache-positive-ttl = 0` (measured the same day: the cached run
printed the path, the clean run got the 401).

Measured the same day, with a read token: `nix path-info` through a `netrc-file` whose `password` is
the token reads the narinfo, the path carries the cache key's signature, and `nix store verify`
checks it against that key. A read token is refused a configuration change (403).

== Usage patterns

=== ✅ Fill from a revision, under the fill job's own user

[source,bash]
----
# as the fill job's user: its own XDG_CACHE_HOME, never shared with a worktree evaluation
nix build "git+file:///Volumes/git-bare-store/seedmatic/ndh.git?ref=develop&rev=$REV#nixosConfigurations.bioskop-nixos.config.system.build.toplevel" \
  --option allow-dirty false
# the same revision by GitHub
nix build "github:seedmatic/ndh/$REV#darwinConfigurations.nikopol.system" --option allow-dirty false
----

=== ✅ Publish the computed set, then check it

[source,bash]
----
# {set}: the publishable paths of the allow-listed outputs — closure rule and content guard
nix store sign --key-file {publication key} {set}
cachix push nxmatic {set}      # the set, explicitly, path by path
# then: every path of {set} answers 200 on cachix, and no closure member outside it does
----

=== ❌ Publish an output with `cachix push` and let it take its closure

`cachix push` uploads the closure. One built output whose closure reaches the ndh `self` source or a
sops-nix file would publish them. Publish only the computed set (see <<public-private-split>>).

=== ❌ Put the publication key in `secret-key-files`

The daemon would sign every build with it, the operator's dirty dev builds and the remote builds
included, and the key would stop meaning "published from a revision" (see <<signature-scope>>).

=== ❌ Evaluate a working tree on the builder — even once, even clean

`nix build .#x` in a decrypted checkout copies its files in clear. It also records that copy in the
fetcher cache for the revision, where a later `?rev=` build of the same commit picks it up (see
<<revisions-only>>).

=== ✅ A watch-store on every host, behind authenticated reads

[source,bash]
----
# on each of the four hosts, as the daemon's service: the cache was created without --public
attic watch-store seedmatic
----

Allowed under one condition, which <<read-test>> checks: every read needs a token. What it uploads
is listed in <<watch-store-sees>>, and what it costs in trust in <<trust-model>>.

=== ❌ A watch-store towards a cache readable without a token

On a `--public` cache, or on a public one like `nxmatic.cachix.org`, a watch-store brings the
incident back as it was: every dirty evaluation of every host published.

=== ❌ Share one write token between hosts, or give one more than push

One token per host, each with its own `--sub`, never one copied to several hosts. And no
`create-cache`, `configure-cache`, `delete` or `destroy-cache`: the tokens sit on four hosts, one of
them on the corporate side, and none can be revoked alone yet.

=== ❌ Derive the key-name list from `trusted-public-keys`

That list holds `io-nxmatic-nix-darwin-home`, which signs every local build, so the cache would stay
empty. It also holds `nxmatic.cachix.org-1`, whose paths the public cache no longer serves. Write
the list out: the upstream substituters' key names, plus the layer key.

== Troubleshooting

[cols="2,2,2",options="header"]
|===
| Symptom | Cause | Fix

| the dataset grows week after week
| GC on SQLite, capped at 500 chunks per run
| a GC interval of 15 minutes on SQLite; PostgreSQL if that is not enough

| a superseded path is never collected
| retention 0 (the default), or a `cache configure` that reset it
| set `--retention-period` in the same declarative step as every other cache setting

| attic holds nothing after a pause
| expected: the retention is the active session (see <<retention>>)
| the next fill refills it. Its running closure is local anyway, sent by the fill job

| a published path is also in attic
| the race: the watch-store saw it before the fill job signed it
| nothing to do: it is public content, and the short retention removes it

| a path is in no cache, and the host must rebuild it
| it carries a stale `nxmatic.cachix.org-1` signature from before the purge, so attic skips it
| a fill re-publishes it, if it is publishable. Otherwise the host's rebuild uploads it to attic

| the post-push check finds a path on cachix outside the computed set
| a push took a closure instead of the set
| ⛔ treat it as a publication incident: purge it from cachix, then find the push that took the
closure. Count, never print, what that path holds

| a fill publishes nothing
| the guard refused, or every output's closure reaches an added path no upstream serves
| read the job's per-path verdicts. The paths stay private, which is the intended outcome

| the cache uploads paths cache.nixos.org serves
| they carry no upstream signature locally: layer registration, or a local rebuild
| the layer key for the layer paths. The rest is disk, until the fork.

| an anonymous narinfo request returns 200
| the cache was created or reconfigured `--public`
| make it private again. Until then the watch-store's condition does not hold, so stop it.

| a host cannot substitute from attic at all
| its `netrc-file` is missing, or its token is expired or has no `--pull`
| check the decrypted token under `/run/secrets` and the `netrc-file` setting

| the cache stays empty
| `io-nxmatic-nix-darwin-home` is in `upstream-cache-key-names`
| remove it: it signs every local build

| a host is lost, or a token leaked
| attic tokens cannot be revoked one by one
| rotate the server secret and re-issue the tokens (see the revocation steps in <<secrets>>)

| every host stops uploading on the same day
| the write tokens were issued together and expired together
| re-issue them; the validity is bounded on purpose

| the container's store reports a stale file handle (ESTALE)
| a lower changed under `index=on`
| restart the container on the layer set nerd-nixos booted
|===

[[attic-fork]]
== The real fix — an attic fork, later

The read token **confines** a plaintext path that reaches the cache; it does not keep it out. The
fix is upstream of the token: the cache must refuse such a path. attic offers no hook for that, so
it is a fork, meant to be contributed upstream. Decided with the operator on 2026-10-10, for later.

[cols="1,3",options="header"]
|===
| Change | What it does

| a daemon-to-server protocol
| the **server** judges what enters, rather than a filter in each client. The natural place for it
is `get-missing-paths`, the exchange that already opens every push: the server can answer "served
upstream" or "refused" as well as "missing".

| an upstream check by query, not by signature
| ask the upstream caches for the narinfo, instead of reading local signatures. That closes the
297-path gap, and makes the layer key a convenience rather than a necessity.

| a content filter, which refuses
| with the repository's `.sops.yaml` shared to the server: a `# sops:encrypted` annotation followed
by anything but an `ENC[` value marks a decrypted file. Measured on `keys.yaml`: the annotation
survives in clear in both states (9 annotations, each followed by `ENC[` when encrypted, by a `\|`
block when decrypted). A second test, independent of the rules, looks for private-key armour with a
body, an `AGE-SECRET-KEY-1`, and GitHub token shapes, because the `.sops.yaml` itself was once wrong
(2026-08-27).
|===

Two more contributions follow from the operator's choices on writers (see <<trust-model>>):

[cols="1,3",options="header"]
|===
| Change | What it does

| revocable per-host tokens
| a token per host that can be ended alone, without rotating the server secret. That needs state on
the server, a list of revoked subjects or of issued tokens, where attic is stateless today
(`token/src/lib.rs:3-12`).

| trust restored per writer
| the content check above, at upload, so that no writer can publish what the server rejects. Or
per-writer signing keys that consumers can tell apart.
|===

The filter **refuses**; it never re-encrypts. A `-source` path is addressed by its content, a cache
signature covers the NAR hash, and sops draws a fresh IV at each encryption. A rewritten path would
be a different path, and every closure that references it would have to be rebuilt.

[[open-questions]]
== Open questions

* **The allow-list**: which named outputs it holds. Its criterion is what the clusters need, since
  they read the public tier only, plus the hosts' public packages.
* **The public/private split on the four hosts**: measured on bioskop's system closure only (161
  publishable paths, 18 private). The quota (16G or about 8G) waits for it.
* **The retention value**: 6 hours is a proposal in the operator's order of magnitude, to confirm
  against a real session.
* **The cachix plan**: the public tier's storage quota, and what cachix collects when it is full.
* **Where the content guard runs**: in the fill job, before signing. The shapes are rke2lab's
  `token_shape_guard`; whether to share that script or restate it is open.
* **Package outputs, cluster node closures and in-cluster env closures**: their size, once a fill has
  built them.
* **Reaching the builder from the cluster nodes**: the nodes sit on their bare-metal's `vmnet`
  segments and the clusters on the SaaS tailnet. The route and the identity from a node to its
  `{host}-nixos` (see <<secrets>>) have to be stated. Nodes no longer need to reach attic itself.
* **The node-base nix configuration** (`builders`, `max-jobs = 0`, `builders-use-substitutes`,
  `require-sigs`): a rke2lab follow-up.
* **The builder tests** (<<builder-tests>>): their results decide between the design as written and
  fallback B.
* **The pod tier's lower changes while mounted**: it is the node's live `/nix`, which the flox
  controller grows and the node's GC shrinks. That is the case this spec forbids for tier 2. The hook
  reconciles the pod's store DB at every container start, which repairs the DB, not the overlayfs
  rule. Whether tier 3 should instead stack on the immutable layers is rke2lab's to decide.
* **uid shifting**: an unprivileged container sees the store's files as `nobody`, and nix expects
  root-owned store paths. Incus `shift` relies on idmapped mounts, and whether EROFS supports them is
  unverified. If it does not: a privileged container or a `raw.idmap`.
* **Dataset creation**: does disko create `tank/nerd/attic` on a pool that is already formatted, or
  does an activation step have to?
* **The TLS leaf behind attic's fabric URL**: from `mammoth-skate-tls`, like the control URL?
* **`nix store copy-sigs` from a local store**: whether it accepts `local?root=…` as its source, for
  the layer key.
* **Token validity and re-issue**: the validity of the write and read tokens (three months in the
  example), and what re-issues them on schedule.
