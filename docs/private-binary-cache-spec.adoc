== Overview

The seedmatic hosts share most of one configuration, so they run mostly the same packages. Today
each host builds them again. The cache makes a path **built once and substituted everywhere**:

* **each access point builds** — bioskop and nikopol, from its darwin host or its NixOS guest —
  from a **pushed revision**, never from a working tree (see <<per-metalspace>>, <<revisions-only>>);
* what they build stays in **each metalspace's private** cache: an **attic** server in a cache
  container (an Incus container) on that metalspace's NixOS guest, filled by an `attic watch-store`
  on each machine of the access point, read by every machine, every read of which needs a token (see
  <<per-metalspace>>);
* **nothing of ours is public**: the only public caches are upstream's, cache.nixos.org and flox
  (decided 2026-10-17, see <<no-public-cache>>);
* a cluster's nodes and workloads build nothing themselves: they delegate every build to their
  metalspace's **cluster builder**, which holds no attic token (see <<cluster-builds>>).

[cols="1,3",options="header"]
|===
| Property | What it gives

| One build per path
| The four host closures add up to 32 GiB, but their union is 15.7 GiB, and only 1.6 GiB of that union
is not already on cache.nixos.org (measured, see <<sizing>>). That 1.6 GiB is the part the hosts
rebuild today.

| The active session only
| The cache keeps what the current coding session needs, for a few hours, not a history and not
the previous day (see <<retention>>). It skips the paths whose signature says an upstream cache
serves them.

| No public cache of ours
| Our builds never leave the fleet's private caches. The 2026-10-10 class, a watch-store pushing to a
public cache, has nowhere to go: there is no such cache (see <<no-public-cache>>).

| Each access point writes its own metalspace's private cache, and reads both
| Each machine uploads to its own metalspace's attic, with a write token of its own, and reads both
caches. The price is trust: a cache is as trustworthy as its least trusted writer, and each has only
its own access point's writers (see <<per-metalspace>>, <<trust-model>>). The corporate bare-metal writes nothing.
The clusters hold **no** attic token: their nodes and workloads delegate every build to their
metalspace's cluster builder (see <<cluster-builds>>, design only). The infrastructure containers hold none either.

| Private by authentication
| The cache is created **without** `--public`, so an anonymous request is refused (see
<<read-test>>). Listening on the fabric segment only, never on a public port, adds to that. It does
not replace it.
|===

The motive is the incident of 2026-10-10. A daemon pushed every new store path to the public cache.
On a machine whose git config smudge-decrypts sops files, evaluating a dirty rke2lab tree copies
`.secrets` and `.ndh-ssh.d/keys.yaml` in clear into the store, so 52 such copies became public. The
daemon was disabled on every host in `395b34a1`.

It is not only a dirty tree. Measured on 2026-10-11: **any** evaluation that names a decrypted
checkout (`.`, `.#x`, a bare `git+file://`) copies the files from disk, clean tree or dirty. Only a
revision read from git objects stays encrypted (see <<revisions-only>>).

This spec brings the cache back, private only, and narrows that shape in layers:

* the builders evaluate revisions only;
* **nothing of ours is published** (see <<no-public-cache>>);
* every read of our builds needs a token.

None of these proves a path's content clean. That is the job of an attic fork that refuses such paths
at upload (see <<attic-fork>>), and of the content guard on whatever leaves a metalspace by copy (the
corporate vz-host's `nix copy`).
Upstream of all of it: no plaintext on disk in a flake tree.

[[why-attic]]
== Why attic, and not the stores themselves

A nix store is already a cache for another store: a builder could serve its own store in place (harmonia, or
`ssh-ng://`), signed with its key, and stacked stores (one store as an overlay on another's frozen layers) would
share paths without any server. attic is chosen anyway, for one reason, the operator's (2026-10-18):

[quote]
____
Les stores contiennent déjà le monde entier ; l'avantage d'attic, c'est d'avoir un contenu séparé par cache, et donc
d'aider à identifier les vraies outputs des builds dans seedmatic.
____

A store holds everything its machine ever needed: sources, every `.drv` (`keep-derivations`), the inputs a client
handed it, whatever an evaluation copied in. A cache holds only what was pushed into it, cache by cache: the set of
seedmatic's own outputs. It is the same idea as prefixing our packages' names `io.seedmatic.…`
(`io.seedmatic.ndh-nix-store-erofs-001`, …), the operator's: our outputs found at a glance, physically in a store by
their name, logically in attic by their cache. What follows from it:

* **exposure**: serving a store exposes all of it to every reader, a slipped plaintext `-source` included (the
  2026-10-10 class); a cache exposes what was pushed, to its token holders only, after the watch-store's own skips
  (`.drv`, `*-source`). Those skips are not enough: the watch-store pushes built outputs, and an output can EMBED an
  evaluation-time value (a secret wrongly interpolated into a generated configuration file lands in the output
  itself, not only in its `.drv`). That is what the fork's content filter is for, later, with the content guard on
  what leaves by copy (see <<attic-fork>>);
* **lifetime**: a builder's store dies with its machine; a cache outlives the builder that filled it;
* **access**: a token per cache and per right (read, push), which a served store does not offer;
* **retention**: per cache, independent of the machine's disk and its GC.

Its cost, accepted: a second copy of each pushed path, and the push itself. Sharing a base by layers (a store over
another's frozen layers) is not ruled out by this: it shares what a machine runs on, while attic records what
seedmatic builds.

The **client** is distinct from the **builder**. Every **fleet** machine, the
darwin host and the NixOS guest alike, is a build client and may ask for a package of **any** system, darwin or Linux.
The access point's two machines hold the metalspace's **builder role**, which dispatches by system:
`aarch64-darwin` to the darwin host (its loopback `nix-store`, see <<every-build-a-request>>),
`aarch64-linux` to the NixOS guest. Within an access point, its two machines therefore trust each
other's store: each is a trusted client of the other's `nix-store` (accepted: they already share every
secret, and the darwin host runs the guest). **Every fleet builder** (the access point's two machines; the
cluster builders hold no attic token, see <<cluster-builds>>) **pushes its outputs into its metalspace's
attic**: each holds a write token and a watch-store, minted by its cache's `attic-token-mint` and pulled by the machine.

A cache is as trustworthy as its least trusted writer (<<trust-model>>), and each cache has only its
own access point's writers. But nikopol's writers, the darwin host nikopol and nikopol-nixos, are
Tart VMs **on** the corporate bare-metal, whose hypervisor can read and alter their memory, disks and
tokens. So bioskop's machines, trusting nikopol's key, trust what the corporate bare-metal hosting
metalspace nikopol could inject: **an accepted risk** (the operator, under the security model's
"corp IT"), **not an absence of risk**. A blob's provenance is its signature: the
key names the metalspace.

The private tiers' confidentiality still rests on <<revisions-only>>: a watch-store uploads any store
path, including what an evaluation of a decrypted working tree copies into the store (the 2026-10-10
class), and now the OTHER metalspace reads it too.

| *Builder*
| A machine holding its metalspace's builder role: the darwin host builds `aarch64-darwin`, the NixOS guest

| A metalspace's attic, readable with a token, which holds our builds. There is no public tier of

| *Cluster builder*
| A metalspace's Incus container to which a cluster's nodes and workloads delegate every build. It

| *Read token*
| An attic token that can pull from the cache and nothing else. Every substituter of attic holds one

| *Ours*
| A path that has no `cache.nixos.org-1` or flox signature in the local Nix DB.

| *Truly ours*
| A path that is ours **and** whose narinfo returns 404 on cache.nixos.org. Only these belong in the
cache.

| *Live set*
| The paths attic must keep while a session is active: for each host, the closure of its latest
built generation, minus what upstream serves.

[[who-fills]]
== Who fills the cache — every machine, into its own metalspace's cache

A watch-store on each of the four machines uploads what that machine builds, dev builds included, into its own
metalspace's cache. bioskop-nixos and nikopol-nixos are their darwin hosts' Linux builders, so they also receive the
builds of those hosts' dirty trees: whether a dirty build lands on the operator seat or on its builder is a difference
of degree, not of kind.

[cols="1,3",options="header"]
|===
| | What it gives, and what it costs

| Gain
| every build on any machine is shared, dev builds included

| Price — trust
| a write token on every machine, so a cache is as trustworthy as the **least trusted of its two writers** (see
<<trust-model>>), and tokens that cannot be revoked one by one (see <<revocation>>)

| Price — the corporate side
| nikopol's two writers are Tart VMs on the corporate bare-metal (see <<trust-model>>)

| Price — exposure
| every operator seat's dirty evaluations reach the cache, confined by authenticated reads (see <<watch-store-sees>>)
|===

[[write-tokens]]
=== One write token per machine, a read token per machine and cache

Each cache container's `attic-token-mint` makes, for each of the four machines, a read token (`--pull seedmatic`) and,
for its own metalspace's two, a write token (`--push seedmatic --pull seedmatic`), each with `--sub <machine>` and
nothing else: no `create-cache`, `configure-cache`, `delete` or `destroy-cache`.

[cols="1,3",options="header"]
|===
| A token | Rule

| subject
| the machine's name, so each token belongs to one machine and none is shared

| validity
| 14 days, minted again every week by a persistent timer, and at every container start or change of who gets a token;
a missed week is harmless, and a machine that has not pulled for 10 days fails loudly

| revocation
| attic's tokens are stateless JWTs: ending one means rotating the cache's server secret, which ends every token of
that cache (see <<revocation>>; revoking one machine alone is for <<attic-fork>>)
|===

[[watch-store-sees]]
=== What a host's watch-store uploads

The daemon watches the whole store, not the fill. Read in attic `client/src/command/watch_store.rs`
at `7a19204d`:

* when a path becomes valid, the daemon skips it if its name ends in `.drv` or `-source`. That is a
  test on the **name**, done once, when the path appears;
* for every path it keeps, it pushes the **closure** by default (`--no-closure` is a hidden flag).
  An output that references a flake source therefore carries that source, whatever its name.

With a daemon on every host, these origins all reach the cache:

[cols="1,1,2",options="header"]
|===
| Host | Origin | What lands in the cache

| every host
| its own builds
| the outputs of whatever it builds, dirty trees included. A dirty evaluation's `-source` copy,
plaintext included, is skipped by name, but an output that references one carries it in its closure.

| bioskop-nixos, nikopol-nixos
| the operator seats' remote builds (`ssh-ng`, `/etc/nix/machines` on the darwin hosts)
| the outputs of derivations their darwin host evaluated, dirty trees included

| —
| the cluster nodes' and pods' builds
| **nothing**: they are delegated to the cluster builders, which hold no attic token (see
<<cluster-builds>>)
|===

This is **accepted under authenticated reads**. A plaintext copy that reaches the cache can be read
only by a holder of a read token, all of which are machines of the fabric (see <<secrets>>). It is
not fixed by them. The fix is the fork in <<attic-fork>>.

[[bringup-images-never-cached]]
=== Bringup images never go to a cache

**Rule.** No cache — the public cachix, attic, or any other — receives a bringup disk image: the
EROFS store layers (`io.seedmatic.ndh-nix-store-erofs-*`), the raw disk set
(`*-bringup-zfs-disk-images-raw`) and its reference-free copy (`*-bringup-zfs-disk-images-raw-detached`),
or the set that links them (`*-bringup-zfs-disk-images`). They reach a host only by `nix copy` from the
builder, through `nerd-tart-<host>-materialize` or `nerd-tart-<host>-deploy`.

**Why.** An image is a whole guest store and a whole guest pool in one opaque file: whatever a closure
or the target root held lands there, and since the images record no reference to what they pack
(2026-10-14, the materializer's closure fix), nothing downstream sees what they carry. The
secret-material guard refuses key material when a layer is packed and when the target root is
written (`modules/nixos/secret-material-guard.d/`), but it answers one question — an image that
never reaches a cache cannot leak what the guard does not ask about.

The watch-stores skip these names — the daemon's own test is on the name, done once, when the path appears (see

=== What `secret-key-files` signs — measured

Measured on 2026-10-11 (nix 2.34.8):

* **in an isolated store** (its own store root, `HOME` and `XDG_CACHE_HOME`, a throwaway key, no
  substituters): a `builtins.path`, a `builtins.toFile`, a flake `path:` source and a
  `nix store add-path` receive **no** signature, only their `ca:` field. `nix store sign` on the
  same path works, so the key was read;
* **in bioskop's store**, 396 paths created since 2026-10-09: 69 of 69 built locally are signed by
  `io-nxmatic-nix-darwin-home` (the fleet key then, rotated to `seedmatic-fleet-1` before T4), 0 of 210 added paths are;
* fixed-output outputs (fetchers) are content-addressed too, but they have a deriver and are signed
  like any build.

And `secret-key-files` is **daemon-wide**. A key placed there signs the operator's dirty dev builds

[[cluster-builds]]
== The clusters build through a cluster builder

A cluster's nodes and workloads build
nothing themselves: they delegate every build (`max-jobs = 0`, `builders = ssh-ng://…`,
`builders-use-substitutes = true`) to **their cluster's builder**, and to it only: a
cluster trusts its **own** cluster builder and no other, so there is **no fallback** to the other
metalspace's cluster builder. The cross-metalspace fallback is the four fleet
machines' alone (their own metalspace's builder first, then the other's). The `builders` list is
generated from the machines holding the builder role, each with its systems. seedmatic builds for **arm64 only**, so a cluster's derivations are all `aarch64-linux`
and the darwin hosts are never among its builders (they offload `aarch64-linux` to their guest
themselves).

The cluster builder is **its own unprivileged Incus container, one per cluster**, not the NixOS guest:
a node-supplied derivation runs arbitrary code in the builder's sandbox, and on the guest an escape
would land on the access point's age identity, its sops secrets, the Incus member, the fabric and
attic's push token.

**Its shape: an LXC image of its own**, its store the image's rootfs, which
Incus idmaps. ndh **defines** it (`modules/nixos/cluster-builder.nix`, exported as `nixosModules.cluster-builder`,
with its settings check) and builds no image of it, having no use for one; **rke2lab builds the image**, by
revision, in a `nixosConfigurations` beside `rke2-node-base`, the same route as its node image. Not the
shape of ndh's other containers (<<container-store>>): their store is composed by the NixOS guest, an
unprivileged container sees it as `nobody`'s and cannot write it (measured: a cache container's upper stays at 0
entries), and a builder writes every output; privileged, it could, but its root would be the guest's,
so a sandbox escape would land next to the guest's keys. From nixpkgs' `lxc-container.nix` only the image is kept:
`lxc-instance-common.nix`, which it imports, opens a password-less root login, enables sshd with its defaults and
copies a channel in, so it is disabled. A new system is a new image, hence a new host key and a new nix key.

**It never builds bringup**. Bringup and the disk images are ndh's, built by the fleet's
builders for the fabric's bootstrap, and a node only inherits its system from them. The cluster builder serves
what a cluster's nodes and workloads ask at run time, so it stays small and has no `/dev/kvm`.

[[node-image-paths]]
**A node's image paths keep their provenance.** Found by
test 0: a store booted from an image is registered by `nix-store --load-db`, whose format
(`Store::makeValidityRegistration`, nix 2.34.9 `src/libstore/store-api.cc:824-845`) keeps a path's hash, size, deriver
and references, and **no content address and no signature**. So every path a node has from its image looks, to its
untrusted builder, like an unsigned input-addressed path, and is refused when the node hands it over (test 1's case),
even a pure source; paths fetched or built after boot keep theirs. Measured on the probe: a source of flox's build,
`ca` null, deriver null, registered at the VM's creation, refused.

The node image therefore registers its store **from a binary cache at boot**, keeping the content addresses and
signatures its origin store gave those paths, and the untrusted builder accepts them. Two conditions:

* the binary cache the node registers from is the image's **own local `file://` cache**, baked into the image, never a
  network cache;
* the builder trusts the key that signed the image's paths, a fleet machine's derived key (<<builder-keys>>), beside
  cache.nixos.org's and flox's, and its trusted keys are **listed exactly by a check**. Trust flows down, from the fleet
  to a cluster's builder, never the reverse: nothing of the fleet trusts a cluster builder's key.

The work is **rke2lab's**, in node-base's image and the cold start, not this spec's code.

**Future (b)**: a cluster spanning both metalspaces, with two cluster builders scoped to that cluster,
one per metalspace, tied to the cluster mesh. Until then a cluster lives in one metalspace and has one
builder.

The node side is **rke2lab's**: `nixos/nix-builders.nix` turns the builder description a node receives at boot
(cloud-init, one nix machines line per builder) into `max-jobs = 0`, `builders = @…` and `builders-use-substitutes =
true`, through a gate that refuses any description it cannot check, so a node never falls back to building in
silence.

[[revisions-only]]
=== The builder evaluates revisions only — and with its own fetcher cache

**A hard rule, measured (nix 2.34.8, a fresh store per case).** On a
machine whose git config smudge-decrypts sops files, **any** evaluation that names a checkout copies
its files from disk into the store, decrypted, **clean tree or dirty**. That covers `.`, `.#x` and a
bare `git+file://{worktree}`. Only a reference to a **revision** reads git objects, so the secrets
stay encrypted:

[source,bash]
----
# ✅ revisions — git objects
github:seedmatic/{repo}/{sha}
git+file:///Volumes/git-bare-store/seedmatic/{repo}.git?ref=develop&rev={sha}
{repo}-bare/develop/{sha}          # the same, by its host-registry id
# ❌ a working tree, clean or dirty
.   .#x   git+file://{worktree}
----

**The source-cache trap.** nix's fetcher cache keys a commit's source by its revision, and the
**first** evaluation wins. One `nix build .#x` in a decrypted worktree records a plaintext copy for
that revision, and every later evaluation of the same commit, by `?rev=` or by the bare repository,
reuses it as `${self}`. A revision reference is therefore safe only with a fetcher cache that no
worktree evaluation ever wrote. So:

. a builder evaluates only revisions, with `--option allow-dirty false` on its command line where it runs unattended;
. a revision is safe only with a fetcher cache that no worktree evaluation ever wrote: whatever builds from it
  unattended runs under its own `XDG_CACHE_HOME`.

The detector, while a worktree on disk is decrypted: a sweep of the store for new `-source` copies
of a seedmatic tree, `find /nix/store -maxdepth 1 -newerct {absolute date}`. Then count, never
print: `grep -c 'ENC\['` on its sops files, compared with the committed blob.

=== A build client cannot write into the builder's store — on three settings

A build over `ssh-ng` copies paths into the builder. If a node could import an arbitrary path there,
it would poison what that cluster's other nodes substitute from it. Read in nix 2.34:

* for a client it does not trust, the daemon **forces signature checking** on every import
  (`src/libstore/daemon.cc:505-506`, `:907-908`). An unsigned, input-addressed path is refused;
* the daemon refuses an untrusted client's `buildDerivation` of an input-addressed derivation
  (`daemon.cc:632-633`: _"you are not privileged to build input-addressed derivations"_);
* `build-remote` handles that case: when the builder does not trust the client and the derivation
  is input-addressed, it copies the `.drv` closure, which is content-addressed and so accepted, and
  asks for `buildPaths` instead (`src/nix/build-remote/build-remote.cc:300-340`). **The builder
  computes the outputs itself.**

So, with these three settings on the cluster builder:

. the build clients (nodes, pods) are **not** in `trusted-users` (test 1 decides, see above);
. `require-sigs = true` (nix's default, stated so that nobody turns it off);
. their input paths are signed by a trusted key or content-addressed.

[mermaid]
....
sequenceDiagram
  autonumber
  participant N as Node or pod (not a trusted user)
  participant B as Its cluster builder
  participant U as cache.nixos.org, flox
  N->>B: copy the .drv closure — content-addressed, accepted

locked by flake ref, never by a bare store path. What upstream serves, the node substitutes directly.

[[every-build-a-request]]
=== Every build is a request

With `max-jobs = 0`, a machine's own daemon builds nothing: each derivation goes over `ssh-ng`, by
certificate, to a `nix-store` account (forced `nix-daemon --stdio`, a trusted user of its store). The
machine's own system goes through a **loopback** entry on its fleet name, never `localhost`, which no
certificate vouches for; the other system goes to a builder of that system. The `builders` list is
generated from the machines holding the builder role, as for <<cluster-builds>>.

The first step is in ndh `feature/builds-as-nix-store`: a Darwin host's `aarch64-linux` builds reach
its guest through the `nix-store.<host>-nixos` alias, no longer as root with the operator's raw key.
`max-jobs = 0` follows, under these conditions:

[cols="1,2",options="header"]
|===
| Condition | Why

| a documented and proven way out: `--option max-jobs 1` or `--option builders ''`, passed by root,
the caches' substitutes, the guests' console
| a broken sshd, certificate or KRL would otherwise leave the machine unable to build anything

| `ndh-switch` and `fleet-switch` keep an explicit local-build option
| a broken loopback must never prevent building the switch that repairs it

| a probe of the loopback passes, machine by machine, before it is enabled
| the failure is found before it locks a machine

| the loopback accepts certificates only, on the fleet name
| `localhost` and a raw key would bypass the role

| a build check that the KRL never cuts a machine's own `nix-store` certificate
| a machine would lock itself out of its own builds
|===

| nowhere in a repository, and it never transits: HKDF of the machine's host-key seed, label
`seedmatic/nix-signing/<n>`, re-derived on its machine at activation from its own host key, root 0400
outside the store
| the machine's activation; `ndh-keyring` derives it once, at generation, only to record the public

| a fleet machine's nix signing **public**
| `keys.yaml`, the machine's entry, beside its host public; `acceptedBy` and `trusted-public-keys`
read it from there and restate nothing
| `ndh-keyring`, in the same gesture as the host public

| a fleet machine's ssh identity for build requests
| a second, **user** certificate on its host key, principal `nix-store`, replacing keys.yaml's single
`nix-store` key shared by every machine; the KRL cuts it alone, by its key id
| the user authority, from the recorded host public

| an attic cache key
| its **private** inside its cache container only, generated there by attic and never exported; its
**public** in `catalog/cache-trust.nix`'s `privateCaches`, as the operator's acceptance (see the
accepted-key schema in `catalog/private-caches.nix`). `catalog/cache-trust.yaml` holds no cache key:
it keeps `seedmatic-fleet-1`'s private until step 9, then empties
| attic in the container; the operator's merge for the public

| the cluster builder's nix signing **private**
| inside its container only: **generated** at first start (`nix key generate-secret`, root 0400), never
derived from its host key, never leaving; a grow is a new container, so a new key
| the container, at first start

| the cluster builder's two publics
| the cluster's own cellar, never fleet `keys.yaml`, `acceptedBy` that cluster only (<<cluster-builds>>)
| the cluster's own scenario
|===

**Derive or generate.** The fleet machines **derive** their nix key from their host key, because that host key is
recorded (`keys.yaml`, the operator's keyring), so its public is derived and recorded ahead and the private
re-derived at every activation without being stored. A cluster builder **generates** its own: its host key is
born and destroyed with each grow and recorded nowhere, and deriving would only tie the two keys together.

* **Naming:** `seedmatic-<machine>-<n>`, where `<n>` is the HKDF label's version and `<machine>` the
  machine's `keys.yaml` name, as in `host-<machine>`. Cache keys keep their names
  (`seedmatic-<metalspace>-attic-<n>`, `seedmatic-<cluster>-attic-<n>`).
* **A distinct key, not the host key itself**: the same ed25519 key would sign both ssh and
  narinfo with no domain separation. So the nix public cannot be computed from the host public, and
  `ndh-keyring`, which holds the private at generation, records both.
* **The cost**: one leak is both keys, and renewing a host key renews its signing key; paths the
  old key signed are re-signed or re-substituted.
* **When:** a host key generated before this rule gets its nix key at the single renewal (roles × keys
  step 9), not before. Until then `seedmatic-fleet-1` stays the interim key of every builder, and the
  gate of T4; <<revisions-only>>'s copies carry it until then.

[[who-imposes]]
=== Who imposes "built by a builder"

Each **consumer**, through its own `trusted-public-keys`, generated from the catalog. Nobody else
imposes; attic only stores.

* **Nodes:** their cluster builder's key and upstream's (cache.nixos.org, flox) only.
* **The four machines:** the attic cache keys, and the builders' keys (`seedmatic-fleet-1` today, the
  derived keys from step 9). A builder's signature is **accepted**, not required, while an attic key
  is also trusted: it is recorded provenance.
* **Later:** once <<attic-fork>> serves `object.sigs`, the builders' keys become the only accepted
  ones on the hosts, and the cache keys stop being trusted.

[[trust-model]]
== Trust model — the cache is as trustworthy as its least trusted writer

This is a fact of the design, not a footnote. It applies to the private caches; there is no public
tier of ours (see <<no-public-cache>>).

attic signs, with **the cache's** key, every path a writer uploads. For an input-addressed path,
which most outputs are, nothing proves the uploaded content is what the derivation would produce.
Any writer can publish **arbitrary content under any input-addressed path**, and every consumer
accepts it, signed by attic. Content-addressed paths, such as a `-source`, are the exception: their
name is derived from their content, so a substitute for one cannot be swapped. With a write token on
four hosts, the cache is therefore exactly as trustworthy as the **least trusted** of the four.

[cols="1,3",options="header"]
|===
| Writer | What its token puts at stake

| bioskop, bioskop-nixos, nikopol-nixos
| a writer of the fabric: a compromise of any one of them can poison what all the others substitute

| nikopol
| its own write token (`--sub nikopol`) **inside the darwin VM that runs on the corporate
bare-metal**. It sits next to the fabric rule that the corporate machine holds no key. The token
lives in the VM, not on the bare-metal, and is scoped to pushing to `seedmatic`, with no end of its
own. It is nikopol's alone, but until attic can revoke one token, losing it still means
rotating every token (see <<write-tokens>>).
|===

**The plaintext the private tier accepts.** With a watch-store on every host, a plaintext
`-source` produced by one slipped `.#x` on bioskop lands in attic. It is an added path, so no key
signs it and `upstream-cache-key-names` never skips it. That is the risk the operator accepted on
2026-10-10, under three bounds: the tier is private, every read needs a token, and the retention is
short (see <<retention>>). It is detected, not prevented, by the store sweep of
<<revisions-only>>, and prevented only by the fork (see <<attic-fork>>). No public cache receives
such a path: there is none.

What would restore the trust, neither of which this spec builds:

* a **content check at upload**, so that a writer cannot publish what the server rejects. That is
  the fork, <<attic-fork>>;
* **per-writer signing keys that consumers can tell apart**, so that a consumer trusts some writers
  and not others. attic gives one key per cache, so this means a cache per writer, which the operator
  did not choose (see <<write-tokens>>).

=== The upstream filter — signatures, for the watch-store and the push alike

attic's filter is a setting **of the cache**, on the server: `upstream-cache-key-names`. Both
`watch-store` and `push` read it. For each path of the closure, the client reads the path's
signatures **from the local Nix DB**, splits each at the `:`, and drops the path if the key name is
in the list. It asks no upstream server (attic `client/src/push.rs:449-466`).

The list is `cache.nixos.org-1`, `flox-cache-public-1` and `floxhub-1`. It is
**not** ndh's `trusted-public-keys` as they stand:

[cols="1,3",options="header"]
|===
| Key name | Why

| `seedmatic-fleet-1` — out
| the fleet's own key, in `secret-key-files`, so nix signs **every local build** with it (about 1170
of our paths carry it, measured). In the list, it would leave the cache empty.

| `nxmatic.cachix.org-1` — out, since 2026-10-17
| no public cache of ours (see <<no-public-cache>>). About a hundred local paths still carry it from
before the 2026-10-10 purge; with the key out of the list, the watch-stores upload them to attic like
any build of ours.

|===

The filter misses what upstream serves but no local signature says: **297 paths (0.66 GiB)** across
the four host closures. On bioskop-nixos, 96 of its 289 such paths are in the EROFS layers,
registered from `closureInfo` without signatures (`nix-store --load-db`,
`modules/nixos/bringup-disk-image-common.sh:131`). The others were built locally. They cost disk,
not a leak. No uploader can query upstream before uploading until the fork.

=== Excluding the EROFS layers' own paths

A path that is in the layers is already on every consumer that mounts them, so it should not be uploaded. The layers'
provenance is the building machine's own nix-signing key, checked when a layer is mounted (F8: each layer ships with
its dm-verity tree, and the initrd checks its root hash's narinfo signature against the recorded nix-signing publics;
a refused layer is never mounted). It is not coded yet. Until then, the paths of the layers carry no signature in a
guest's DB (`nix-store --load-db` keeps none), and the upstream filter cannot skip them: they cost disk, not a leak.

=== The secret guard — no step left to run it in, so it is the fork

Every host's system closure already carries sops files **by design**: sops-nix puts the encrypted
file in the store. Measured, by counts only: `ndh-.secrets` (16 `ENC[` values), `keys.yaml` (10
`ENC[`, no `PRIVATE KEY` marker, its 77 plain values are public by design) and `cache-trust.yaml`
(2 `ENC[`). So a guard must judge **content, not names**. It would refuse a path that holds:

* a `# sops:encrypted` annotation followed by anything but an `ENC[` value (the rule of
  <<attic-fork>>);
* a private-key armour header followed by a body;
* a GitHub token shape (`gh[opsu]_…`, `github_pat_…`).

With no public tier, it gates what leaves a metalspace by copy (the corporate vz-host's `nix copy`),
as a library. For the private caches, a watch-store on every host leaves no push step to run it in,
and attic offers no hook. So there the guard **is** the fork.

[[retention]]
== Retention — the active session, not a history

=== What attic actually does

Read in attic's source at `7a19204d` (2026-07-06), not taken from the usual summary:

[cols="1,3",options="header"]
|===
| Fact | Source

| An object is collected when **both** `created_at` and `last_accessed_at` are older than the
retention period.
| `server/src/gc.rs:108-123`

| Only a **NAR download** bumps `last_accessed_at`. A narinfo lookup does not.
| `server/src/api/binary_cache.rs:212` (bump) and `:115-160` (narinfo, no bump)

| A retention of **0 disables GC**, and 0 is the default.
| `gc.rs:95`, `config.rs:561-563`

| Re-pushing a path the cache already holds never reaches the server, so it refreshes nothing.
| `client/src/push.rs:478-484`

| There is **no pinning and no single-path delete**. The only DELETE destroys a whole cache.
| `server/src/api/v1/mod.rs:10-37`

| `attic cache configure` **without** `--retention-period` resets the cache's retention to the
global default.
| `client/src/command/cache.rs:225-229`

| On SQLite, a GC run reaps at most **500 chunks**; on PostgreSQL, 65535.
| `gc.rs:178-190`
|===

=== How "the active session only" is obtained

The private tier only has to stay in step **while a coding session is active**. A slower restart after a pause is
accepted, and no generation of the previous day is kept. Since nothing can be pinned or deleted path by path, that is
**a short retention period**:

. per cache, `retention-period = 6 hours` (proposed, in the order of magnitude the operator set). It
  is set in the same declarative step as every other cache setting, so a later `configure` cannot
  reset it silently;
. a path nobody uploads or substitutes for 6 hours is collected at the next GC run, within 15 minutes.
  After a longer pause, attic holds nothing of the previous session: the next session's builds refill it, and that
  is the slower restart accepted;

[mermaid]
....
stateDiagram-v2
  [*] --> Uploaded: created_at set
  Uploaded --> Live: a substitution downloads its NAR
  Live --> Live: last_accessed_at bumped
  Live --> Idle: the session pauses, or a newer generation
  Idle --> Expired: 6 hours without a download
  Expired --> Orphaned: GC deletes the object, within 15 minutes
  Orphaned --> Reaped: no NAR or chunk holder left
  Reaped --> [*]: disk freed
....

An idle path goes back to _Live_ as soon as a machine downloads it again. The disk is freed
only at the last step, which is why the GC cadence matters: SQLite reaps at most 500 chunks per GC
run.

[cols="1,3",options="header"]
|===
| Guarantee | Holds when

| a host never loses its running closure
| always: it is in its own store, and needs no cache

| a host re-substitutes from the private tier
| within 6 hours of the last upload or substitution of the path
|===

=== GC cadence and database — SQLite, a GC every 15 minutes

attic runs **no database service of its own**. `atticd` keeps its metadata (caches, objects, NARs,
chunks, the GC's dates) in the database named by `[database] url`. The nixpkgs module's default is a
SQLite **file**, `sqlite:///var/lib/atticd/server.db`; PostgreSQL is an option, which attic's
template recommends for production (`server/src/config-template.toml:44`).

What decides is the GC's reap rate. On SQLite a run frees at most **500 chunks**, on PostgreSQL
65 535 (`gc.rs:178-190`). With a retention of hours, every session restart re-uploads the set that
expired during the pause, so the worst case is **one full set reaped per day**. One full set of
truly-ours paths is at most about 2.2 GiB of NAR (see <<sizing>>), roughly 36 000 chunks at
FastCDC's 64 KiB average:

[cols="1,1,1",options="header"]
|===
| GC interval on SQLite | Chunks reaped per day | Against one set a day (≈ 36 000)

| 12 hours (default) | ≈ 1 000 | no: the disk grows without bound
| 1 hour | ≈ 12 000 | no
| **15 minutes** | **≈ 48 000** | **yes, 1.3 times the need**
| 10 minutes | ≈ 72 000 | twice the need
|===

The margin at 15 minutes is thin against that bound: with no public tier, attic holds the packages
too. Watch the dataset's `used`, and shorten the interval if it climbs.

**SQLite, with `[garbage-collection] interval` at 15 minutes.** No database service is added; the SQLite file lives in the cache's dataset.
PostgreSQL (nixpkgs `services.postgresql`, 65 535 chunks per run) is the fallback, if write
contention appears. Four watch-store daemons and a frequent GC writing to one SQLite file could
answer _database is locked_; that is unverified.

=== Quota — 8G per metalspace

A dataset `tank/nerd/attic` on each metalspace's NixOS guest, holding the chunk storage and the SQLite file, with a
quota of **8G**, well above the upper bound (1.15 GiB + 0.52 U), U being the unmeasured package outputs and cluster
closures. The quota is raised with `zfs set quota` if the 75 % alarm below fires.

`ndh-attic-dataset` creates it on the guest if it is missing and applies the quota at every boot; it is split into
three directories that reach the container as three disk devices: `state` (`/var/lib/private/atticd`, the chunks and
the database, owned through atticd's `StateDirectory`), `secrets` (`/var/lib/attic-secrets`, the server secret) and
`shared` (`/var/lib/attic-shared`, where the container writes its cache's public for the guest to publish). It is
**not** replicated to the `recover` pool: a cache refills from the next session's builds.

[[container-store]]
== The containers' `/nix/store` — an overlay on a snapshot of nerd-nixos's store

A cache container mounts its `/nix/store` as an overlay **from the start**. Their lowers are a **ZFS snapshot of
nerd-nixos's own store** on top of the EROFS layers nerd-nixos already mounts: `deliver` takes that
snapshot of nerd-nixos's upper and DB in one command. nerd-nixos built the container's system into its
own store when it switched, so the snapshot already carries it; the container's upper, a per-container
ZFS dataset, starts **empty** and only receives what the container itself writes. Implemented by
`modules/nixos/incus-nixos-container.nix`.

[cols="1,3",options="header"]
|===
| Rule | Why

| the store overlay's lowers are **one ZFS snapshot of nerd-nixos's upper on top of the EROFS
layers, flat**, never nerd-nixos's live `/nix/store` and never an overlay of the layers
| the live store changes as nerd-nixos switches and collects garbage, and in OverlayFS a lower that
changes while mounted is undefined; a snapshot cannot change. An overlay as lowerdir mounts, but the
kernel silently falls back to `index=off` ("does not support file handles", measured 2026-10-11).
The snapshot's directory has file handles: with **one** snapshot over the EROFS layers, `index=on`
holds (measured 2026-10-14). Once nerd-nixos has frozen layers, a container stacks two snapshots or
more, ZFS snapshots have a null filesystem UUID, and the kernel drops `index` silently (measured on
the probe, 2026-10-14): the store unit then neither requests nor requires `index=on`, and the stamp
beside the upper — the snapshot and every ZFS layer by GUID, the layers' content and order — is the
only guard (store-freeze spec, _Rules that hold at every level_)

| one **layer contract**, `/etc/ndh/store-layers.json`, rendered by `erofs-store-mount.nix`
| the ordered lowerdirs (newest first, `.003:.002:.ro-store`), the options a consumer must find on its
mount, and `upperRoot`, where nerd-nixos's upper dataset is mounted (from `erofs-store-layers.nix`). A
second, hand-written list would drift. The flox NRI plugin's pod stores are a candidate second
consumer

| the store unit **asserts** the effective mount — the snapshot's upper over the layers stamped at
delivery in `lower.layers` (nerd-nixos's frozen layers, then the contract's EROFS ones), and every
required option — and fails hard, leaving nothing mounted (store-freeze spec, _What the containers
need from increment 1_)
| it replaces nix's `check-mount`, which must be off: nix wants lowerdir to be the lower store's
single directory, and these lowers are four

| nix's lower store is a separate **read-only metadata view**: an overlay of the same lowers plus a
shim holding an empty `.links`, and the snapshot's DB
| nix reads paths and metadata there, never through overlayfs. The shim: nix 2.34 creates `.links`
even in a read-only store (`src/libstore/local-store.cc:139`), and neither the layers nor the
snapshot carry one

| the view's DB is a **copy of the snapshot's DB**, WAL included, taken in the **same** `zfs snapshot`
command as the upper
| one command snapshots both datasets atomically, so the paths the DB calls valid are the paths the
snapshot holds (measured: a path deleted from the live store afterwards stays valid in the copy). A
copy, opened normally: SQLite's `immutable` mode would ignore the WAL. It replaces the DB generated
once per layer set by `--dump-db`/`--load-db` (2026-10-11)

| the container's lowers are **exactly** nerd-nixos's stack: its snapshot over its layers, in its order
| the copied DB is nerd-nixos's. Measured with a contract one layer short: paths the DB calls valid
were absent, `deliver` copied nothing, and the container broke ("Command not found")

| the container's `/nix/var/nix` lives on its dataset, beside the upper
| `deliver` sets the container's profile host-side through the same store, no SSH needed

| the snapshot is **reached host-side** before anything uses it
| `.zfs/snapshot/{name}` is automounted on first access, and an access from a private mount namespace
does not see a mount made outside it: ENOENT (measured 2026-10-14)

| the stamp beside the upper names the **snapshot and the layer set**; a mismatch fails the store
unit before mounting and names `deliver`
| the kernel does NOT refuse an `index=on` upper over a newer snapshot of the same dataset (measured
2026-10-14), so the binding is ours

| **one snapshot per container**: `deliver` destroys the previous one only once the container runs
on the new one
| a snapshot holds every block nerd-nixos frees after it, so the latest only is kept

| the view enters the container as **two plain read-only binds**, its store and its DB
| the view's store is a mount of its own, and the kernel refuses a recursive read-only bind
("Recursive read-only bind-mounts aren't currently supported by the kernel", measured 2026-10-14)

| the store unit runs **only once the container's dataset is mounted**
| `create` makes the dataset, and zfs-mount mounts it, not a mount unit, so `RequiresMountsFor`
cannot wait for it. Without the condition the unit ran at first boot on the root fs, and the dataset
then hid that upper (measured 2026-10-14)

| the host-side store URL names the view's real directory, never a symlink to it
| nix refuses a symlink on a store path or its parents (measured 2026-10-14)

| an extra device states its **`type`**, and never targets `/run` or `/tmp`; both are asserted at
evaluation
| Incus wants the type positionally and refuses it among the keys ("Unsupported device type"); the
container's systemd mounts tmpfs on `/run` and `/tmp` at boot, over the device (attic's environment
file at `/run/attic` was simply not there, 2026-10-14)

| a device's **source must exist before Incus autostarts** the instance
| a missing source fails the autostart three times, then gives up ("Missing source path", measured
after a reboot of the probe). sops-nix decrypts into `/run/secrets` during activation, before any
service, so a sops secret qualifies; a file written by a later service would not

| the containers' firewall is **nftables**
| the iptables firewall needs `xt_*` modules a container cannot load; nerd-nixos had loaded
`xt_pkttype` only by chance, and after its reboot the firewall unit failed in every container

| a delivery's copy runs **without checking signatures**, and normally copies nothing
| the snapshot carries the system, so the copy only checks that it does. Its source is nerd-nixos's
own store, which built or validated every path, and most carry no signature: a checked copy refused
the first path of the first real delta (2026-10-14)
|===

[source,ini]
----
# the container's store setting — /nix/.lower and /nix/.upper are binds from nerd-nixos
store = local-overlay://?lower-store=local%3Froot%3D/nix/.lower%26read-only%3Dtrue&upper-layer=/nix/.upper&check-mount=false
extra-experimental-features = local-overlay-store read-only-local-store
----

**The overlap no longer depends on the layers' lock.** On 2026-10-11, against layers from an older
lock, 525 of a container's 535 paths were outside them, and a copy-based delivery would have put them
all in its upper. With the snapshot, everything nerd-nixos built since its layers is in the
container's lowers too. Measured on 2026-10-14 on a throwaway nerd-nixos: `deliver` copied **0**
paths for both `probe` and `attic` (attic's closure had cost 43 MB of upper by copy), and both uppers
stayed at about 11 KB. How that holds over nerd-nixos's life is the next section.

The cache containers are **unprivileged**: each runs in its own user namespace, and every disk device is shifted.

=== Across nerd-nixos's life — what moves under a container

A container's lowers are nerd-nixos's EROFS layers, so the container lives through every event of
nerd-nixos's own life cycle. That cycle is rke2lab's
`docs/architecture/nixos-substrate/erofs-store-layer-stack.adoc`: a VM is materialized with its
layers and pools, its first boot hands over to the target configuration and reboots, and from then
on a generation is either switched inside the VM or delivered as an **appended** layer; replacing a
layer's content means re-provisioning. Each event does something different to a container:

`deliver` is the one gesture for A and B, and it absorbs the former `switch` (activate a delivered
system in the running container) and `reset` (set an upper aside after a layer change): every
delivery is a restart on a fresh upper, the way nerd-nixos itself takes a new generation; service data
lives on its own devices. B is decided ("every generation is an EROFS layer") but **not
implemented**: the layer list is fixed at three in `modules/nixos/erofs-store-layers.nix`, one source
the whole fleet shares. A probe that rebuilds the image tests **C**, not B: the materializer refuses
it, which says nothing about an append (a wrong conclusion drawn exactly that way on 2026-10-14,
discarded before push).

=== The tests the implementation must pass — the container

Measured on 2026-10-14 on a throwaway nerd-nixos (`incus-probe`, standalone Incus), with the snapshot
delivery (`aab6235a`): tests 1, 2, 3, 5, 6 and 7 pass, and test 4 rests on the snapshot measurements.
Test 8 passed **synthetically**: a runtime drop-in gave the store unit a contract one layer short, the
unit refused before mounting and named `deliver`, and `deliver` then restarted the container on a new
snapshot. The same run showed why the container's stack must be nerd-nixos's own (the identity rule

Four conditions:

. **share the paths, not the boot.** nerd-nixos's generation is a VM's (kernel, initrd, EROFS mounts
  in the initrd) and cannot boot as an Incus container. The container's own system is a
  `boot.isContainer` configuration, evaluated by nerd-nixos's generation;
. **the container's system is in nerd-nixos's store before the delivery**: `deliver` refuses a system
  nerd-nixos has not switched to, since the snapshot would not carry it;
. **the system does not come from the cache that does not exist yet.** attic's own container gets its
  system from the snapshot, not by substitution;
. **the container never evaluates a flake.** Evaluation, the incident's vector, stays on nerd-nixos.

== Hosting — one Incus service, two owners of instances

The Incus service already belongs to ndh: it is part of nerd-nixos's configuration
(`modules/nixos/incus.nix`, `incus-cluster.nix`). On that one service, instances have two owners:

[cols="1,1,2",options="header"]
|===
| Owner | Project | Instances

| rke2lab, through CAPN
| `rke2lab`
| the cluster nodes, which come and go with each grow

| ndh
| its own project, not `rke2lab`
| the cache containers, which outlive any cluster
|===

The infrastructure containers stay out of `rke2lab`, so nothing that tears down or re-grows a
cluster can reach them. This is the single-owner rule applied to a shared service.

=== Placement is stated, never left to Incus

In a cluster, an instance created without a `target` lands on a member that Incus chooses. These
containers depend on things that exist on **one** member only: their lowers (that member's
`/nix/.ro-store*`), and for attic the `nerd/attic` dataset. So:

* each metalspace's cache container has its own metalspace's Incus member as its target (bioskop for attic.bioskop,
  nikopol's for attic.nikopol), since each depends on that member's lowers and `nerd/attic` dataset
  (<<per-metalspace>>); a standalone Incus takes no target;
* none of them migrates when its member is evacuated: `create` sets `cluster.evacuate=stop`.

=== One module for both containers

Every ndh instance is declared through one module (`modules/nixos/incus-nixos-container.nix`):

* the container declaration, with its project, its target and its devices;
* the overlay store described above;
* the delivery: switch nerd-nixos, then a converge delivers each instance whose system, profiles or devices differ
  from its declaration, keeps it if healthy, and rolls it back onto its snapshot if not.

Each service then adds only its own NixOS configuration: for attic, `services.atticd` (SQLite, no database service),
`modules/nixos/attic-cache.nix`.

`services.atticd` comes from ndh's stable nixpkgs, and `services.atticd.package` from unstable (attic `7a19204d`, the
revision this spec's source facts were read on), the way `modules/.common.d/headscale-pkg.nix` pins headscale. The
hosts' `attic-client` takes the same revision.

[[revocation]]
=== Revocation — the events that rotate a cache's server secret

A token ends after 14 days by itself (see <<write-tokens>>); before that, attic cannot revoke one token alone, so every
event below ends all the tokens of the caches it names. Every machine reads BOTH caches, so it holds a read token of each: an event that touches a
machine rotates both server secrets.

[cols="2,1",options="header"]
|===
| The event | The caches to rotate

| a machine holding tokens is lost, reinstalled or retired
| both (its read tokens are for both; its write token for its own metalspace's)

| a token is seen anywhere it should not be: a log, a transcript, a commit, a file outside
`ndh.atticClient.paths`
| the cache that issued it (the `machine` line of a netrc fragment, or the write token's endpoint);
both if it cannot be told

| a machine's host key is rotated or exposed (its tokens' ciphertext was sealed to it)
| both, since that machine holds tokens of both

| a cache container's disk is copied or restored elsewhere (its server secret went with it)
| that cache
|===

The rotation, for each cache named, then the re-issue:

. rotate the server secret: in the cache container, remove `/var/lib/attic-secrets/server.env`, then
  restart `attic-server-secret` (it generates a new one, which never leaves the container) and
  `atticd`. Every token of that cache, write and read, stops working at that moment;
. mint now: `systemctl start attic-token-mint` in that container, so every machine finds a valid token at its next
  pull instead of at the next weekly mint (a lost host is first removed from the declaration, so it gets none);
. each machine pulls by itself (`systemctl start ndh-attic-tokens` on a NixOS guest, or wait for its daily pull);
. check with <<read-test>> that the old read token gets 401 and the new one 200.

Until a host has pulled, it can neither upload nor substitute from attic. It falls back to cache.nixos.org and to
building.

[[read-test]]
=== The test the implementation must pass — an anonymous read is refused

[source,bash]
----
# a path known to be in the cache: {hash} of the fill's last system closure
curl -s -o /dev/null -w '%{http_code}\n' "http://{attic}/{cache}/{hash}.narinfo"
# → 401  (anonymous: refused)
curl -s -o /dev/null -w '%{http_code}\n' --netrc-file {netrc} "http://{attic}/{cache}/{hash}.narinfo"
# → 200  (read token)
----

attic answers **401** to a client without the permission. A **200 without a token** means the cache
was created or reconfigured `--public`: the cache is then not private, and this spec's condition for
the watch-store no longer holds.

⚠️ **The anonymous answer still tells present from absent.** This spec read attic's source as masking
a missing object behind the same `Unauthorized` (`server/src/error.rs:194-205`, `:218`). Measured on
2026-10-14 against attic `7a19204d` on the probe, anonymous:

[cols="2,1,1",options="header"]
|===
| Request | Object in the cache | Object absent

| `GET` or `HEAD` `/{cache}/{hash}.narinfo`
| 401
| **404**

| `GET` `/{cache}/nar/{hash}.nar`, `/{cache}/nix-cache-info`, an unknown cache
| 401
| 401
|===

So anyone who reaches the port can test whether a store hash they already know is cached, without
reading anything of it. Reaching the port is the fabric segment only, and a hash has to be known
first, so the exposure is small; it is still one more reason never to listen beyond the fabric. The
read test therefore uses a hash **known to be in the cache**, as written above: an absent one answers
404 and proves nothing.

⚠️ **nix caches narinfo answers**, positive ones included, under `~/.cache/nix`. A substitution test
run after a successful one answers from that cache and looks authorised without a token. Run it with
an empty `XDG_CACHE_HOME` and `narinfo-cache-positive-ttl = 0` (measured the same day: the cached run
printed the path, the clean run got the 401).

Measured the same day, with a read token: `nix path-info` through a `netrc-file` whose `password` is
the token reads the narinfo, the path carries the cache key's signature, and `nix store verify`
checks it against that key. A read token is refused a configuration change (403).

nix build "git+file:///Volumes/git-bare-store/seedmatic/ndh.git?ref=develop&rev=$REV#nixosConfigurations.bioskop-nixos.config.system.build.toplevel"
nix build "github:seedmatic/ndh/$REV#darwinConfigurations.nikopol.system"

=== ❌ Publish our builds to a public cache

No consumer needs one (see <<no-public-cache>>). A public path can be copied or indexed after a
purge, and the 2026-10-10 incident was exactly a store watched into a public cache.

=== ❌ Lock a package of ours by a bare store path in a cluster's env

The cluster builder cannot fetch from attic, so a path only attic holds fails the activation. Lock
our packages by flake ref (`[install] x.flake = "github:seedmatic/…#pkg"`), which the builder can
build (see <<cluster-builds>>).

=== ❌ Evaluate a working tree on the builder — even once, even clean

`nix build .#x` in a decrypted checkout copies its files in clear. It also records that copy in the
fetcher cache for the revision, where a later `?rev=` build of the same commit picks it up (see
<<revisions-only>>).

=== ✅ A watch-store on every host, behind authenticated reads

[source,bash]
----
# on each of the four hosts, as the daemon's service: the cache was created without --public
attic watch-store seedmatic
----

Allowed under one condition, which <<read-test>> checks: every read needs a token. What it uploads
is listed in <<watch-store-sees>>, and what it costs in trust in <<trust-model>>.

=== ❌ A watch-store towards a cache readable without a token

On a `--public` cache, or on a public one like `nxmatic.cachix.org`, a watch-store brings the
incident back as it was: every dirty evaluation of every host published.

=== ❌ Share one write token between hosts, or give one more than push

One token per host, each with its own `--sub`, never one copied to several hosts. And no
`create-cache`, `configure-cache`, `delete` or `destroy-cache`: the tokens sit on four hosts, one of
them on the corporate side, and none can be revoked alone yet.

=== ❌ Derive the key-name list from `trusted-public-keys`

That list holds `seedmatic-fleet-1`, which signs every local build, so the cache would stay
empty. Write the list out: the upstream substituters' key names, plus the layer key.

== Troubleshooting

[cols="2,2,2",options="header"]
|===
| Symptom | Cause | Fix

| the dataset grows week after week
| GC on SQLite, capped at 500 chunks per run
| a GC interval of 15 minutes on SQLite; PostgreSQL if that is not enough

| a superseded path is never collected
| retention 0 (the default), or a `cache configure` that reset it
| set `--retention-period` in the same declarative step as every other cache setting

| attic holds nothing after a pause
| expected: the retention is the active session (see <<retention>>)
| the next session's builds refill it; a machine's running closure is in its own store anyway

| a cluster's activation fails on a path of ours
| it is locked by a bare store path that only attic holds
| lock it by flake ref, so that the cluster builder builds it (see <<cluster-builds>>)

| a cluster rebuilds a nixpkgs package
| a pin Hydra did not build, or an overlay of ours changing a widely used derivation
| test 0 of <<builder-tests>> names it; move the pin, or narrow the overlay

| the cache uploads paths cache.nixos.org serves
| they carry no upstream signature locally: layer registration, or a local rebuild
| the layer key for the layer paths. The rest is disk, until the fork.

| an anonymous narinfo request returns 200
| the cache was created or reconfigured `--public`
| make it private again. Until then the watch-store's condition does not hold, so stop it.

| a host cannot substitute from attic at all
| its `netrc-file` is missing, or its token predates the server secret's rotation
| `journalctl -u ndh-attic-tokens` (NixOS) or `/var/log/ndh-attic-tokens.log` (darwin): « fetched N file(s) » and the
unseal's line; then `systemctl start attic-token-mint` in the cache container

| a pull gets 404 on its token files
| the container's mint failed, or this machine is not among its targets
| `journalctl -u attic-token-mint` in the cache container: « done: N ciphertext file(s) »; the declared targets are
`ndh.atticCache.tokenTargets`

| the unseal refuses a token file that was fetched
| it is sealed to another key than this machine's host key
| the target's `publicKey` must be this machine's own current slot (`targets.nix`)

| the cache stays empty
| `seedmatic-fleet-1` is in `upstream-cache-key-names`
| remove it: it signs every local build

| a host is lost, or a token leaked
| attic tokens cannot be revoked one by one
| rotate the server secret and re-issue the tokens (see the revocation steps in <<secrets>>)

| the container's store reports a stale file handle (ESTALE)
| a lower changed under `index=on`
| restart the container on the layer set nerd-nixos booted
|===

[[attic-fork]]
== The real fix — an attic fork, later

The read token **confines** a plaintext path that reaches the cache; it does not keep it out. The
fix is upstream of the token: the cache must refuse such a path. attic offers no hook for that, so
it is a fork, meant to be contributed upstream. Decided with the operator on 2026-10-10, for later.

[cols="1,3",options="header"]
|===
| Change | What it does

| a daemon-to-server protocol
| the **server** judges what enters, rather than a filter in each client. The natural place for it
is `get-missing-paths`, the exchange that already opens every push: the server can answer "served
upstream" or "refused" as well as "missing".

| an upstream check by query, not by signature
| ask the upstream caches for the narinfo, instead of reading local signatures. That closes the
297-path gap, and makes the layer key a convenience rather than a necessity.

| a content filter, which refuses
| with the repository's `.sops.yaml` shared to the server: a `# sops:encrypted` annotation followed
by anything but an `ENC[` value marks a decrypted file. Measured on `keys.yaml`: the annotation
survives in clear in both states (9 annotations, each followed by `ENC[` when encrypted, by a `\|`
block when decrypted). A second test, independent of the rules, looks for private-key armour with a
body, an `AGE-SECRET-KEY-1`, and GitHub token shapes, because the `.sops.yaml` itself was once wrong
(2026-08-27).
|===

Two more contributions follow from the operator's choices on writers (see <<trust-model>>):

[cols="1,3",options="header"]
|===
| Change | What it does

| revocable per-host tokens
| a token per host that can be ended alone, without rotating the server secret. That needs state on
the server, a list of revoked subjects or of issued tokens, where attic is stateless today
(`token/src/lib.rs:3-12`).

| trust restored per writer
| the content check above, at upload, so that no writer can publish what the server rejects. Or
per-writer signing keys that consumers can tell apart.
|===

The filter **refuses**; it never re-encrypts. A `-source` path is addressed by its content, a cache
signature covers the NAR hash, and sops draws a fresh IV at each encryption. A rewritten path would
be a different path, and every closure that references it would have to be rebuilt.

[[f7]]
== Reading and pushing — declared, off

Each machine's client is declared (`modules/.common.d/attic-client.nix`), and off: `ndh.atticClient.read.enable` adds
both caches as substituters (its own metalspace's first, priority 50, then the other's, 51; after cache.nixos.org at
40) with the unsealed netrc, and trusts their keys; `ndh.atticClient.watchStore.enable` runs the watch-store towards
its own metalspace's cache with its write token. Turning them on is a decision of its own, one machine first.

[[open-questions]]
== Open questions

* **The retention value**: 6 hours is a proposal in the operator's order of magnitude, to confirm
  against a real session.
* **Package outputs, cluster node closures and in-cluster env closures**: their size, once they are built.
* **The cluster builder**: the container, its dataset and quota, its keys born
  inside, the route from the nodes' `vmnet` segments to it over the fabric, and the tests of
  <<builder-tests>> on a throwaway first.
* **The node-base nix configuration** (`builders`, `max-jobs = 0`, `builders-use-substitutes`,
  `require-sigs`): a rke2lab follow-up.
* **The builder tests** (<<builder-tests>>): test 1 decides whether `cluster-build` stays untrusted.
* **The pod tier's lower changes while mounted**: it is the node's live `/nix`, which the flox
  controller grows and the node's GC shrinks. That is the case this spec forbids for tier 2. The hook
  reconciles the pod's store DB at every container start, which repairs the DB, not the overlayfs
  rule. Whether tier 3 should instead stack on the immutable layers is rke2lab's to decide.
