= A Machine's SOPS Identity (Shared Flake)
:toc: left

== Why this exists

Darwin and NixOS hosts share one flake, and each decrypts its secrets with an age identity. This note says
where that identity comes from, what happens when it is missing, and how a new machine joins.

The model is ndh `docs/ssh-keys-architecture.adoc` (Roles × Keys): a machine's identity is generated
**once by the operator** and kept in their keyring; nothing on a machine generates or copies one. The
earlier two-phase flow (`bootstrap`, which generated a key on first activation, then `enforce`) is gone:
every host behaves as `enforce` did.

== What a host does at activation

[source,text]
----
the keyFile is present ──► mode set to root:root 0400 on a NixOS guest ──► its public published ──► sops installs
the keyFile is absent  ──► ONE loud fault naming the path ──► the units that need secrets wait
----

* On a NixOS guest, the age bootstrap unit fails and `sops-install-secrets` with it; the console stays
  reachable (root autologin), so the operator can place the identity there.
* On darwin, the activation stops before anything else, with the same message.
* A NixOS guest that still imports its host's key (`ndh.sopsAgeKeyBootstrap.nixosHostKeyImport`, today the
  bringup images only) takes it from the host share first.

== Placing an identity

[source,bash]
----
# on the machine, as root (the console, or from bioskop once the push lands)
rm -f /var/lib/sops-nix/<machine>.age
umask 077; cat > /var/lib/sops-nix/<machine>.age   # paste the identity, then Ctrl-D
age-keygen -y /var/lib/sops-nix/<machine>.age      # must print the recipient listed in .sops.yaml
ndh-identity-reload                                # restarts sops and every unit that reads a secret
----

`rm -f` first: `umask` applies only when a file is created, and a file left by an earlier attempt keeps
its mode. The bootstrap sets the mode to `0400` anyway at its next run. On the serial console, `stty -echo`
before pasting keeps the private out of the console log.

== A new machine

1. The operator generates its identity into their keyring, and records its **public** recipient
   (`age1...`) — never `AGE-SECRET-KEY-...`.
2. The recipient is added to the `.sops.yaml` creation rules, then the affected files are re-keyed on a
   seat. For extensionless YAML secrets files (for example `.secrets`), pass explicit format flags:
   `sops updatekeys -y --input-type yaml --output-type yaml .secrets`.
3. The identity is placed on the machine (above), and the machine activates.

== Security reminders

* Never commit private age keys.
* Rotate immediately if private keys were exposed in logs or chat.
* Keep runtime secret path namespaces (`/run/secrets/nix-darwin-home/*`, `/run/secrets-per-user/*`) to
  avoid collisions. `/run/secrets.d` is sops-nix's internal generation storage; consumers use
  `/run/secrets`.
