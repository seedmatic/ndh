= Host Builder Phases (bootstrap → steady → requests)
:toc: left
:icons: font

== Overview

Every Darwin host in the fleet needs to build `aarch64-linux` derivations —
the NixOS side of itself. But a Mac cannot build Linux natively, which creates
a chicken-and-egg:

* The `aarch64-linux` builder we *want* is the host's own NixOS sibling next
  door (`<host>-nixos`, which also hosts incus). It is fast, native, and pulls
  from the binary caches.
* But that sibling does not exist yet the first time — it is precisely what we
  are trying to build and activate.

`ndh.hostBuilder` names this as a **lifecycle phase of the host**, with a single
host-derived knob rather than a hand-maintained `nix.buildMachines` block per
host:

`bootstrap`:: No NixOS sibling yet. Build `aarch64-linux` locally through the
embedded QEMU `linux-builder` (baremetal only — a `vm`-form host cannot run a
nested builder). This is the *only* way to build+activate `<host>-nixos` the
first time.

`steady`:: `<host>-nixos` is up. It becomes the builder: the local
`linux-builder` is turned off and the Mac offloads over ssh, pulling
dependencies straight from the caches instead of uploading its whole closure.

`requests`:: Every build is a request. The Mac builds nothing itself
(`max-jobs = 0`): its own `aarch64-darwin` builds go through ssh-ng to its own
`nix-store` account (the loopback, `nix-store.<host>`), its `aarch64-linux`
builds to `<host>-nixos`. `ndh-builders fabric` adds the other metalspace's Mac
and guest, over the tailnet (`nix-store.<peer>` → `<peer>.<tailnet domain>`);
`ndh-builders metalspace`, the default, leaves them out.

The builder name is *derived* from `config.profile.host.hostName`
(`<host>-nixos`), never hardcoded — so the same module offloads
`bioskop → bioskop-nixos` and `nikopol → nikopol-nixos`. The Mac's nix-daemon
reaches it through the `nix-store.<host>-nixos` ssh alias: the guest's
`nix-store` account (forced `nix-daemon --stdio`, a trusted nix user), with the
fleet's `nix-store` certificate. Builds never log in as root.

== The three phases

[mermaid]
....
stateDiagram-v2
    direction LR
    [*] --> bootstrap: fresh Mac,<br/>no NixOS sibling
    bootstrap: bootstrap
    bootstrap: local linux-builder (QEMU)<br/>baremetal only
    steady: steady
    steady: offload to the host's -nixos guest<br/>linux-builder OFF
    bootstrap --> steady: the -nixos guest built,<br/>activated and incus up
    requests: requests
    requests: max-jobs = 0, darwin via the loopback<br/>other metalspace as fallback
    steady --> steady: darwin-rebuild switch
    steady --> requests: way back proven,<br/>one fallback cut proven
    requests --> steady: way back
    note right of bootstrap
        vm-form hosts (nikopol) can
        never run a nested builder,
        so they start in steady
    end note
....

The gate lives in one place: `modules/darwin/linux-builder.nix` only selects the
embedded builder when the host is baremetal *and* `ndh.hostBuilder == "bootstrap"`.
`modules/darwin/host-builder.nix` owns the reverse: in `steady` it wires
`nix.buildMachines = [ <host>-nixos ]` + `builders-use-substitutes`. The two are
mutually exclusive by construction — never both on.

=== The builders in `requests`, and `ndh-builders`

Two lists are generated at every switch: `/etc/nix/machines.metalspace` (the
loopback and the own guest) and `/etc/nix/machines.fabric` (the same, plus the
other metalspace's Mac and guest). The daemon reads `builders =
@/var/lib/ndh/builders/active`, a root symlink to one of them; nix-darwin
renders no list of its own. nix reads the list when a command's build hook
starts, so `sudo ndh-builders metalspace|fabric` applies from the next nix
command, with no daemon restart; `ndh-builders` alone prints the mode. A
missing list is skipped silently by nix, and with `max-jobs = 0` every build
would then fail: the command refuses such a mode, and the activation sets a
missing or dangling pointer back to `metalspace`, keeping an existing choice.
`fabric` is for spreading builds while the operator is on their local network;
it is switched by hand only.

nix sends a build to the machine with a free slot whose busy slots divided by
its `speedFactor` is lowest (nix 2.34 `build-remote.cc`): home carries 10, the
other metalspace 1, so an idle peer wins as soon as home has one build running.
nix gives ssh no timeout, so every `nix-store.*` alias sets `ConnectTimeout 5`
and `ServerAliveInterval 15` × 4: a cut tailnet route fails within seconds.

A receiving daemon has no cap across its connections, so `ndh.builderCapacity`
splits each builder's capacity by who sends the builds: its own `max-jobs`, its
own metalspace's entries (`home`), the other's (`peer`). Darwin: 4 own (0 in
`requests`), 3 home, 1 peer; NixOS: 2 own, 6 home, 2 peer. An assertion refuses
`max-jobs = 0` when a list has no entry for the machine's own system.

The trusted `nix-store` account receives its client's `builders`, so a build
received through the loopback can be forwarded again (chaining), bounded by the
free slots: the last hop builds it. An episode shows as several slots held at
once: `sudo lsof +D /nix/var/nix/current-load` lists the hooks holding them.

== Per-host state

[cols="1,1,1,1", options="header"]
|===
| Host | `ndh.hostBuilder` | Local linux-builder | Remote buildMachine

| bioskop (first bring-up) | `bootstrap` (default) | ✅ baremetal | —
| bioskop (post-bring-up)  | `steady`              | ❌            | `bioskop-nixos`
| nikopol                  | `steady`              | ❌ (vm, never) | `nikopol-nixos`
|===

`nikopol` is a `vm`-form host: it can never run a nested `linux-builder`, so it
declares `steady` from day one and always offloads to `nikopol-nixos`. The
`bootstrap` default exists for baremetal Macs (`bioskop`) that must first build
their own sibling.

== Cold bootstrap from zero (first build ever, no builder at all)

`bootstrap` assumes `darwin-rebuild switch` can stand up the embedded
`linux-builder`. On a *truly* fresh Mac there is a deeper chicken-and-egg: the
embedded builder's own guest system is an `aarch64-linux` derivation (customised
here — 9p cache-key mounts, host port), so building it *itself* needs an
`aarch64-linux` builder. `darwin-rebuild switch` then fails with
`platform mismatch … Required system: 'aarch64-linux'` — no machine to offload
to yet, and it falls back to building locally on `aarch64-darwin`.

Escape: bring up a *stock*, cache-substitutable `linux-builder` (it downloads
from `cache.nixos.org`, no local `aarch64-linux` build), wire the nix-daemon to
it, then build `<host>-nixos` directly. You do **not** need `darwin-rebuild
switch` for a renew — the goal is `<host>-nixos`, not the embedded builder.

=== 1. Launch + wire the temporary builder (one app)

[source,bash]
----
nix run .#bootstrap-linux-builder          # stays attached (the builder console)
----

This app (`modules/.common.d/bootstrap-linux-builder.d/`) does everything the
cold start needs:

* launches the *vz* `linux-builder` from `nixpkgs-unstable` (the pinned nixpkgs
  lacks `darwin.linux-builder-vz`), which substitutes from cache — no
  `aarch64-linux` build;
* pins `KEYS` to a dedicated state dir so the generated keypair is stable (not
  left in whatever cwd you launched from) and lets `create-builder` install it
  into `/etc/nix/builder_ed25519`;
* writes the root-side wiring — the ssh alias
  `/etc/ssh/ssh_config.d/100-linux-builder.conf` (so root's ssh reaches
  `localhost:31022`) and an `/etc/nix/machines` entry (backing up any existing
  one) — using the ambient setuid `sudo`, not a pinned one.

Tear it all down (kill the VM + remove the temporary wiring) with:

[source,bash]
----
nix run .#bootstrap-linux-builder -- --stop
----

[NOTE]
====
The builder runs *attached* in this terminal, so run step 2 from a second
terminal. The `KEYS`-in-cwd trap and the root-side key/ssh/machines wiring were
formerly manual (and easy to get wrong — the generated key sitting in a user's
cwd yields `Permission denied (publickey)` on offload); the app now owns them.
====

=== 2. Verify + build the sibling (second terminal)

[source,bash]
----
sudo nix store info --store ssh-ng://linux-builder        # go/no-go: must answer
nix build --system aarch64-linux nixpkgs#hello --no-link  # smoke test
TMPDIR=/tmp nixos-rebuild boot --flake .#<host>-nixos --target-host root@nerd-nixos.local
ssh root@nerd-nixos.local reboot
----

Use `boot` + reboot, *not* `switch`, for a first bring-up: the guest has never
booted the target config, and an online `switch` runs activation scripts before
`systemd-tmpfiles` / the boot oneshot seed the bringup-runtime profile, so the
age-key enforce fails (see bringup-runtime.nix). `boot` only installs the
bootloader + sets the system profile — no online activation — and the reboot
brings the guest up in the correct order (seed → enforce), renamed to
`<host>-nixos`. (`nixos-rebuild switch --target-host` for a *day-2* rebuild is
fine: the profile is already seeded, and the activation-time seed in
bringup-runtime.nix covers a never-booted online switch too.)

`TMPDIR=/tmp` is required: `nixos-rebuild`'s ssh `ControlPath` lives under
`$TMPDIR`, and a long `$TMPDIR` (e.g. macOS `/Users/<user>/.tmpfs`) overflows the
~104-byte Unix-socket limit → `too long for Unix domain socket`.

At first boot the guest carries the generic bringup hostname `nerd-nixos`, so
target it as `nerd-nixos.local` (fall back to the guest IP if mDNS is flaky) —
`<host>-nixos.local` does not resolve until *after* the reboot renames it.

Once `<host>-nixos` is up and trusted as a builder, `--stop` the temporary
builder and promote to `steady` (below); the hand-wired stock builder +
`/etc/nix/machines` are superseded by the module-generated wiring.

== Operator: promoting a host to steady

Once `<host>-nixos` is built, activated, and serves its `nix-store` account:

. Set `ndh.hostBuilder = "steady"` in `hosts/<host>/darwin.nix`.
. `darwin-rebuild switch` — regenerates `/etc/nix/machines` pointing at
  `<host>-nixos`, and drops the embedded `linux-builder` launchd job.
. Verify: `sudo nix store ping --store ssh-ng://nix-store.<host>-nixos` succeeds, and a
  fresh `aarch64-linux` build offloads (watch `nix.settings.builders`).

To fall back (e.g. sibling wiped), flip to `bootstrap` and re-switch — the
embedded builder returns on baremetal hosts.

== Operator: promoting a host to requests

Before the first host moves, 🎛️ proves on it, once: the way back (a build with
`--option max-jobs 4 --option builders ''`, and ndh-switch's local-build
option), and one fallback cut (the tailnet route to the peer metalspace down:
a build falls back to home within the timeout).

. Set `ndh.hostBuilder = "requests"` in `hosts/<host>/darwin.nix`, and switch:
  the activation points `ndh-builders` at `metalspace`.
. Verify: `sudo nix store ping --store ssh-ng://nix-store.<host>` succeeds, and
  a fresh `aarch64-darwin` build is sent to the loopback.

To go back, flip to `steady` and re-switch; for one command,
`--option max-jobs 4 --option builders ''`.
