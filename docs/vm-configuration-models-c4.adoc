= VM Configuration Models (Lima + Tart) — C4-Style UML
:toc: left

== Purpose

This note describes the two VM configuration models currently present in `nix-darwin-home`:

* the active Lima VM configuration model (`lima.configGenerator`), and
* the Tart VM configuration target architecture (future plan).

It also explains how both models relate to each other and to the host profile model.

IMPORTANT: for Lima, first-boot guest bring-up is primarily cloud-config/cloud-init driven; this note now models that path explicitly.

== Host Role Taxonomy (Runtime-Agnostic)

To avoid overloading a single "host" term in mixed Lima/Tart topologies, this note uses explicit roles:

* **Access Host**: where the operator is currently connected (for example shared screen/auto-login session).
* **Virtualization Host**: where guest runtime engines execute (Lima/Tart/Virtualization.framework).
* **Control Host** (optional): where orchestration commands are initiated.

A single machine may provide one or multiple roles. For example, one host can be both Access Host and Virtualization Host, while another host may provide only Access Host.

Environment naming follows the same separation:

* `NDH_RDP_HOST` (Access Host for RDP/screen-sharing access path)
* `NDH_VZ_HOST` (Virtualization Host for VM runtime orchestration path)
* `NDH_VZ_GUEST` (guest identity for virtualization runtime path)
* `NDH_USER` (operator/user identity for NDH helpers)
* for `nix-darwin-home`-owned variables, use `NDH_*`.
* avoid runtime-coupled naming like `LIMA_HOSTNAME` for cross-runtime control paths.

See also link:env-prefix-policy.adoc[Environment Variable Prefix Policy].

== Scope and Artifact Boundaries (Do Not Mix)

This document covers three related but distinct concerns:

* **NixOS guest VM boot artifacts** (Lima today, Tart/NixOS adapter in plan):
  raw/qcow2-style VM disk artifacts + cloud-init/NoCloud seed.
* **NixOS OCI/container artifacts**:
  optional container payloads for container runtimes (not canonical VM boot media in this plan).

Cloud-init semantics in this note apply to **NixOS guest paths**.

=== Artifact mapping matrix

* **Lima + NixOS** -> NixOS VM disk image (`nixos.img` raw/qcow2 family) + NoCloud/cidata seed.
* **Tart + NixOS (planned)** -> same NixOS VM disk artifact, exported/attached through NBD bridge + NoCloud-style seed via Tart adapter.
* **NixOS OCI** -> optional runtime payload format (non-canonical for VM boot in this plan).

Adapter parity note: Lima and Tart perform the same orchestration role and can share the same canonical disk artifact source (`.qcow2`/raw), with Tart consuming it through NBD.

=== Canonical convergence — single disk artifact via NBD bridge

Canonical convergence model:

* Keep one canonical NixOS disk artifact (`.qcow2`/raw) as source of truth.
* Reuse that same artifact for Lima directly.
* Export it via NBD (`qemu-nbd`/`nbdkit`) for Tart adapter attachment path.

This removes `.oci` as canonical Tart bootstrap input and minimizes format translation.

== Shared Model — Cloud-Config Contract (Canonical)

Both runtime paths are defined against one canonical guest bootstrap contract:

* Cloud-init/NoCloud-style seed payload for NixOS guest bootstrap.
* Shared host/profile-derived identity and topology inputs.
* Common guest bootstrap steps (user/network/secret bootstrap/reconfigure hooks).
* Runtime-specific adapters that transport/inject the same contract.

In other words:

* Lima = active adapter implementation of the shared cloud-config model.
* Tart = planned adapter implementation of the same shared cloud-config model.

=== Shared components

The two models should converge on these shared components:

* **Host profile contract**: `config.profile.*` and host identity derivation.
* **Seed schema contract**: metadata/user-data/network-config conventions for NixOS guests.
* **Guest bootstrap executor**: cloud-init-driven systemd path on NixOS.
* **Post-bootstrap orchestration contract**: remote `nixos-rebuild` / lifecycle commands.

=== Runtime layering architecture (explicit)

To avoid Lima-only coupling while preserving one guest intent model:

* Keep a **common NixOS guest base** module set (runtime-agnostic).
* Add **exclusive runtime bootstrap modules**:
** `lima-cloud-init` layer for Lima-specific datasource/mount/service ordering.
** `tart-cloud-init` layer for Tart-specific datasource/NBD/service ordering.
* Select one runtime layer through a single runtime selector option (e.g. `ndh.vmRuntime`).
* Enforce exclusivity with assertions so Lima and Tart runtime layers cannot be active simultaneously.

[NOTE]
====
Path neutrality rule:

* Guest-side mountpoints and config paths should be either runtime-neutral or explicitly runtime-scoped.
* Avoid Lima-only hardcoded paths in shared modules (for example, direct `/mnt/lima-cidata/...` assumptions in common guest logic).
* Runtime-specific path wiring belongs in runtime layers (`lima-cloud-init` vs `tart-cloud-init`).
====

== Model A — Lima Adapter (Current Implementation)

=== What it is

The Lima model is the currently active and mature path for host-managed VM orchestration.
The Darwin module `modules/darwin/lima-config.nix` derives host/profile-aware values and generates:

* `~/.lima/_config/lima.yaml` (from the evaluated Nix model), and
* `~/.lima/run.sh` (managed host orchestration wrapper).

On guest boot, the NixOS side consumes Lima cidata via `lima-cloud-init.service`
(`modules/nixos/systemd/lima-cloud-init.nix` + `lima-cloud-init.sh`), which is the key bootstrap mechanism.

=== Core inputs and invariants

* Host/profile identity comes from `config.profile.*`.
* Network topology is sourced from canonical catalog data (`catalog.netplan.rke2labNetplan`).
* Hostname-to-cluster mapping must be explicit (hard failure when missing).
* Script provisioning is done via activation (`system.activationScripts.postActivation`).
* Guest bootstrap depends on cidata mount (`/mnt/lima-cidata`) and `lima-cloud-init.service`.

=== Operational role

The Lima model is responsible for:

* VM runtime config materialization,
* cloud-init/cidata based first-boot guest reconfiguration,
* remote NixOS activation convenience commands,
* alignment with existing bootstrap + ZFS workflows.

== Model B — Tart VM Configuration Model (Scaffold)

[NOTE]
====
The previously drafted Tart Darwin module and scripts were intentionally removed because they did not match the required target architecture.
Tart is documented here as a future plan, not as an active module implementation in this repository.
====

=== What it is

The Tart target model in this plan is a runtime adapter around the same shared NixOS cloud-init contract,
with an NBD-backed shared qcow2/raw disk artifact as canonical input.
Unlike the removed draft, the intended design does not start from a bespoke Tart-only wrapper contract.

=== Core inputs and invariants

* Uses the same host/profile inputs as Lima at architecture level.
* Targets a common NoCloud/cidata payload format for NixOS guests.
* Keeps runtime-specific host logic in adapters (Lima adapter vs Tart adapter).
* Uses NBD-exported canonical qcow2/raw artifact as canonical Tart-side disk input.

=== Operational role

The Tart target model should provide:

* a Tart adapter that injects the same cloud-init payload shape used by Lima,
* an image-build pipeline for base artifacts,
* parity with shared guest bootstrap semantics.

== Relationship Between Models

=== Architectural relationship

The two models are sibling host modules under the same flake and profile system:

* Both consume shared host/profile configuration.
* Both should implement the same cloud-config/bootstrap contract for NixOS guests.
* Lima is the active runtime path today.
* Tart is a planned runtime adapter path for NixOS guests.

=== Canonical behavior policy

At this stage, canonical runtime behavior remains Lima-first.
Tart implementation remains deferred until it follows the shared cloud-init-first contract.

== Bootstrap and Disk Attachment Relationship (Lima vs Tart)

=== Lima bootstrap (runtime cloud-config)

* Host activation renders `lima.yaml` + helper scripts.
* Lima exposes cidata to guest (`/mnt/lima-cidata`).
* `lima-cloud-init.service` applies runtime bootstrap on guest boot.
* Post-bootstrap host commands (`~/.lima/run.sh`) drive `nixos-rebuild` + ZFS activation.

=== Tart disk attachment (NBD-backed)

* Host-side adapter exports/attaches NBD from canonical qcow2/raw artifact.
* Tart runtime receives NBD-backed disk attachment plus shared NoCloud seed contract.
* Future Tart adapter should also attach/serve NoCloud-style data so guest bootstrap can run common cloud-init steps.

[NOTE]
====
TBD — Tart NoCloud seed transport:

The concrete delivery mechanism for NoCloud seed data in Tart still needs to be finalized.
Candidate options include:

* attaching a seed ISO/cidata-style artifact, or
* using a native Virtualization.framework-compatible injection path.

Whichever option is selected, the guest-consumed seed schema must stay aligned with the shared cloud-config contract.
====

== Policy Decision (Current Plan)

For the canonical Tart + NixOS bootstrap path:

* use the same canonical `.qcow2`/raw artifact lineage as Lima,
* expose it to Tart through NBD bridge,
* keep shared NoCloud/cloud-init semantics for guest bootstrap,
* keep runtime-specific NBD wiring in Tart adapter logic.

Packer/IPSW paths are outside this canonical plan.

== Planned Nix -> Tart Input Strategy (NBD + shared disk artifact)

=== Phase 1 — Canonical Nix-produced VM disk artifact

* Build/resolve canonical NixOS `.qcow2`/raw artifact path.
* Publish deterministic path/reference as canonical adapter disk source.

=== Phase 2 — Adapter NBD bridge

* Tart adapter exposes the canonical artifact via NBD (`qemu-nbd`/`nbdkit`) and attaches it.
* Adapter also injects shared NoCloud seed for unified guest bootstrap steps.

=== Phase 3 — Contract convergence

* Keep cloud-init bootstrap steps shared across Lima and Tart NixOS paths.
* Keep NBD bridge concerns isolated to adapter layer.

=== Phase 4 — Runtime-layered module structure

* Refactor guest config into:
** common runtime-agnostic modules,
** `lima-cloud-init` runtime layer,
** `tart-cloud-init` runtime layer.
* Wire runtime selector to include exactly one runtime layer per build.
* Keep shared bootstrap semantics in common modules; keep datasource/transport details in runtime layers only.

=== How they relate

* They share host profile and orchestration contracts.
* They share a target guest bootstrap contract (cloud-init semantics for NixOS).
* They differ in *where bootstrap logic lives*:
** Lima: mostly runtime cloud-init/cidata at guest boot.
** Tart: runtime NBD disk attachment + shared cloud-init seed.
* Migration intent is to unify guest bootstrap behavior around shared cloud-init steps for NixOS guests.

=== Target convergence rule

For NixOS guests, runtime-specific logic must remain in adapters only.
Guest bootstrap semantics should be defined once in the shared cloud-config contract and reused by both adapters.

== Practical Reading Guide

* If you need current production behavior, read Lima model first.
* If you are planning migration, compare Level 3 component contracts.
* Treat Tart here as future architecture, not active module behavior.

== Current Status Summary

* Lima model: active and canonical runtime path.
* Tart model: future plan; drafted module artifacts removed.
* Relationship: migration target is shared cloud-init semantics for NixOS guests with runtime-specific adapters.
